### Test Case 1: End-to-End Data Parity (Golden Dataset Comparison)

*   **Purpose:** To verify that the migrated BigQuery stored procedure produces data in all target tables that is byte-for-byte identical to the data generated by the legacy KornShell script running its Oracle SQL. This is the ultimate output parity test.
*   **Setup:**
    1.  **Prepare Golden Dataset:** Populate the source tables in both Oracle and BigQuery with a comprehensive, identical dataset. This dataset should include various scenarios:
        *   Typical data values.
        *   Edge cases (e.g., minimum/maximum lengths, boundary dates).
        *   NULL values in columns where they are allowed.
        *   Data that triggers all branches of `CASE` statements and `COALESCE` functions.
        *   Data that results in zero rows, one row, and multiple rows for each target table.
    2.  **Legacy Run & Capture:**
        *   Execute the legacy `k_ausd_geschaeftspartner.ksh` script with a specific set of parameters (e.g., `p_JobKennung='LEGACY_GOLD'`, `p_EintragsNr='L1'`, `p_Stichtag='01012023'`).
        *   After successful execution, extract all data from the 6 target tables (`sof_ta_segm_prem`, `sof_ta_bpr_dn_evn_his`, `sof_ta_bpr_dn_evn`, `sof_ta_p_gesch_part`, `sof_ta_p_dn_nutzer`, `sof_ta_p_evn_empf`) from the Oracle database. Store this extracted data as the "expected output" (e.g., CSV, JSON, or a dedicated comparison database).
    3.  **Clean BigQuery Targets:** Ensure all 6 target tables in BigQuery are empty.
*   **Action:**
    1.  Call the BigQuery control stored procedure with the *exact same parameters* used for the legacy run:
        ```sql
        CALL `your_project.your_dataset.r_ausd_vertrag_control_sp`(
          'LEGACY_GOLD',
          'L1',
          '01012023',
          0 -- Assuming p_wiederanlauf_wert was 0 or empty in legacy run
        );
        ```
    2.  After successful execution, extract all data from the 6 target tables in BigQuery.
*   **Pass/Fail Criterion:**
    *   **Pass:** The data in each of the 6 BigQuery target tables is *identical* to the corresponding "expected output" captured from the Oracle legacy run. This includes matching row counts, column values, data types, and NULL handling.
    *   **Fail:** Any discrepancy in data content, row counts, or data types between the BigQuery output and the legacy Oracle output.

### Test Case 4: `p_wiederanlauf_wert` Default Handling (Identified Discrepancy)

*   **Purpose:** To verify how `p_wiederanlauf_wert` is handled when passed as `NULL` and to highlight a potential discrepancy with the legacy script's explicit defaulting to `0` if empty.
*   **Setup:**
    1.  Populate source tables with minimal data to ensure successful execution of the core logic.
    2.  Ensure `job_tracking_table` is empty.
*   **Action:**
    1.  Call `r_ausd_vertrag_control_sp` providing `p_wiederanlauf_wert` as `NULL`.
        ```sql
        CALL `your_project.your_dataset.r_ausd_vertrag_control_sp`(
          'TEST_JOB_W_NULL',
          'A5_NULL',
          '01012023',
          NULL -- Explicitly pass NULL
        );
        ```
    2.  Call `r_ausd_vertrag_control_sp` providing `p_wiederanlauf_wert` as `0`.
        ```sql
        CALL `your_project.your_dataset.r_ausd_vertrag_control_sp`(
          'TEST_JOB_W_ZERO',
          'A5_ZERO',
          '01012023',
          0 -- Explicitly pass 0
        );
        ```
    3.  Query `job_tracking_table` for both entries (if `p_wiederanlauf_wert` were stored, which it isn't in the current `job_tracking_table` DDL).
*   **Pass/Fail Criterion:**
    *   **Pass (as per current code):** Both calls execute successfully. The `job_tracking_table` entries are created. Since `p_wiederanlauf_wert` is not used in `d_ausd_geschaeftspartner_proc` nor stored in `job_tracking_table`, its value (NULL or 0) does not directly impact the observable output of the current migration.
    *   **Fail (if legacy parity is strict):** If any *future* or *unseen* downstream logic within `d_ausd_geschaeftspartner_proc` (or other parts of the system that might consume this parameter) expects `0` when `NULL` is passed, this would represent a behavioral deviation from the legacy script's explicit `p_wiederanlaufWert=0` initialization.
    *   **Recommendation:** To ensure strict behavioral equivalence as per the design document ("Original ksh initialized to 0 if empty."), the `r_ausd_vertrag_control_sp` procedure should be modified to explicitly handle `NULL` for `p_wiederanlauf_wert`. Add the following line at the beginning of the procedure:
        ```sql
        SET p_wiederanlauf_wert = IFNULL(p_wiederanlauf_wert, 0);
        ```
        If this change is implemented, the test should then verify that passing `NULL` results in `0` being used internally.
