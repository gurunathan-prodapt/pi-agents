# Test Suite: DW.DWH_RECHNUNG_EXPORT_TAEGLICH_JS Validation

## 1. Output Parity & Format Verification

### Purpose
To verify that the migrated pipeline produces a pipe-separated flat file (`.dat`) on Google Cloud Storage (GCS) that is structurally and textually identical to the legacy output generated by SQL*Plus spooling. This ensures downstream parsers do not break.

### Setup
1. Populate the legacy Oracle source table `DWH_KERN.T_RECHNUNG` and the BigQuery source table `dw_source.tb_rechnungen` with identical test records for a specific date (`2023-11-20`).
2. Include edge cases in the data:
   * Numeric values with varying decimal places (e.g., `123`, `45.6`, `78.90`, `0.00`).
   * Nullable fields containing `NULL` values (e.g., `TARIF` or `ABRECHNUNGSZEITRAUM` as `NULL`).
   * Special characters in text fields (e.g., German umlauts `ä, ö, ü, ß`).

### Action
1. Execute the legacy shell script:
   ```bash
   ./r_exp_rechnung_taeglich.ksh -s 20231120
   ```
2. Execute the migrated Airflow DAG with the manual configuration override:
   ```json
   {"stichtag": "2023-11-20"}
   ```
3. Download the legacy output file `rechnung_export_20231120.dat` and the migrated GCS output file `gs://<GCS_BUCKET>/rechnung_export_20231120.dat`.
4. Run a comparison script to check line-by-line formatting, field delimiters, trailing newlines, and character encoding.

### Pass/Fail Criterion
* **Pass:** 
  * The files are identical byte-for-byte (or match exactly after converting character encodings if migrating from `ISO-8859-15` to `UTF-8`).
  * No headers are present in either file.
  * The field delimiter is strictly `|`.
  * Decimal values are rounded to exactly 2 decimal places (e.g., `100` becomes `100.00` or `100` depending on the exact SQL*Plus formatting; BigQuery `NUMERIC` cast to 2 decimal places must match the legacy output format).
* **Fail:** Any mismatch in row count, column order, delimiter presence, trailing spaces, or decimal precision.

```python
# pytest test_output_parity.py
import subprocess
import pytest
from google.cloud import storage

def test_file_parity_and_encoding():
    # Download migrated file from GCS
    storage_client = storage.Client()
    bucket = storage_client.bucket("test-gcs-bucket")
    blob = bucket.blob("rechnung_export_20231120.dat")
    migrated_content = blob.download_as_text(encoding="utf-8")

    # Read legacy file (assuming copied to local test runner)
    with open("legacy_rechnung_export_20231120.dat", "r", encoding="iso-8859-15") as f:
        legacy_content = f.read()

    # Normalize line endings and compare
    legacy_lines = [line.strip() for line in legacy_content.strip().split("\n")]
    migrated_lines = [line.strip() for line in migrated_content.strip().split("\n")]

    assert len(legacy_lines) == len(migrated_lines), "Row count mismatch!"
    
    for idx, (legacy_line, migrated_line) in enumerate(zip(legacy_lines, migrated_lines)):
        # If legacy used ISO-8859-15, decode/encode to match UTF-8 string representation
        assert legacy_line == migrated_line, f"Mismatch at line {idx + 1}:\nLegacy: {legacy_line}\nMigrated: {migrated_line}"
```

## 2. Transformation & Type-Handling Correctness

### Purpose
To verify that the Dataform SQLX model correctly handles data types, rounding logic, sorting, and partition filtering in BigQuery, matching the legacy Oracle SQL logic.

### Setup
1. Populate `dw_source.tb_rechnungen` with a diverse set of test cases:
   * **Rounding Case:** `RECHNUNGSBETRAG` values: `10.456`, `10.454`, `10.455`, `0.001`.
   * **Sorting Case:** Out-of-order `RECHNUNGSNUMMER` values (e.g., insert `REC003`, then `REC001`, then `REC002`).
   * **Partition/Filter Case:** Records with `RECHNUNGSDATUM` set to `2023-11-20`, `2023-11-19`, and `2023-11-21`.

### Action
Run a validation query directly in BigQuery against the compiled staging table `dw_staging.tmp_export_rechnung_taeglich` after running the Dataform compilation for `stichtag = '2023-11-20'`.

### Pass/Fail Criterion
* **Pass:**
  * Only records with `rechnungs_datum = '2023-11-20'` are present in the target table.
  * `brutto_betrag` values are rounded using half-up rounding to 2 decimal places:
    * `10.456` $\rightarrow$ `10.46`
    * `10.454` $\rightarrow$ `10.45`
    * `10.455` $\rightarrow$ `10.46`
  * The output is strictly ordered by `rechnungs_id` ascending.
* **Fail:** Any record from another date is present, rounding is incorrect, or the ordering is violated.

```sql
-- BigQuery Validation Assertions
-- 1. Assert Partition Filtering
ASSERT (
  SELECT COUNT(1) 
  FROM `dw_staging.tmp_export_rechnung_taeglich` 
  WHERE rechnungs_datum != DATE('2023-11-20')
) = 0 
AS "ERROR: Partition filter failed! Found records outside of target stichtag.";

-- 2. Assert Rounding Logic
ASSERT (
  SELECT brutto_betrag 
  FROM `dw_staging.tmp_export_rechnung_taeglich` 
  WHERE rechnungs_id = 'REC_ROUND_TEST_1' -- original value 10.456
) = 10.46 
AS "ERROR: Rounding logic failed for 10.456";

-- 3. Assert Strict Ordering
ASSERT (
  SELECT logical_and(is_ordered) FROM (
    SELECT 
      rechnungs_id,
      rechnungs_id >= LAG(rechnungs_id) OVER (ORDER BY rechnungs_id) as is_ordered
    FROM `dw_staging.tmp_export_rechnung_taeglich`
  )
) = true 
AS "ERROR: Output is not strictly ordered by rechnungs_id";
```

## 3. Date Parameter Fallback & Resolution Logic

### Purpose
To verify that the date parameter resolution (`resolve_stichtag`) behaves identically to the legacy shell script fallback logic when no explicit date parameter is provided.

### Setup
1. Mock the system current date to a fixed value (e.g., `2023-11-20 12:00:00 UTC`).
2. Prepare two execution contexts:
   * **Context A:** Manual trigger with a custom JSON payload `{"stichtag": "2023-11-15"}`.
   * **Context B:** Scheduled run (no configuration payload).

### Action
Execute the `resolve_stichtag` Python function under both contexts and capture the returned string.

### Pass/Fail Criterion
* **Pass:**
  * **Context A** returns exactly `"2023-11-15"`.
  * **Context B** returns exactly `"2023-11-19"` (T-1 relative to the mocked system date `2023-11-20`).
* **Fail:** Any other date format or value is returned.

```python
# pytest test_date_utils.py
from datetime import datetime
from unittest.mock import patch
from dags.modules.date_utils import resolve_stichtag

def test_resolve_stichtag_with_manual_conf():
    conf = {"stichtag": "2023-11-15"}
    result = resolve_stichtag(conf)
    assert result == "2023-11-15"

def test_resolve_stichtag_default_fallback():
    # Mock datetime.utcnow to return 2023-11-20
    mocked_now = datetime(2023, 11, 20, 12, 0, 0)
    with patch('dags.modules.date_utils.datetime') as mock_datetime:
        mock_datetime.utcnow.return_return_value = mocked_now
        mock_datetime.strftime = datetime.strftime
        
        # Call with no configuration (scheduled run)
        result = resolve_stichtag(None)
        assert result == "2023-11-19"
```

    * `Export Rechnungsdaten ohne erkennbare Fehler beendet`

    * `Rechnungsexport fuer Stichtag 2023-11-20 angestossen`
    * `Starte Export Rechnungsdaten fuer Stichtag 2023-11-20`

import sys

from dags.modules import logger as custom_logger
