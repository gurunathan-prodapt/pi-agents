# MIGRATION_NOTES.md

**Job Name:** `DW.DWH_RECHNUNG_EXPORT_TAEGLICH_JS`  
**Source Platform:** UC4 Scheduler + KSH Shell Script + Oracle SQL*Plus  
**Target Platform:** Google Cloud Platform (Cloud Composer / Apache Airflow + BigQuery + Google Cloud Storage)  

---

## 1. Summary

The `DW.DWH_RECHNUNG_EXPORT_TAEGLICH_JS` job has been migrated from a legacy on-premises environment to Google Cloud Platform (GCP). 

* **Legacy Architecture:** A UC4 orchestration wrapper triggered a KornShell script (`r_exp_rechnung_taeglich.ksh`), which executed an Oracle SQL query (`d_exp_rechnung_taeglich.sql`) via SQL*Plus. This script extracted daily billing data from the `T_RECHNUNG` table, formatted it as a pipe-separated flat file, validated the output row count, and wrote the file to a local directory (`/rechnung/ausgang/`).
* **Target Architecture:** The job is now fully orchestrated by a native Apache Airflow DAG running in **Cloud Composer**. The data extraction, formatting, and export are performed directly within **BigQuery** using high-performance `EXPORT DATA` statements. The output is written to **Google Cloud Storage (GCS)**, where a Python-based helper task validates the export and consolidates sharded files into a single, clean output file.

---

## 2. Generated Artifacts

The migration process generated the following files, organized within the Airflow deployment structure:

* ### `dags/dwh_rechnung/dwh_rechnung_export_taeglich.py`
  The primary Airflow DAG file. It replaces the UC4 XML job definition and orchestrates the execution flow. It handles parameter injection (such as the dynamic `Stichtag` date), triggers the BigQuery export job, and coordinates logging and post-processing.
* ### `dags/dwh_rechnung/sql/d_exp_rechnung_taeglich.sql`
  The migrated SQL extraction query. The legacy Oracle SQL syntax has been converted to BigQuery Standard SQL. It uses dynamic parameter bindings (`@p_Stichtag`) and references environment-specific project and dataset variables.
* ### `dags/dwh_rechnung/bin/dwh_rechnung_export_taeglich_bin.py`
  A Python module containing auxiliary helper logic. This replaces the operational shell-script logic (`r_exp_rechnung_taeglich.ksh`). It handles GCS file operations, merges sharded CSV files generated by BigQuery into a single consolidated `.dat` file, counts the exported records, and raises warnings if zero rows are processed.

## 3. Key Design Decisions

* ### Push-Down Export Architecture (BigQuery `EXPORT DATA`)
  * **Decision:** Instead of pulling data from BigQuery into an intermediate container or Dataproc cluster to write a flat file, we utilize BigQuery's native `EXPORT DATA` statement.
  * **Rationale:** This offloads the compute-intensive formatting and writing operations to BigQuery's serverless engine, maximizing throughput and reducing runtime costs.
* ### GCS Shard Consolidation Helper
  * **Decision:** BigQuery's `EXPORT DATA` natively writes sharded files (e.g., `rechnung_export_*.csv`) to optimize write performance. To satisfy legacy downstream requirements for a single, un-sharded file, we implemented a GCS "compose" operation in `dwh_rechnung_export_taeglich_bin.py`.
  * **Trade-off:** This introduces a lightweight post-processing step in Python, but it avoids the overhead of running a Spark/Dataproc cluster while guaranteeing a single, ordered output file.
* ### Dynamic Environment Substitution
  * **Decision:** The SQL file contains placeholders (`@gcp_project` and `@bq_dataset`) that are dynamically replaced at runtime by the Airflow DAG.
  * **Rationale:** This ensures strict separation of code and configuration, allowing the exact same SQL file to run unmodified across Development, Test, and Production environments.
* ### Preservation of Legacy Logging and Date Semantics
  * **Decision:** The Airflow DAG uses `{{ ds_nodash }}` (format: `YYYYMMDD`) to match the legacy `&EXPORT_STICHTAG` / `p_Stichtag` parameter. Additionally, the German log output format (`"Rechnungsexport fuer Stichtag {stichtag} angestossen"`) has been preserved to maintain compatibility with legacy log-scraping and monitoring tools.

## 4. Manual Steps Before Go-Live

Before enabling and running this DAG in production, the following manual setup steps must be completed:

### 4.1 Schema & Dataset Creation
Ensure that the target BigQuery dataset and table exist in the target environment:
* **Dataset:** `DWH_KERN` (or the environment-specific equivalent configured in Airflow variables).
* **Table:** `T_RECHNUNG` must be fully migrated, partitioned, and populated.

### 4.2 IAM & Permissions
The Cloud Composer / Airflow worker Service Account must be granted the following IAM roles:
* **BigQuery:** `roles/bigquery.jobUser` and `roles/bigquery.dataViewer` on the dataset containing `T_RECHNUNG`.
* **Google Cloud Storage:** `roles/storage.objectAdmin` on the bucket configured for exports.

### 4.3 Airflow Variables & Connections
Configure the following Airflow Variables in the Cloud Composer environment (via Airflow UI -> Admin -> Variables):
* `GCP_PROJECT`: The GCP Project ID (e.g., `gcp-dwh-prod`).
* `GCS_EXPORT_BUCKET`: The target GCS bucket name (e.g., `dwh-export-prod-reporting`).
* `BQ_DATASET`: The target BigQuery dataset name (defaults to `DWH_KERN` if not set).

### 4.4 Scheduling & Upstream Wiring
* **Legacy Trigger:** This job was triggered as part of the parent job plan `DW.DWH_RECHNUNG_EXPORT_TAEGLICH_JP`.
* **Airflow Trigger:** The DAG is currently configured to run daily at `06:00 AM` (`0 6 * * *`). If this DAG must wait for an upstream table load to complete, configure an `ExternalTaskSensor` or update the parent DAG to trigger this DAG using a `TriggerDagRunOperator`.

## 5. Known Gaps & Unresolved References

* ### Redesign (B4) Items: Downstream File Consumption
  * **Gap:** The legacy system wrote files directly to a local directory (`/rechnung/ausgang/`). The migrated job writes files to a GCS bucket (`gs://<GCS_EXPORT_BUCKET>/rechnung/ausgang/`).
  * **Action Required:** Downstream systems that previously read from the local Unix directory must be updated to pull the exported `.dat` files directly from GCS (e.g., using `gsutil`, GCS client libraries, or Storage Transfer Service).
* ### Source SQL Verification
  * **Gap:** The original `d_exp_rechnung_taeglich.sql` file was flagged as `SOURCE: NOT FOUND` in some legacy code repositories.
  * **Action Required:** Verify that the schema and columns selected in `dags/dwh_rechnung/sql/d_exp_rechnung_taeglich.sql` match the exact column order and business logic expected by downstream consumers.

## 6. Validation

To validate the migrated job, perform the following steps:

### 6.1 Local/Development Dry-Run
1. Trigger the DAG manually in the Airflow UI with a specific execution date (e.g., `2026-01-01`).
2. Verify that the task `print_status` prints the expected German log message:
   ```
   Rechnungsexport fuer Stichtag 20260101 angestossen
   ```

### 6.2 BigQuery Execution Validation
1. Verify that the `execute_export_query` task completes successfully.
2. Check the BigQuery Job History in the GCP Console to confirm that the query compiled correctly and that the `EXPORT DATA` statement executed without errors.

### 6.3 Output File & Row Count Verification
1. Verify that the `consolidate_files` task completes successfully.
2. Check the target GCS bucket path: `gs://<GCS_EXPORT_BUCKET>/rechnung/ausgang/rechnung_export_20260101.dat`.
3. Confirm that:
   * The file is **not** sharded (it must be a single `.dat` file).
   * The fields are separated by the pipe character (`|`).
   * The file contains the correct number of rows matching the source table count for that date.
   * If 0 rows were exported, verify that the task logs a warning: `[WARNING] Export file ... contains 0 rows!`.

## 7. Rollback Procedure

In the event of a critical failure or data mismatch on the target platform, follow these steps to roll back:

1. **Pause the Airflow DAG:**
   Go to the Airflow UI and toggle the switch for `dw_dwh_rechnung_export_taeglich_js` to **Off** to prevent future scheduled runs.
2. **Re-enable Legacy UC4 Job:**
   In the UC4 interface, locate the job `DW.DWH_RECHNUNG_EXPORT_TAEGLICH_JS` (or its parent Job Plan `DW.DWH_RECHNUNG_EXPORT_TAEGLICH_JP`) and set its status back to **Active**.
3. **Verify Legacy Execution:**
   Trigger a manual run in UC4 for the failed business date and verify that the flat file is successfully generated in the legacy directory `/rechnung/ausgang/`.
4. **Post-Mortem Investigation:**
   Examine the Airflow task logs and GCS bucket state to diagnose the failure (e.g., permission errors, network timeouts, or SQL syntax mismatches) before attempting a redeployment.
