# GRAPH OVERVIEW
The overall purpose of the `tmp1weojk4_` graph is to process, validate, and categorize incoming contract and billing positions data (ingested from a flat-file source). The graph performs temporal validation by joining the billing positions with contract master data (`dwh$ta_c_vertrag`) using date-validity intervals. Ultimately, the graph deletes preexisting target records to prevent duplicates and writes the validated, categorized records into several destination fact and temporary tables (`DWH$TA_F_RPOS_CARM`, `DWH$TA_F_RPOS_FACT_CARM`, etc.), while updating control and logging tables with processing statistics.

The graph performs temporal validation by joining the billing positions with contract master data (`dwh$ta_c_vertrag`) using date-validity intervals. ## 3. ADAPTING REVERSED DESIGN TO BIGQUERY TARGET METADATA

To deploy this process successfully on the Google Cloud Platform (GCP) target architecture, all Oracle physical logic, tables, SQL variables, and file streams map to native BigQuery (BQ) datasets and standard SQL structures.

### 3.1 BigQuery Schema Physical Alignments
The Oracle schemas map directly into corresponding standard BigQuery datasets. Column data types map as follows:
* `VARCHAR2` / `CHAR` $\rightarrow$ `STRING`
* `DATE` / `DATETIME` $\rightarrow$ `TIMESTAMP` or `DATE` depending on time component requirements.
* `NUMBER` / `DECIMAL` $\rightarrow$ `NUMERIC` or `INT64`

### 3.2 SQL Idempotency Adaptations
BigQuery does not support standard low-latency transactional individual deletes natively in an optimized fashion. Thus, the deletion steps are combined into dynamic DML executions using standard BigQuery SQL statements running inside Cloud Composer Python operations.
