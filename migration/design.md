This document synthesizes two partial migration design documents for the `finaltestingrepo` ETL pipeline, aiming to provide a single, coherent, and comprehensive migration strategy to Google Cloud Platform (GCP) with Google BigQuery as the primary data warehouse.

---

## Data Migration Design Document: `finaltestingrepo` to Google BigQuery

**Migration Job:** `finaltestingrepo`
**Target Platform:** Google BigQuery
**Scope:** Enterprise-wide ETL pipeline covering Customer, Finance, and Retail (Sales) domains.
**Date:** 2024-01-23
**Version:** 1.0 (Synthesized)

---

### 1. Introduction

This document outlines the migration design for the `finaltestingrepo` enterprise ETL pipeline from its legacy Oracle-based and diverse ecosystem (including Ab Initio, Spark, Python, PL/SQL, SQL*Plus, KornShell) to Google Cloud Platform (GCP). The primary objective is to modernize the data platform, improve scalability, reduce operational overhead, and leverage GCP's managed services for data processing, storage, and orchestration.

The `finaltestingrepo` pipeline is a complex, multi-domain system responsible for critical business functions such as customer scoring and segmentation, financial GL reconciliation and reporting, and retail sales analytics. It relies on data from various internal Oracle sources (CRMDB, SOURCE_CRM, RETAILDW, FINANCE_SCHEMA, SOURCE_FIN, SOURCE_OPS) and exhibits significant cross-domain dependencies.

### 2. Current State Analysis

The `finaltestingrepo` ETL pipeline utilizes a highly diverse and complex technology stack:

*   **Databases:** Oracle 19c (CRMDB, SOURCE_CRM, RETAILDW/DW_OWNER, FINANCE_SCHEMA, SOURCE_FIN, SOURCE_OPS). These databases serve as both source systems and the target data warehouse.
*   **ETL Tools:**
    *   **Ab Initio:** Extensive use of graphs (`.mp`, `.xfr`, `.pdl`) for large-scale data transformation, joining, rollup, and parallel processing across Customer, Finance, and Retail domains (e.g., `crm_customer_scoring.mp`, `gl_period_close.mp`, `retail_daily_sales.mp`).
    *   **Oracle PL/SQL:** Numerous packages (`pkg_*.sql`) for SCD Type 2 dimension loading, fact loading, aggregations, and complex dynamic SQL (`EXECUTE IMMEDIATE`, `DBMS_SQL`, runtime table resolution) within Finance and Retail domains.
    *   **SQL*Plus:** Scripts (`.sql`) for data extraction into staging tables, invoking PL/SQL packages, and basic DML operations (e.g., `customer_segment_extract.sql`, `gl_period_extract.sql`, `sales_extract.sql`).
    *   **Python:** Scripts (`.py`) for dynamic SQL scoring (`customer_scoring.py`), metadata/lineage tracking (`crm_lineage_tracker.py`), and advanced data quality checks (`retail_data_quality.py`).
    *   **Scala Spark:** Jobs (`.scala`) for advanced segmentation (`customer_segmentation.scala`), account hierarchy processing (`account_processor.scala`), and sales aggregation (`sales_aggregation.scala`).
    *   **PySpark:** Jobs (`.py`) for GL aggregation (`gl_aggregation.py`).
*   **Orchestration:** Automic (UC4) workflows (`.xml`, `.json`) define job dependencies, schedules, variables, and cross-domain event publishing/consumption (e.g., `crm_weekly_workflow.xml`).
*   **Scripting/Utilities:** KornShell (`.ksh`) scripts orchestrate SQL*Plus, Spark, and Python scripts, handling parameter passing, logging, and basic retry/event handling (e.g., `process_customer_data.ksh`, `retry_handler.ksh`).
*   **Configuration:** `conf/env_retail.properties` for environment-specific parameters.

**Key Components & Dependencies:**
*   **Data Sources:** `SOURCE_CRM`, `SOURCE_FIN`, `SOURCE_OPS`, `RETAILDW`, `FINANCE_SCHEMA`, `CRM_SCHEMA`.
*   **Core Processes:**
    *   Customer scoring, segmentation, and campaign performance analysis.
    *   General Ledger (GL) transaction processing, period closing, account hierarchy, and reconciliation.
    *   Retail daily sales processing, product master management, and regional sales summaries.
    *   SCD Type 2 dimension management for `DIM_CUSTOMER_CRM`, `DIM_ACCOUNT`, `DIM_PRODUCT`, etc.
    *   Dynamic SQL generation for scoring and data quality rules.
    *   Lineage tracking and audit.
*   **Cross-Pipeline Dependencies:** Explicit waits for `FINANCE_GL_CLOSE_COMPLETE` and `RETAIL_DAILY_COMPLETE` events, indicating tight coupling between domains. Data is shared via cross-schema access (e.g., CRM accessing Sales and Finance data).

### 3. Target State Architecture (GCP)

The target architecture on GCP will leverage a suite of managed services to provide a scalable, resilient, and cost-effective data platform:

*   **Data Warehouse:** Google BigQuery (primary data store for all dimensions, facts, and aggregated data).
*   **Data Lake (Staging/Landing):** Google Cloud Storage (GCS) (for raw data ingestion, intermediate files, and error logs).
*   **ETL/Transformation:**
    *   **BigQuery SQL:** For direct SQL translations, simpler transformations, aggregations, and SCD Type 2 `MERGE` operations.
    *   **Dataproc (Spark/PySpark/Scala Spark):** For complex transformations, Ab Initio graph translations, existing Spark jobs, and large-scale data processing.
    *   **Cloud Data Fusion / Dataflow:** For initial Oracle data ingestion and potentially for highly complex Ab Initio graph patterns if Spark translation proves difficult.
    *   **Python (Cloud Functions/Cloud Run/Composer):** For dynamic SQL generation, orchestration logic, and custom data processing tasks.
*   **Orchestration:** Cloud Composer (Apache Airflow) (replaces UC4 and KornShell scripts).
*   **Configuration/Secrets Management:** Cloud Composer Variables, Google Secret Manager.
*   **Metadata Management:** BigQuery (for ETL audit, DQ rules, dynamic configuration tables), potentially Google Data Catalog for automated lineage.
*   **Monitoring/Alerting:** Cloud Monitoring, Cloud Logging, integrated with Cloud Composer.
*   **Source Data Ingestion:** Cloud Data Fusion, custom Python scripts, or Database Migration Service (DMS) for Oracle data transfer.

### 4. Target Schema Design (BigQuery DDL)

All Oracle tables will be migrated to BigQuery. The schema will largely retain the existing table and column names for consistency, with BigQuery-specific optimizations.

**4.1. Naming Conventions**
*   **Project**: `your-gcp-project-id`
*   **Datasets**:
    *   `stg_customer`: Customer domain staging tables.
    *   `dw_customer`: Customer domain dimensions and facts.
    *   `stg_finance`: Finance domain staging tables.
    *   `dw_finance`: Finance domain dimensions and facts.
    *   `stg_retail`: Retail domain staging tables.
    *   `dw_retail`: Retail domain dimensions and facts.
    *   `audit_etl`: ETL audit, data quality rules, and configuration tables.
*   **Tables**: `dataset_name.table_name` (e.g., `dw_finance.fact_gl_balances`).

**4.2. Data Type Mapping (Oracle to BigQuery)**

| Oracle Type          | BigQuery Type      | Notes                                                              |
| :------------------- | :----------------- | :----------------------------------------------------------------- |
| `NUMBER(P,S)`        | `NUMERIC`/`BIGNUMERIC` | `NUMERIC` for precision up to 38, `BIGNUMERIC` for higher. `FLOAT64` for less precise numbers. |
| `VARCHAR2(L)`        | `STRING`           |                                                                    |
| `CHAR(L)`            | `STRING`           |                                                                    |
| `DATE`               | `DATE`             | For date-only values.                                              |
| `TIMESTAMP`          | `TIMESTAMP`        | For date and time with precision.                                  |
| `CLOB`               | `STRING`           |                                                                    |
| `BLOB`               | `BYTES`            |                                                                    |

**4.3. Key Management (Sequences)**

BigQuery does not have native sequences. Surrogate keys will be handled as follows:
*   **Primary Keys**: For new records, `GENERATE_UUID()` can be used, or `ROW_NUMBER()` over a unique set of natural keys during initial load. For existing records, the Oracle surrogate key will be retained.
*   **Version Numbers (SCD Type 2)**: `ROW_NUMBER()` analytic function will be used to assign `VERSION_NUM` during `MERGE` operations.
*   **Batch IDs**: `FARM_FINGERPRINT()` or a simple `UNIX_MILLIS()` timestamp can generate unique batch IDs, or a dedicated metadata table can manage a sequence.

**4.4. Partitioning and Clustering Strategy**

*   **Partitioning**: All large fact tables and frequently queried dimension tables will be partitioned by a date column (e.g., `TRANSACTION_DATE`, `LOAD_DATE`, `VALID_FROM`). This significantly improves query performance and reduces costs.
*   **Clustering**: Tables will be clustered on frequently used join keys or filter columns to optimize query performance.

**4.5. Shared Data and Access Control**

Oracle cross-schema grants will be translated to BigQuery dataset-level access controls. For example, `stg_finance.STG_PERIOD_RATES` will have read access granted to `dw_retail` and `dw_customer` service accounts.

### 5. Transformation Logic Migration

The transformation logic will be rewritten using BigQuery SQL, Python, and Spark (PySpark/Scala Spark) on Dataproc.

**5.1. Oracle PL/SQL Packages (`pkg_*.sql`)**
*   **SCD Type 2 Logic (`LOAD_DIM_CUSTOMER_CRM`, `LOAD_DIM_ACCOUNT`, `LOAD_DIM_COST_CENTRE`, `LOAD_DIM_PRODUCT`, `LOAD_DIM_CUSTOMER`):** These procedures will be rewritten using **BigQuery `MERGE` statements**. This allows for efficient upsert and SCD Type 2 logic (updating `VALID_TO`, `IS_CURRENT` for changed records, and inserting new versions). Oracle-specific functions (`NVL`, `SYSDATE`) will be replaced with BigQuery equivalents (`COALESCE`, `CURRENT_DATE()`/`CURRENT_TIMESTAMP()`).
*   **Dynamic SQL (`EXECUTE IMMEDIATE`, `DBMS_SQL`) (`BUILD_PERIOD_BALANCES`, `RECONCILE_SUBLEDGER`, `APPLY_CATEGORY_RULES`, `BULK_ENRICH_PRODUCTS`, `PURGE_EXPIRED_VERSIONS`):** Procedures with high dynamic SQL complexity will be rewritten in **Python**. Python scripts will read metadata (e.g., `GL_SUBLEDGER_CONFIG`, `DQ_RULES`) from BigQuery configuration tables, dynamically construct BigQuery-compliant SQL queries, and execute them using the `google-cloud-bigquery` client library.
*   **Loops (`LOAD_DIM_PERIOD`, `REBUILD_CUMULATIVE_BALANCES`):** Iterative logic will be translated to BigQuery stored procedures (if simple) or Python scripts that generate and execute BigQuery DML statements.
*   **Aggregations (`AGGREGATE_CAMPAIGN_PERFORMANCE`, `GENERATE_REGIONAL_SUMMARY`):** These `MERGE` and `INSERT` statements will be translated directly to **BigQuery SQL `MERGE` or `INSERT` statements**.
*   **Orchestration Procedures (`MASTER_CRM_LOAD`, `MASTER_LOAD`):** These will be replaced by Cloud Composer DAGs.

**5.2. SQL*Plus Scripts (`*.sql`)**
*   The SQL queries within `gl_period_extract.sql`, `sales_extract.sql`, `customer_segment_extract.sql` will be translated to **BigQuery SQL**.
*   The surrounding shell logic (parameter passing, logging, error handling) will be absorbed into **Python operators** within Cloud Composer DAGs. `INSERT /*+ APPEND */` will be replaced by standard BigQuery `INSERT` or batch loading mechanisms.

**5.3. Ab Initio Graphs (`.mp`, `.xfr`, `.pdl`)**
*   All Ab Initio graphs (`crm_customer_scoring.mp`, `gl_period_close.mp`, `gl_reconcile.pdl`, `gl_transform.xfr`, `retail_daily_sales.mp`, `sales_rollup.xfr`) will be migrated to **Spark jobs (PySpark or Scala Spark)** running on **Dataproc**.
*   **Component Mapping:**
    *   `input_table`/`read_oracle`: Spark DataFrame `read.format("bigquery")`.
    *   `reformat`: Spark `select` with `withColumn` for transformations.
    *   `filter_by_expression`/`filter`: Spark `filter` or `where`.
    *   `join`: Spark `join` (e.g., `left_outer` maps to `left_outer`).
    *   `rollup`: Spark `groupBy` with `agg` for aggregations.
    *   `output_table`/`write_oracle`: Spark DataFrame `write.format("bigquery")`.
*   **DML Translation:** Ab Initio DML expressions (e.g., `NVL`, `CASE`, `ABS`, date functions) have direct equivalents in Spark SQL or DataFrame API.

**5.4. Spark Jobs (Scala/PySpark)**
*   Existing Scala Spark (`account_processor.scala`, `sales_aggregation.scala`, `customer_segmentation.scala`) and PySpark (`gl_aggregation.py`, `retail_data_quality.py`) jobs will be migrated to **Dataproc** with minimal changes.
*   **JDBC Connections:** Oracle JDBC connections will be replaced by the **Spark BigQuery connector** for reading from and writing to BigQuery.
*   **Dynamic SQL (in `retail_data_quality.py`):** The Python code that dynamically constructs SQL queries will be updated to generate **BigQuery SQL** syntax.

**5.5. KornShell Scripts (`.ksh`)**
*   All KornShell scripts (`process_customer_data.ksh`, `run_account_load.ksh`, `run_gl_close.ksh`, `load_daily_sales.ksh`, `load_product_master.ksh`, `retry_handler.ksh`) will be rewritten in **Python** and orchestrated by **Cloud Composer**.
*   **Orchestration Logic:** Parameter parsing, logging, conditional execution, and error handling will be implemented in Python.
*   **External Command Execution:** Calls to `sqlplus`, `spark-submit`, etc., will be replaced by BigQuery operators/client library calls, DataprocSubmitJobOperator, or Python operators.
*   **`retry_handler.ksh`:** The retry logic will be handled by Airflow's native retry mechanisms or Python's `tenacity` library. Event waiting will use Airflow `ExternalTaskSensor` or custom BigQuery table sensors. Job auditing will be implemented as a Python function writing to `audit_etl.etl_job_audit`.

### 6. Data Flow & Orchestration

The end-to-end data flow will be managed by Cloud Composer (Apache Airflow), orchestrating tasks across Cloud Storage, Dataproc, and BigQuery.

**6.1. Ingestion Layer (Oracle to GCP)**
*   **Initial Load:** A one-time bulk transfer of historical data from Oracle to BigQuery (or Cloud Storage first) using Cloud Data Fusion, `gsutil cp` (for flat files), or custom Python scripts.
*   **Incremental Load:**
    *   **Oracle Source Systems (`SOURCE_CRM`, `SOURCE_FIN`, `SOURCE_OPS`):**
        *   **Batch Extract:** Python scripts (replacing SQL*Plus extracts) will connect to Oracle, extract data, and upload to Cloud Storage (raw zone) or directly to BigQuery staging tables.
        *   **Change Data Capture (CDC):** For near real-time requirements, consider CDC solutions like Debezium on GKE or Oracle GoldenGate to Cloud Storage.
    *   **Flat Files (e.g., `account_master_*.csv`):** Files will be uploaded to Cloud Storage buckets (e.g., `gs://your-project-id-raw-data/finance/account_master/`).

**6.2. Staging Layer (Cloud Storage & BigQuery)**
*   **Cloud Storage:** Raw ingested data will land here, serving as a data lake.
*   **BigQuery Staging Tables:** Data from Cloud Storage will be loaded into BigQuery staging tables (e.g., `stg_finance.stg_gl_transactions`) using BigQuery batch load jobs or Spark/Dataflow.

**6.3. Transformation Layer (Dataproc & BigQuery)**
*   **Dataproc:** Spark jobs (migrated from Ab Initio, Scala Spark, PySpark) will read from BigQuery staging tables or Cloud Storage, perform transformations, and write results back to BigQuery.
*   **BigQuery SQL:** Used for direct SQL transformations, aggregations, and `MERGE` operations for SCD Type 2.

**6.4. Data Warehouse Layer (BigQuery)**
*   All transformed and aggregated data will reside in BigQuery DW datasets (`dw_customer`, `dw_finance`, `dw_retail`), optimized for analytical queries.

**6.5. Orchestration (Cloud Composer)**
Each UC4 workflow will be translated into a Cloud Composer DAG. Each UC4 job will become an Airflow task (e.g., `BigQueryOperator`, `DataprocSubmitJobOperator`, `PythonOperator`). Dependencies, scheduling, retries, and notifications will be configured natively in Airflow.
