# Migration Design — EXIS_SD_APT_NNA_DATA

## 1. Purpose & Scope
This migration design addresses the `EXIS_SD_APT_NNA_DATA` job, a UC4 (now Automic) UNIX job primarily responsible for exporting telephone system master data. The original job creates a compressed CSV file and distributes it to a designated target system. The objective of this migration is to re-platform this job onto Google Cloud Platform (GCP), utilizing Airflow for orchestration and Google Cloud Storage (GCS) for file storage and staging. Any data processing logic will be re-implemented using PySpark executed on Dataproc.

**`DW.DWH_EXIS_SD_APT_NNA_DATA`**

## 1. Purpose & Scope
This document outlines the migration design for the `DW.DWH_EXIS_SD_APT_NNA_DATA` job, a component of the legacy UC4 (now Automic) workload. The primary function of this job is to export telephone system master data. It generates a compressed CSV file (`DWHM_APT_NNA_Daten_<yyyymmddhhmmss>.csv.gz`) and then distributes this file to a target system.

The scope of this migration is to re-platform this specific UC4 UNIX job from its current on-premise execution environment to Google Cloud Platform (GCP). The target architecture will leverage Cloud Composer (for Airflow orchestration), Dataproc (for executing data processing logic as PySpark jobs), and Google Cloud Storage (GCS) for file storage and staging.

The migrated solution will operate within Google Cloud Platform (GCP), utilizing managed services for robustness and scalability.

-   **Orchestration:** Cloud Composer (managed Airflow) will be the primary scheduler and orchestrator. It will manage the execution of the data export process.
-   **Data Processing:** Dataproc will provide ephemeral clusters for executing PySpark jobs. This is the recommended platform for re-implementing the custom executable logic (`r_exis_v2`).
-   **File Storage:** Google Cloud Storage (GCS) will serve as the landing zone for exported data (`DWHM_APT_NNA_Daten_...csv.gz`) and as a repository for PySpark scripts and configuration files.
-   **Security & Identity:** IAM service accounts will manage permissions, and Secret Manager will securely store any sensitive credentials (e.g., for connecting to external source systems).
-   **Logging & Monitoring:** Cloud Logging and Cloud Monitoring will be integrated with Airflow and Dataproc for centralized observability.

The core UC4 job will be transformed into an Airflow DAG named `dw_dwh_exis_sd_apt_nna_data`.

## 4. Data Flow & Lineage
The original UC4 job's data flow involves executing a shell script that, in turn, calls a custom executable (`r_exis_v2`). This executable, guided by a configuration file (`h_exis_apt_nna_daten.var`), extracts and processes telephone system master data, eventually producing a gzipped CSV output file. A month identifier (`&MONAT_ID`) is dynamically generated and passed as a parameter.

In the target GCP architecture, this process will be reimagined as follows:

1.  **Airflow DAG Trigger:** The `dw_dwh_exis_sd_apt_nna_data` Airflow DAG is triggered based on its defined schedule (or manually).
2.  **Dataproc Job Submission:** The DAG's primary task, `dwh_exis_sd_apt_nna_data` (an Airflow `DataprocSubmitJobOperator`), submits a PySpark job to a Dataproc cluster.
3.  **PySpark Execution:** The PySpark script (`exis_sd_apt_nna_data.py`) runs on the Dataproc cluster:
