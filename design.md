# Design Document: Migration of `k_exis_parallel.ksh` to BigQuery SQL

## 1. Shell Script Analysis

### 1.1 Purpose, Input Parameters, Outputs, and Dependencies
*   **Purpose:** This script (`k_exis_parallel.ksh`) is a generic core utility designed to execute SQL scripts in parallel using multiple subprocesses. It segments the execution across a specified number of threads, captures individual process logs, concatenates the output files produced by each thread, and validates whether any of the parallel steps failed.
*   **Input Parameters:**
    *   `$1` (p_EintragsNr): Entry number for logging/messages.
    *   `$2` (p_JobKennung): Job identifier.
    *   `$3` (p_Skript): Path to the SQL template/script to execute.
    *   `$4` (p_Ausgabe): Output base path/filename for the exported results.
    *   `$5` (p_Anfang): Start timestamp of the processing interval (`YYYYMMDDHH24MISS`).
    *   `$6` (p_Ende): End timestamp of the processing interval (`YYYYMMDDHH24MISS`).
    *   `$7` (p_Debug): Debug switch (binary flag `1` or `0`).
    *   `$8` (p_Anzahl): Total number of parallel processes to run.
    *   `$9` (p_Parameter): Optional additional parameters passed to the SQL script.
*   **Outputs:**
    *   A consolidated export file at the destination designated by `$4`.
    *   Process logs for each parallel execution chunk.
    *   Return code: `0` (Success / `k_FertigOK`) or non-zero database error code (`k_FehlerDB`).
*   **Dependencies:**
    *   Environment initializers: `~/.ccr_init`, `h_alis_sqlplus.ksh`, `h_alis_meldungen.ksh`.
    *   Subprocess calls: `CCRSQL_StarteSkriptSilent`.
    *   Logging utility: `CCRMSG_LogDebug`, `CCRMSG_Logdateiname_Parallel`.
    *   System commands: `cat`, `rm`, `grep`, background operator `&`, and `wait`.

### 1.2 Logic Flow
1.  Initialize local parameters, temporary error tracking files, and counters.
2.  Loop `l_count` from `0` to `p_Anzahl - 1`.
3.  For each iteration, calculate log and output filenames containing the process index (`l_count`).
4.  Spawn a background subshell process executing `CCRSQL_StarteSkriptSilent` with arguments including bounds, total threads (`p_Anzahl`), and current thread index (`l_count`). If the command fails, write `"FEHLER"` to the temporary error tracking file.
5.  Wait for all spawned background subprocesses to finish using `wait`.
6.  Concatenate individual sub-files (`${p_Ausgabe}.*`) into the final consolidated output path (`p_Ausgabe`), then clean up the individual sub-files.
7.  Scan the temporary tracking file for `"FEHLER"`. If found, terminate with an error code; otherwise, exit successfully.

### 1.3 BigQuery Mapping and Feasibility
*   **Parallel execution:** BigQuery inherently parallelizes queries and data exports. Instead of running physical OS-level processes in a loop, we can map the execution parameter `l_count` and total threads `p_Anzahl` into a single query using mathematical partitioning (e.g., modulo routing `MOD(ABS(FARM_FINGERPRINT(routing_column)), p_Anzahl) = l_count`) or native BigQuery features.
*   **Consolidation:** Exporting directly from BigQuery to Cloud Storage (GCS) using `EXPORT DATA` automatically handles parallel file generation and consolidation if desired, or writes partitioned files natively.
*   **Stored Procedure Translation:** The orchestrator loop can be translated into a BigQuery Stored Procedure using procedural scripting (`LOOP`, `WHILE`, Dynamic SQL via `EXECUTE IMMEDIATE`).

## 4. BigQuery SQL Pseudocode (Procedural & Declarative)

```sql
CREATE OR REPLACE PROCEDURE dwh_operations.k_exis_parallel(
  p_EintragsNr STRING,
  p_JobKennung STRING,
  p_Skript STRING,
  p_Ausgabe STRING,
  p_Anfang STRING,
  p_Ende STRING,
  p_Debug INT64,
  p_Anzahl INT64,
  p_Parameter STRING
)
BEGIN
  -- Variable Declarations
  DECLARE l_count INT64 DEFAULT 0;
  DECLARE v_Logdatei_Par STRING;
  DECLARE v_DateiPar STRING;
  DECLARE v_Fehler_Count INT64 DEFAULT 0;
  DECLARE v_Sql_Query STRING;
  DECLARE v_Timestamp_Start TIMESTAMP;
  DECLARE v_Timestamp_End TIMESTAMP;

  -- Convert string timestamps "YYYYMMDDHH24MISS" to BigQuery TIMESTAMP format
  SET v_Timestamp_Start = PARSE_TIMESTAMP('%Y%m%d%H%M%S', p_Anfang);
  SET v_Timestamp_End = PARSE_TIMESTAMP('%Y%m%d%H%M%S', p_Ende);

  -- Create a temporary log table to mimic file tracking
  CREATE TEMP TABLE temp_fehler_log (
    thread_id INT64,
    status STRING,
    error_msg STRING
  );

  IF p_Debug = 1 THEN
    INSERT INTO dwh_operations.ccr_logs (eintrags_nr, job_kennung, log_level, message, created_at)
    VALUES (p_EintragsNr, p_JobKennung, 'DEBUG', 'Starting parallel processes loop.', CURRENT_TIMESTAMP());
  END IF;

  -- Iterate through execution slots to execute processing
  WHILE l_count < p_Anzahl DO
    SET v_Logdatei_Par = CONCAT(p_JobKennung, '_', p_EintragsNr, '_thread_', CAST(l_count AS STRING));
    SET v_DateiPar = CONCAT(p_Ausgabe, '_', CAST(l_count AS STRING));

    IF p_Debug = 1 THEN
      INSERT INTO dwh_operations.ccr_logs (eintrags_nr, job_kennung, log_level, message, created_at)
      VALUES (p_EintragsNr, p_JobKennung, 'DEBUG', CONCAT('Starting process ', CAST(l_count AS STRING), ' of ', CAST(p_Anzahl AS STRING)), CURRENT_TIMESTAMP());
    END IF;

    -- Dynamic execution block replicating the core parallel script operation
    BEGIN
      -- Dynamic export of chunked data matching processing logic
      -- Uses FARM_FINGERPRINT modulo to segment table scans dynamically
      SET v_Sql_Query = """
        EXPORT DATA OPTIONS(
          uri='""" || v_DateiPar || """_*.csv',
          format='CSV',
          overwrite=true,
          header=true,
          field_delimiter=';'
        ) AS
        SELECT * 
        FROM `dwh_operations.source_table`
        WHERE processing_timestamp >= @start_time 
          AND processing_timestamp <= @end_time
          AND MOD(ABS(FARM_FINGERPRINT(CAST(routing_id AS STRING))), @total_threads) = @current_thread
      """;

      EXECUTE IMMEDIATE v_Sql_Query
      USING v_Timestamp_Start AS start_time, v_Timestamp_End AS end_time, p_Anzahl AS total_threads, l_count AS current_thread;

    EXCEPTION WHEN ERROR THEN
      -- Log internal errors to the tracking table
      INSERT INTO temp_fehler_log (thread_id, status, error_msg)
      VALUES (l_count, 'FEHLER', @@error.message);
    END;

    SET l_count = l_count + 1;
  END WHILE;

  -- Validate run status
  SELECT COUNT(1) INTO v_Fehler_Count FROM temp_fehler_log WHERE status = 'FEHLER';

  IF p_Debug = 1 THEN
    INSERT INTO dwh_operations.ccr_logs (eintrags_nr, job_kennung, log_level, message, created_at)
    VALUES (p_EintragsNr, p_JobKennung, 'DEBUG', 'All parallel processes completed.', CURRENT_TIMESTAMP());
  END IF;

  -- Cleanup temporary tracking tables
  DROP TABLE temp_fehler_log;

  -- Raise exception or return error status if process chunks failed
  IF v_Fehler_Count > 0 THEN
    ERROR 'Database Error: One or more parallel export threads failed.';
  END IF;

END;
```

In the BigQuery target, a common routing column (like `routing_id` in the pseudocode) must exist to perform the `MOD(ABS(FARM_FINGERPRINT(...)))` thread segmentation. *   **Output Path URI Mapping:** The legacy logic outputs to localized system paths (`p_Ausgabe`). In Cloud environment deployments, `$4` (`p_Ausgabe`) must be mapped to a valid GCS URI (e.g. `gs://your-export-bucket/exports/output_file`).
