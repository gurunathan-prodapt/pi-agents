# Migration Design — vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/k_ausd_v_ta_discount_rr.ksh

## 1. Purpose & Scope
This migration targets an ETL workflow composed of a KornShell script (`k_ausd_v_ta_discount_rr.ksh`) that orchestrates the execution of an Oracle SQL script (`d_ausd_v_ta_discount_rr.sql`). The overall purpose of this job is to prepare discount-related data for reporting by populating a target table, `sof$ta_discount_rr`, from several source `cds$` tables within the Oracle environment. The KornShell script handles job control, parameter parsing, environment setup, and basic error handling, while the SQL script performs the core data extraction and transformation.

The scope of this migration is to re-platform this entire workflow to Google Cloud's BigQuery platform, preserving the business logic and data integrity.

## 2. Source Inventory

*   **File:** `vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/k_ausd_v_ta_discount_rr.ksh`
    *   **Technology:** KornShell
    *   **Complexity Tier:** `medium`
    *   **Automation Bucket:** `semi_auto`
    *   **Summary:** This script acts as an orchestration layer. It reads environment variables, includes several utility scripts for error handling, date functions, parameter parsing, and SQL*Plus execution. It parses command-line parameters (`-j` for `JobKennung` and `-f` for `EintragsNr`), validates them, and then executes the `d_ausd_v_ta_discount_rr.sql` script. It also manages job status (implicitly via `job_kennung`) and captures a record count from a temporary file generated by the SQL execution.
    *   **Key Operations:** Environment sourcing, parameter parsing (`getopts`), parameter validation, error handling (`f_alis_msgerr.ksh`), SQL script invocation (`starteSQLSkript`), temporary file handling (`cat`, `eval`).

*   **File:** `d_ausd_v_ta_discount_rr.sql` (implicitly identified as `SQL_SCRIPT:D_AUSD_V_TA_DISCOUNT_RR.SQL` through lineage analysis)
    *   **Technology:** Oracle SQL (SQL*Plus script)
    *   **Complexity Tier:** (Inferred as `medium` due to multiple joins, date logic, and specific Oracle syntax)
    *   **Automation Bucket:** (Inferred as `semi_auto` to `auto` given the structural nature of SQL transformation)
    *   **Summary:** This SQL script first defines a processing date (`v_datum`) by querying `isbert_schema.dwtk_meldungen`. It applies filtering based on `insert_at`, `modified_at`, `valid_from`, `valid_to` against `v_datum`, and `is_production` flags. It uses Oracle-specific constructs like `DEFINE`, `COLUMN ... NEW_VALUE`, `NVL`, `TO_DATE`, `WHENEVER SQLERROR`, `SPOOL`, `START`, and a call to `isbert_schema.DWPA_UTIL_SKRIPT.runstatement` for table truncation.

## 3. Target Architecture
The target platform is Google Cloud's BigQuery.

*   **Data Landing Zone:** All source Oracle tables (e.g., `isbert_schema.dwtk_meldungen`, `cds$ta_discount_bc_assoc`, `cds$ta_discount`, `cds$ta_care_description`, `cds$ta_disc_vector`, `cds$ta_disc_invoice_item`) will be ingested into BigQuery, likely into a `raw` or `staging` dataset, preserving their original schemas and data types as much as possible.
*   **Target Data Warehouse:** The `sof$ta_discount_rr` table will be created as a managed BigQuery table, ideally in a `curated` or `reporting` dataset. The name will be BigQuery compliant, e.g., `sof_ta_discount_rr`.
*   **Orchestration & Control:** The KornShell script's orchestration logic will be migrated into a BigQuery Stored Procedure, named `control_ausd_v_ta_discount_rr` (or similar). This stored procedure will handle parameter input, validation, job state management, and invocation of the core data transformation logic.
*   **Transformation Logic:** The Oracle SQL transformation logic from `d_ausd_v_ta_discount_rr.sql` will be directly translated into BigQuery SQL. This translated SQL will either be embedded within the `control_ausd_v_ta_discount_rr` stored procedure or encapsulated in a separate BigQuery script or another stored procedure invoked by the main control procedure.
*   **Job Metadata/Logging:** Dedicated BigQuery tables, such as `project.dataset.job_table` and `project.dataset.job_error_log`, will be used to track job execution, status, and log any errors or messages.
*   **External Scheduling:** If the original job was part of a larger scheduling system (e.g., UC4 invoking `r_ausd_v_ta_discount_rr.ksh`), a Cloud Composer (Apache Airflow) DAG or Cloud Workflows might be used to trigger the BigQuery stored procedure.

## 4. Data Flow & Lineage
The migration will maintain a clear data flow:

1.  **Trigger:** An external scheduler (e.g., Cloud Composer) invokes the main BigQuery control stored procedure, passing necessary job parameters (`p_JobKennung`, `p_EintragsNr`).
2.  **Control Procedure (`control_ausd_v_ta_discount_rr`):**
    *   **Initialization:** Validates input parameters.
    *   **Job Status Update:** Records the start of the job in `project.dataset.job_table` and deactivates any previously active instances for the same job.
    *   **Date Determination:** Queries the BigQuery `raw_isbert.dwtk_meldungen` table to determine the `v_datum` (processing date), using `FORMAT_DATE` and `IFNULL` for date handling.
    *   **Pre-processing (Truncation):** Executes a `TRUNCATE TABLE` command on the target `sof_ta_discount_rr` table.
    *   **Data Transformation:** Executes the core BigQuery SQL logic (derived from `d_ausd_v_ta_discount_rr.sql`). This logic performs the following:
        *   Reads from BigQuery tables: `raw_isbert.cds_ta_discount_bc_assoc`, `raw_isbert.cds_ta_discount`, `raw_isbert.cds_ta_care_description`, `raw_isbert.cds_ta_disc_vector`, `raw_isbert.cds_ta_disc_invoice_item`, and `raw_isbert.dwtk_meldungen`.
        *   Joins these tables based on matching IDs (`discount_id`, `cds_description_id`, `disc_invoice_item_id`, `obj_version`).
        *   Applies filters using the `v_datum` for `insert_at`, `modified_at`, `valid_from`, `valid_to` columns, and `is_production = 1`.
        *   Selects specific columns: `cntrct_id`, `discount_id`, `disc_vector_ty`, `cntrct_obj_version`, `cntrct_template_id`, `disc_invoice_item_id`, `cds_description` (aliased as `rabatt`), `calc_rule_value` (aliased as `rabatthoehe`), and `cds_description` (aliased as `rabattierte_rech_pos`).
        *   Inserts the results into the `curated_rpt.sof_ta_discount_rr` table.
    *   **Record Count:** Performs a `COUNT(*)` on the `curated_rpt.sof_ta_discount_rr` table to get the number of processed records.
    *   **Job Finalization:** Updates the `project.dataset.job_table` with the record count and marks the job as completed.
    *   **Error Logging:** If any errors occur, they are logged to `project.dataset.job_error_log`.

## 5. Transformation Logic

### a. `k_ausd_v_ta_discount_rr.ksh` (Orchestration) to BigQuery Stored Procedure
The shell script's orchestration will be transformed into a BigQuery Stored Procedure, e.g., `control_ausd_v_ta_discount_rr(p_JobKennung STRING, p_EintragsNr STRING)`.

*   **Parameter Handling:** `getopts` logic will be replaced by direct input parameters to the stored procedure.
*   **Environment Sourcing:** The sourcing of `.dw_init` and utility scripts (`f_alis_msgerr.ksh`, `h_alis_date.ksh`, `h_alis_parameter.ksh`, `h_alis_sqlplus.ksh`) will be replaced by BigQuery's built-in functions, variables, and procedural logic within the stored procedure.
*   **Parameter Validation:** `pruefeParameterGesetzt` will be translated into `IF` statements and `ASSERT` or `RAISE` in BigQuery SQL for error handling.
*   **Error Handling (`DWMSG_MeldeFehler`):** Custom error logging to `project.dataset.job_error_log` will replace this.
*   **SQL Script Invocation (`starteSQLSkript`):** The execution of `d_ausd_v_ta_discount_rr.sql` will be integrated directly as BigQuery SQL within the stored procedure or as a call to another BigQuery stored procedure.
*   **Temporary File (`tmpFile`) for Record Count:** This is eliminated. The `v_records` will be populated by a `SELECT COUNT(*)` directly on the target BigQuery table (`sof_ta_discount_rr`) after the insert operation, using `DECLARE` and `SET` statements.
*   **Job Table Management:** `INSERT` and `UPDATE` statements will be used against `project.dataset.job_table` to manage job state and record counts.

### b. `d_ausd_v_ta_discount_rr.sql` (Data Transformation) to BigQuery SQL
The core SQL logic will be translated to BigQuery SQL:

*   **Variable Definition (`DEFINE v_carmen`, `COLUMN s_datum new_value v_datum noprint`):**
    *   The `DEFINE v_carmen` (DB Link) will be removed; tables will be fully qualified with their BigQuery project and dataset names (e.g., ``project.dataset.table_name``).
    *   The `v_datum` determination will be done using `DECLARE v_datum STRING; SET v_datum = (SELECT IFNULL(FORMAT_DATE('%Y%m%d', MAX(DATE(m.timecreated))), '19000101') FROM `raw_isbert.dwtk_meldungen` m WHERE m.job_kennung = 'BERT_DROP_TEMP_TABLE');`.
*   **Tracing and Settings (`START ../trace.sql.cfg`, `SPOOL`, `SET TIMING ON`, `SET SERVEROUTPUT ON`, `WHENEVER SQLERROR`):** These SQL*Plus specific commands will be removed. Logging and error handling will be handled by the BigQuery Stored Procedure and Cloud Logging.
*   **Table Truncation (`isbert_schema.DWPA_UTIL_SKRIPT.runstatement(0, 'TRUNCATE TABLE sof$ta_discount_rr');`):** This will be directly translated to `TRUNCATE TABLE `curated_rpt.sof_ta_discount_rr`;` within the BigQuery stored procedure, potentially using `EXECUTE IMMEDIATE` if dynamic table names are required.
*   **`INSERT INTO ... SELECT` Statement:**
    *   Oracle `NVL` will become BigQuery `IFNULL`.
    *   Oracle `TO_CHAR(MAX(...), 'YYYYMMDD')` will become `FORMAT_DATE('%Y%m%d', MAX(DATE(...)))`.
    *   Oracle `TO_DATE('&v_datum', 'YYYYMMDD')` will become `PARSE_DATE('%Y%m%d', v_datum)`.
    *   Oracle join syntax (`FROM table1 a, table2 b WHERE a.id = b.id`) will be converted to explicit `JOIN` clauses (`FROM table1 a JOIN table2 b ON a.id = b.id`).
    *   Oracle `/*+ parallel(da,4) ... */` hints will be removed as BigQuery handles query parallelism automatically.
    *   Table names will be fully qualified using backticks (e.g., ``raw_isbert.cds_ta_discount``).
*   **Transaction Management (`commit;`):** Explicit `COMMIT` is not needed in BigQuery SQL for single statements; for multiple statements within a stored procedure, BigQuery transaction control (e.g., `BEGIN TRANSACTION`, `COMMIT TRANSACTION`) can be used if atomicity across multiple operations is strictly required.

## 6. External Dependencies

*   **Oracle Database Link (`&v_carmen`):** This will be resolved by migrating the referenced `cds$` tables (`cds$ta_discount_bc_assoc`, `cds$ta_discount`, `cds$ta_care_description`, `cds$ta_disc_vector`, `cds$ta_disc_invoice_item`) to BigQuery. The BigQuery stored procedure will directly query these migrated tables.
*   **Oracle Package (`isbert_schema.DWPA_UTIL_SKRIPT`):** Specifically, the `runstatement` function used for `TRUNCATE TABLE`. The `TRUNCATE TABLE` action will be directly implemented in BigQuery SQL. Any other complex logic within this package would require analysis and reimplementation as BigQuery UDFs or stored procedures.
*   **Temporary File System (`$DW_DIR_UTL/bert_k_ausd_v_ta_discount_rr_$$.tmp`):** The mechanism of writing to and reading from a temporary file for record counts will be replaced by direct variable assignment within the BigQuery stored procedure using `DECLARE` and `SET`.
*   **Unix Utilities/Environment (`.dw_init`, `getopts`, `print`, `cat`, `eval`):** These shell-specific functionalities will be replaced by BigQuery stored procedure parameters, control flow statements (e.g., `IF`, `CASE`), and built-in functions.
*   **`TABLE:ZWISCHEN` (READS) and `TABLE:VIA` (WRITES):** These tables appeared in the lineage graph but not in the provided SQL code. Further investigation is required to determine their purpose and whether they are temporary tables, views, or external dependencies, and how they should be handled in BigQuery. If they are temporary, BigQuery temporary tables or CTEs will be used.

## 7. Unresolved / Risks

*   **Missing Table Definitions:** The precise DDL for all source Oracle tables (`cds$ta_discount_bc_assoc`, `cds$ta_discount`, `cds$ta_care_description`, `cds$ta_disc_vector`, `cds$ta_disc_invoice_item`, `isbert_schema.dwtk_meldungen`) and the target `sof$ta_discount_rr` was not available. This is crucial for accurate BigQuery schema definition and data type mapping.
*   **Unclear `ZWISCHEN` and `VIA` Table Usage:** The lineage indicated `READS` from `ZWISCHEN` and `WRITES` to `VIA` for `d_ausd_v_ta_discount_rr.sql`, but these tables were not found in the SQL code. Their role needs clarification to ensure no data loss or incorrect processing during migration.
*   **Full Scope of `isbert_schema.DWPA_UTIL_SKRIPT`:** Only the `TRUNCATE TABLE` usage was clear. If this Oracle package performs other critical or complex operations, they need to be fully understood and re-implemented in BigQuery.
*   **Complex `f_alis_msgerr.ksh` Logic:** The error reporting and handling within `f_alis_msgerr.ksh` may have intricate logic beyond simple logging. A detailed understanding is needed to replicate equivalent error management in BigQuery and potentially integrate with Cloud Logging or other monitoring tools.
*   **External Orchestration (`r_ausd_v_ta_discount_rr.ksh`):** The relationship where `r_ausd_v_ta_discount_rr.ksh` invokes the current job implies a higher-level orchestration. This parent job would also need to be migrated or adapted to call the new BigQuery workflow.
