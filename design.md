# Migration Design — vobs/dw_source/isrpt/isbert/install_save/k_ausd_bp_ta_tarifoption.ksh

## 1. Purpose & Scope
This document outlines the migration plan for the KornShell script `k_ausd_bp_ta_tarifoption.ksh` to Google BigQuery.

The original script serves as a control script for a data processing job. Its primary purpose is to:
- Initialize the environment by sourcing various shell libraries.
- Parse command-line parameters (`p_JobKennung`, `p_EintragsNr`, `p_Stichtag`, `p_wiederanlaufWert`).
- Validate the presence of required parameters.
- Validate the format of the `p_Stichtag` parameter (DDMMYYYY).
- Orchestrate the execution of a core SQL script, `d_ausd_bp_ta_tarifoption.sql`, which processes data related to the business entity 'PoolBasisprodukt'.
- Retrieve a record count from a temporary file generated by the SQL execution.
- Optionally log job-related information (currently commented out).
- Handle error conditions by reporting via `DWMSG_MeldeFehler` and exiting with appropriate error codes.

The scope of this migration is to re-implement the orchestration logic and the underlying data transformations in a BigQuery-native environment, leveraging BigQuery SQL stored procedures and related GCP services.

## 3. Target Architecture
The migrated solution will primarily reside within Google BigQuery, leveraging its capabilities for data processing and orchestration.

- **BigQuery Stored Procedure:** The main orchestration logic of `k_ausd_bp_ta_tarifoption.ksh` will be converted into a BigQuery SQL stored procedure. This procedure will accept parameters, perform validations, and execute the core transformation logic.
  - **Name:** `project.dataset.r_ausd_bp_ta_tarifoption` (or similar, following BigQuery naming conventions).
- **Core Transformation Logic:** The SQL logic originally in `d_ausd_bp_ta_tarifoption.sql` will be refactored and implemented directly within the BigQuery stored procedure or as separate BigQuery SQL scripts/views called by the stored procedure.
- **Control/Audit Table:** A BigQuery table, e.g., `project.dataset.job_log`, will be created to store job execution logs, error messages, and record counts, replacing the shell script's `tmpFile` and commented-out job logging.
- **Data Tables:** The `PoolBasisprodukt` table and any other source/target tables will be migrated to BigQuery.
- **Orchestration:** The BigQuery stored procedure will be invoked by a scheduling mechanism like Cloud Composer (Airflow DAG) or Cloud Workflows, replacing the original `ksh` script's role as the job entry point. Cloud Scheduler can trigger these orchestrators.

## 5. Transformation Logic
The transformation logic from `k_ausd_bp_ta_tarifoption.ksh` is primarily orchestration, with the actual data transformations delegated to `d_ausd_bp_ta_tarifoption.sql`.

**Orchestration Logic Transformation:**
- **Parameter Parsing:** `getopts` functionality will be replaced by direct input parameters to the BigQuery stored procedure.
- **Variable Assignments:** Shell variable assignments (`v_TabName`, `p_datum_heute`, `p_datum_gestern`) will be replaced by `DECLARE` and `SET` statements in BigQuery SQL.
- **Conditional Logic:** `if/then/else` and `case` statements will be translated to BigQuery SQL's `IF ... THEN ... END IF` constructs.
- **Date Derivation:** The call to `gestern.ksh` will be replaced by BigQuery's `CURRENT_DATE()` and `DATE_SUB(CURRENT_DATE(), INTERVAL 1 DAY)`.
- **Date Validation:** `DWDate_Datum_Check` will be replaced by `SAFE.PARSE_DATE('%d%m%Y', p_Stichtag)` and checking for `NULL` results.
- **Error Handling:** `DWMSG_MeldeFehler` and `exit` calls will be replaced by `INSERT` statements into a `job_log` table and `LEAVE` statements to exit the stored procedure.
- **Temporary File (`tmpFile`) for Record Count:** This will be replaced by directly capturing the `COUNT(*)` from the transformation result and storing it in a BigQuery variable or inserting it into the `job_log` table.

**Data Transformation Logic (from `d_ausd_bp_ta_tarifoption.sql`):**
- The content of `d_ausd_bp_ta_tarifoption.sql` (not directly available in this step but referenced) will need to be fully converted to BigQuery SQL. This will involve:
  - Replacing Oracle-specific SQL syntax (if any) with BigQuery equivalents.
  - Ensuring table and column references are mapped to their BigQuery counterparts.
  - Any procedural SQL (PL/SQL) within `d_ausd_bp_ta_tarifoption.sql` will be integrated into the BigQuery stored procedure or separate BigQuery functions.

**Commented Post-processing Logic:**
The commented-out `sed`, `sort`, and `join` commands indicate potential file-based transformations. If these were ever active or represent latent requirements, they would be translated to BigQuery SQL operations:
- `sed s/\\ //g`: `REGEXP_REPLACE(column_name, ' ', '')`
- `sort -u`: `SELECT DISTINCT ... ORDER BY`
- `join`: BigQuery `JOIN` operations.
