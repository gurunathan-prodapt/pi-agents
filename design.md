# Migration Design — vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/k_ausd_v_ta_vvl_dwh.ksh

## 1. Purpose & Scope
This migration design document outlines the re-platforming of the `k_ausd_v_ta_vvl_dwh.ksh` ETL job from its legacy KornShell environment to Google BigQuery.

The primary purpose of `k_ausd_v_ta_vvl_dwh.ksh` is to serve as a control script. It is invoked by `r_ausd_v_ta_vvl_dwh.ksh` and its main responsibilities include:
-   Parsing command-line parameters for job identification (`p_JobKennung`) and entry number (`p_EintragsNr`).
-   Performing basic parameter validation and error handling.
-   Executing a core SQL script, `d_ausd_v_ta_vvl_dwh.sql`, which contains the actual data processing logic.
-   Registering job status and deactivating old active jobs (handled implicitly by the `starteSQLSkript` function and the SQL script).
-   Capturing the count of processed records from a temporary file generated by the SQL execution.

The job is classified as having "medium" complexity according to the initial assembly.

## 2. Source Inventory
The job consists of one primary source file:

**File:** `vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/k_ausd_v_ta_vvl_dwh.ksh`
-   **Technology:** KornShell Script
-   **Complexity Tier:** Undefined (based on available metadata, but the script is a wrapper, suggesting the complexity resides in the invoked SQL)
-   **Automation Bucket:** `semi_auto`
-   **Description:** This script acts as a wrapper. It sources several utility shell scripts for environment initialization, error handling, date utilities, parameter parsing, and SQL*Plus routines. It then parses `JobKennung` and `EintragsNr` parameters, performs validation, and executes an external SQL script (`d_ausd_v_ta_vvl_dwh.sql`) using a `starteSQLSkript` function. It captures the record count from a temporary file after the SQL execution.

The script indirectly depends on:
-   `d_ausd_v_ta_vvl_dwh.sql`: This SQL script is executed by `k_ausd_v_ta_vvl_dwh.ksh`. It reads from `TABLE:DWTK_MELDUNGEN` and `TABLE:DWH$TA_F_VVL_EREIGNISSE`, and writes to `TABLE:SOF$TA_VVL_DWH` and `TABLE:VIA`. It also uses `PACKAGE:DWPA_UTIL_SKRIPT`.
-   Various internal utility KornShell scripts (`f_alis_msgerr.ksh`, `h_alis_date.ksh`, `h_alis_parameter.ksh`, `h_alis_sqlplus.ksh`).

## 3. Target Architecture
The migrated solution will leverage Google BigQuery's capabilities, primarily using:
-   **BigQuery Stored Procedures:** To encapsulate the orchestration logic previously handled by the KornShell script and the data transformation logic from the SQL script.
-   **BigQuery Tables:** To replace source and target tables, including `DWTK_MELDUNGEN`, `DWH$TA_F_VVL_EREIGNISSE`, `SOF$TA_VVL_DWH`, and `VIA`.
-   **BigQuery Logging/Monitoring Tables:** To replace the shell script's error logging and job tracking mechanisms.
-   **Cloud Composer (Airflow) / Cloud Workflows / Dataform:** For external orchestration, if needed, to manage parameter passing, job scheduling, and dependency handling between migrated components.

## 4. Data Flow & Lineage
The original data flow is as follows:
1.  **Invocation:** The parent script `vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/r_ausd_v_ta_vvl_dwh.ksh` INVOKES `vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/k_ausd_v_ta_vvl_dwh.ksh`.
2.  **Orchestration & Parameter Handling:** `k_ausd_v_ta_vvl_dwh.ksh` prepares the environment and parses parameters (`p_JobKennung`, `p_EintragsNr`).
3.  **SQL Execution:** `k_ausd_v_ta_vvl_dwh.ksh` EXECUTES the SQL script `vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/sql/d_ausd_v_ta_vvl_dwh.sql`.
4.  **Data Transformation (within SQL):**
    -   `d_ausd_v_ta_vvl_dwh.sql` READS data from `TABLE:DWTK_MELDUNGEN` and `TABLE:DWH$TA_F_VVL_EREIGNISSE`.
    -   `d_ausd_v_ta_vvl_dwh.sql` WRITES transformed data to `TABLE:SOF$TA_VVL_DWH` and `TABLE:VIA`.
    -   `d_ausd_v_ta_vvl_dwh.sql` USES `PACKAGE:DWPA_UTIL_SKRIPT`.
5.  **Record Count & Logging:** `k_ausd_v_ta_vvl_dwh.ksh` retrieves the processed record count from a temporary file (implicitly written by the SQL execution framework) and performs final logging/status updates.

In the target BigQuery environment:
-   The parent invocation from `r_ausd_v_ta_vvl_dwh.ksh` will be replaced by an external orchestrator (e.g., Cloud Composer DAG) that calls the main BigQuery stored procedure.
-   A main BigQuery stored procedure (e.g., `project.dataset.r_ausd_vertrag_control`) will handle parameter validation, job registration, and invocation of the data transformation stored procedure.
-   A data transformation BigQuery stored procedure (e.g., `project.dataset.d_ausd_v_ta_vvl_dwh_proc`) will replace the `d_ausd_v_ta_vvl_dwh.sql` logic, performing reads from source BigQuery tables and writes to target BigQuery tables.
-   Job tracking and error logging will be managed by inserting records into dedicated BigQuery logging tables.

## 5. Transformation Logic

**Shell Script (`k_ausd_v_ta_vvl_dwh.ksh`) to BigQuery Stored Procedure:**

The shell script's functionalities will be translated as follows:
-   **Environment Initialization (`. $HOME/.dw_init`):** These settings will be managed through BigQuery procedure parameters, dataset/project constants, or configuration tables.
-   **Utility Scripts:** The logic within `f_alis_msgerr.ksh`, `h_alis_date.ksh`, `h_alis_parameter.ksh`, and `h_alis_sqlplus.ksh` will be re-implemented as BigQuery UDFs or separate BigQuery stored procedures, or their functionality will be absorbed directly into the main procedure if simple.
-   **Parameter Parsing (`getopts`):** Replaced by direct BigQuery stored procedure input parameters (`IN p_JobKennung STRING`, `IN p_EintragsNr STRING`).
-   **Parameter Validation:** `IF/ELSEIF` statements in BigQuery SQL with `RAISE USING MESSAGE` or inserts into an error log table.
-   **Job Registration/Deactivation:** Implemented as `UPDATE` or `INSERT` statements against a BigQuery job tracking table within the stored procedure, potentially through a separate helper stored procedure (`register_job_start`).
-   **SQL Script Execution (`starteSQLSkript`):** The logic will be replaced by a `CALL` to the BigQuery stored procedure containing the actual SQL transformation (`d_ausd_v_ta_vvl_dwh_proc`).
-   **Temporary File Record Count (`cat $tmpFile`):** Replaced by a `DECLARE` variable (`v_records INT64`) and `SET` statement within the BigQuery stored procedure, capturing the `ROW_COUNT()` or `COUNT(*)` after the `INSERT`/`UPDATE` operations.
-   **Logging (`print`):** Replaced by `SELECT` statements for immediate output or `INSERT` statements into a BigQuery logging table.

**SQL Script (`d_ausd_v_ta_vvl_dwh.sql`) to BigQuery Stored Procedure:**

The core SQL transformation logic will be lifted and shifted into its own BigQuery stored procedure (e.g., `project.dataset.d_ausd_v_ta_vvl_dwh_proc`).
-   **Source Tables:** `DWTK_MELDUNGEN` and `DWH$TA_F_VVL_EREIGNISSE` will be migrated to corresponding BigQuery tables.
-   **Target Tables:** `SOF$TA_VVL_DWH` and `VIA` will be migrated to corresponding BigQuery tables.
-   **SQL Logic:** The `SELECT`, `INSERT`, `UPDATE`, `DELETE` statements, and any procedural logic within `d_ausd_v_ta_vvl_dwh.sql` will be directly converted to BigQuery Standard SQL.
-   **Package Usage (`DWPA_UTIL_SKRIPT`):** Functions/procedures within this Oracle package will need to be re-implemented as BigQuery UDFs or stored procedures.

## 6. External Dependencies
-   **Legacy Environment Variables and Helper Scripts (`.dw_init`, `f_alis_msgerr.ksh`, `h_alis_date.ksh`, `h_alis_parameter.ksh`, `h_alis_sqlplus.ksh`):** These are internal shell dependencies. Their functionalities will be replaced by BigQuery stored procedure logic, UDFs, or configuration management within the BigQuery environment.
-   **Oracle Database (implicitly where `DWTK_MELDUNGEN`, `DWH$TA_F_VVL_EREIGNISSE`, `SOF$TA_VVL_DWH`, `VIA`, `DWPA_UTIL_SKRIPT` reside):** The legacy database dependencies will be removed. All tables and packages will be migrated to BigQuery. There are no other external systems like SFTP, S3, etc., explicitly identified in the `lineage_assembled_jobs` analysis.

## 7. Unresolved / Risks
-   **Completeness of `d_ausd_v_ta_vvl_dwh.sql`:** The actual content of this SQL script was not directly analyzed by the tool. A detailed analysis and conversion of this SQL script to BigQuery Standard SQL will be a critical next step. The complexity of this SQL will influence the overall effort.
-   **Utility Scripts Re-implementation:** The internal KornShell utility scripts (`f_alis_msgerr.ksh`, `h_alis_date.ksh`, `h_alis_parameter.ksh`, `h_alis_sqlplus.ksh`) need explicit re-implementation details. Their exact functionality and complexity are not fully known from the current analysis.
-   **`DWPA_UTIL_SKRIPT` Package:** The functionality of this Oracle package needs to be fully understood and re-implemented in BigQuery.
-   **Job Tracking Logic:** While the tool inferred job registration/deactivation, the exact logic within the original `starteSQLSkript` and `d_ausd_v_ta_vvl_dwh.sql` might contain specific business rules that need to be carefully translated.
-   **`semi_auto` Migration Bucket:** The `semi_auto` classification suggests that some parts of this migration will require manual intervention or detailed review, particularly concerning the exact business logic within the SQL script and utility functions.
-   **Orchestration for `r_ausd_v_ta_vvl_dwh.ksh`:** The invoking script `r_ausd_v_ta_vvl_dwh.ksh` indicates that this job is part of a larger workflow. The migration of this parent orchestrator is outside the current scope but will be necessary for a complete solution.

## 8. Build Plan
The build plan will focus on creating the necessary BigQuery components:

1.  **Migrate Source and Target Tables (BQSQL):**
    -   Create `project.dataset.DWTK_MELDUNGEN` (BQ Table)
    -   Create `project.dataset.DWH_TA_F_VVL_EREIGNISSE` (BQ Table)
    -   Create `project.dataset.SOF_TA_VVL_DWH` (BQ Table)
    -   Create `project.dataset.VIA` (BQ Table)
    *(Note: Table names will be adjusted to BigQuery naming conventions)*

2.  **Create BigQuery Stored Procedures (BQSQL):**
    -   `project.dataset.d_ausd_v_ta_vvl_dwh_proc`: Contains the core data transformation logic from `d_ausd_v_ta_vvl_dwh.sql`, including the logic for reading from `DWTK_MELDUNGEN` and `DWH$TA_F_VVL_EREIGNISSE`, and writing to `SOF$TA_VVL_DWH` and `VIA`. Re-implementation of `DWPA_UTIL_SKRIPT` functions will be integrated here or as separate UDFs/procedures.
    -   `project.dataset.r_ausd_vertrag_control`: The main orchestration stored procedure, replacing `k_ausd_v_ta_vvl_dwh.ksh`. This procedure will handle parameter validation, job tracking, error logging, and call `d_ausd_v_ta_vvl_dwh_proc`.
    -   Helper procedures/UDFs (e.g., `project.dataset.register_job_start`, error logging procedures) based on the functionality extracted from the sourced shell scripts.

3.  **Implement Logging and Job Tracking (BQSQL):**
    -   Create `project.dataset.job_error_log` (BQ Table)
    -   Create `project.dataset.job_run_log` (BQ Table)
    -   Create `project.dataset.job_table` (BQ Table, if a specific one is used for active job handling)

4.  **External Orchestration (if necessary, e.g., Cloud Composer DAG - Python):**
    -   Develop a Cloud Composer DAG to schedule and invoke `project.dataset.r_ausd_vertrag_control`, passing the required parameters. This will replace the invocation by `r_ausd_v_ta_vvl_dwh.ksh`.
