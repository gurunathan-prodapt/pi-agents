# Migration Design — vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/k_ausd_v_ta_acc_ref.ksh

## 1. Purpose & Scope
This document outlines the migration design for the KornShell script `k_ausd_v_ta_acc_ref.ksh` and its dependent SQL script `d_ausd_v_ta_acc_ref.sql` to Google BigQuery.

The primary purpose of `k_ausd_v_ta_acc_ref.ksh` is to orchestrate the execution of the SQL script `d_ausd_v_ta_acc_ref.sql`. It acts as a control script that:
*   Initializes the environment by sourcing other utility scripts for error handling, date checks, parameter parsing, and SQL*Plus routines.
*   Parses command-line parameters (`p_JobKennung` and `p_EintragsNr`).
*   Validates the presence of required parameters.
*   Sets a table name variable `v_TabName` to `ta_acc_ref`.
*   Executes the core SQL logic encapsulated in `d_ausd_v_ta_acc_ref.sql` via a `starteSQLSkript` function. This execution includes logic to ignore active jobs and register the current job in a job table.
*   Reads the number of records processed from a temporary file generated by the `starteSQLSkript` function.

The SQL script `d_ausd_v_ta_acc_ref.sql` performs the core data transformation:
*   It determines a cut-off date (`v_datum`) by querying the `isbert_schema.dwtk_meldungen` table.
*   It truncates the `sof$ta_acc_ref` table.
*   It inserts data into `sof$ta_acc_ref` by selecting from `cds$ta_acc_ref` (potentially from a linked Oracle database via `v_carmen`) after applying filters based on `insert_at`, `modified_at`, `valid_from`, `valid_to` and `is_production` attributes against the determined `v_datum`.

The overall scope of this migration is to re-implement this job's functionality natively in BigQuery, covering both the orchestration and the data transformation logic.

## 3. Target Architecture
The migrated job will be implemented in Google BigQuery, primarily utilizing BigQuery Stored Procedures for both the orchestration logic (from the KornShell script) and the data transformation logic (from the Oracle SQL script).

*   **Orchestration Layer**: The `k_ausd_v_ta_acc_ref.ksh` script's logic will be translated into a BigQuery Stored Procedure, let's call it `sp_k_ausd_v_ta_acc_ref_control`. This stored procedure will handle parameter validation, job registration/deactivation logic, and invocation of the data transformation logic.
*   **Data Transformation Layer**: The `d_ausd_v_ta_acc_ref.sql` script's logic will be translated into a separate BigQuery Stored Procedure, `sp_d_ausd_v_ta_acc_ref_transform`, or directly inlined within the control procedure if it's a simple, single-step transformation. Given the summary indicates truncating and inserting, a separate procedure or a direct execution within the control procedure is feasible.
*   **Logging and Metadata**: Instead of temporary files and shell-based error handling, dedicated BigQuery tables (e.g., `job_log`, `error_log`, `job_table` for active jobs) will be used to store job execution status, errors, and record counts.
*   **Data Sources**:
    *   `isbert_schema.dwtk_meldungen` will be mapped to a corresponding BigQuery table (e.g., `project.dataset.dwtk_meldungen`).
    *   `cds$ta_acc_ref` will be sourced from a BigQuery equivalent table or a federated query if the source remains external (e.g., via BigQuery Omni or external tables over Cloud Storage if the Oracle data is periodically exported). For this design, we assume `cds$ta_acc_ref` will be available in BigQuery as `project.dataset.cds_ta_acc_ref`.
    *   `sof$ta_acc_ref` will be the target table in BigQuery (e.g., `project.dataset.sof_ta_acc_ref`).

## 4. Data Flow & Lineage

The data flow in the migrated BigQuery environment will be as follows:

1.  **Job Invocation**: The BigQuery stored procedure `sp_k_ausd_v_ta_acc_ref_control` is invoked, potentially by an external orchestrator (e.g., Cloud Composer/Airflow, Dataform, or scheduled BigQuery queries). It receives `p_JobKennung` and `p_EintragsNr` as input parameters.
2.  **Orchestration (Control Procedure)**:
    *   `sp_k_ausd_v_ta_acc_ref_control` performs parameter validation. If validation fails, it logs an error to `error_log` and exits.
    *   It updates a `job_table` to register the current job as active and deactivates any older active jobs for the same table (`ta_acc_ref`).
    *   It calls the data transformation stored procedure `sp_d_ausd_v_ta_acc_ref_transform`.
    *   After the transformation, it queries the `sof_ta_acc_ref` table (or uses the output of the transformation procedure) to get the processed record count.
    *   It logs the job's completion and record count to a `job_log` table.
3.  **Data Transformation (Transformation Procedure)**:
    *   `sp_d_ausd_v_ta_acc_ref_transform` will read from `project.dataset.dwtk_meldungen` to determine the `v_datum` (cut-off date).
    *   It will truncate the `project.dataset.sof_ta_acc_ref` table.
    *   It will then perform an `INSERT INTO ... SELECT FROM` operation, extracting data from `project.dataset.cds_ta_acc_ref`.
    *   The selection criteria will involve filtering based on `insert_at`, `modified_at`, `valid_from`, `valid_to`, and `is_production` columns against the derived `v_datum`.
4.  **Target**: The transformed data is stored in `project.dataset.sof_ta_acc_ref`.

**Original Lineage (Inferred):**
`k_ausd_v_ta_acc_ref.ksh` (invokes) -> `d_ausd_v_ta_acc_ref.sql`

`sp_d_ausd_v_ta_acc_ref_transform` (writes) -> `project.dataset.sof_ta_acc_ref`

## 5. Transformation Logic

**Orchestration Logic (`k_ausd_v_ta_acc_ref.ksh` to `sp_k_ausd_v_ta_acc_ref_control`)**:
*   **Parameter Handling**: The shell script's `getopts` and `pruefeParameterGesetzt` logic will be replaced by direct parameters to the BigQuery stored procedure.
    *   `p_JobKennung` (STRING)
    *   `p_EintragsNr` (STRING)
*   **Environment Sourcing**: The `. $HOME/.dw_init` and other sourced utility scripts will be replaced by:
    *   Hardcoding values (e.g., `v_TabName='ta_acc_ref'`).
    *   Dedicated BigQuery helper procedures or inlined logic (e.g., for error logging, date handling if needed beyond standard SQL functions).
*   **Error Handling**: The `DWMSG_MeldeFehler` and `exit` calls will be replaced by `RAISE` in BigQuery, and errors will be logged to a `project.dataset.error_log` table.
*   **Job Management**: The `starteSQLSkript` function's assumed behavior (job registration, deactivation of old jobs) will be implemented using `INSERT` and `UPDATE` statements on a `project.dataset.job_table`.
*   **Record Count**: The shell's reading from a temporary file (`tmpFile`) and using `eval` will be replaced by a `SELECT COUNT(*)` query on the target table after the transformation, and this count will be logged to `project.dataset.job_log`.

**Data Transformation Logic (`d_ausd_v_ta_acc_ref.sql` to `sp_d_ausd_v_ta_acc_ref_transform`)**:
*   **Date Determination**:
    *   Original: `SELECT NVL(TO_CHAR(MAX(m.timecreated),'YYYYMMDD'),'19000101') FROM isbert_schema.dwtk_meldungen m WHERE m.job_kennung = 'BERT_DROP_TEMP_TABLE';`
    *   Target: Will be translated to BigQuery SQL, e.g., `SELECT IFNULL(FORMAT_DATE('%Y%m%d', MAX(m.timecreated)), '19000101') FROM project.dataset.dwtk_meldungen m WHERE m.job_kennung = 'BERT_DROP_TEMP_TABLE';`
*   **Truncate and Insert**:
    *   Original: `TRUNCATE TABLE sof$ta_acc_ref;` followed by `INSERT INTO sof$ta_acc_ref (...) SELECT ... FROM cds$ta_acc_ref ... WHERE ...`
    *   Target: `TRUNCATE TABLE project.dataset.sof_ta_acc_ref;` or `DELETE FROM project.dataset.sof_ta_acc_ref WHERE 1=1;` for a full truncate equivalent in a transaction. Then, `INSERT INTO project.dataset.sof_ta_acc_ref (acc_ref_id, account_reference) SELECT ar.acc_ref_id, ar.account_reference FROM project.dataset.cds_ta_acc_ref ar WHERE ar.insert_at <= PARSE_DATE('%Y%m%d', v_datum) AND (ar.modified_at IS NULL OR ar.modified_at > PARSE_DATE('%Y%m%d', v_datum)) AND ar.valid_from <= PARSE_DATE('%Y%m%d', v_datum) AND (ar.valid_to IS NULL OR ar.valid_to > PARSE_DATE('%Y%m%d', v_datum)) AND ar.is_production = 1;`
*   **DB Link**: The `&v_carmen` variable in `cds$ta_acc_ref &v_carmen ar` suggests a database link. In BigQuery, this will either mean `cds_ta_acc_ref` is already in BigQuery or accessed via federated queries or an external table, simplifying the `FROM` clause.
*   **Commit**: The `commit;` statement will be implicit in BigQuery transactions or handled by default behavior of DML statements.

## 7. Unresolved / Risks

*   **Job Management Logic in `starteSQLSkript`**: The exact details of the job registration and deactivation logic within the `starteSQLSkript` function are not fully known without its source code. The migration design assumes a standard job status management pattern that will need to be verified and accurately re-implemented in BigQuery using DML statements on a dedicated job metadata table.
*   **`BERT_DIR_ROOT` and `DW_DIR_UTL` resolution**: The exact paths and values of these environment variables are not known. They are assumed to point to relevant directories for scripts and temporary files. In BigQuery, these will be replaced by dataset/table names or storage bucket paths.
*   **Parameter `ParamList`**: The `getopts` parameter list `j:f:` indicates named parameters. The migration to BigQuery stored procedure parameters will directly use named arguments.
*   **Oracle-specific SQL Features**: While the SQL provided is fairly standard, subtle Oracle-specific functions or syntax might exist in the full `d_ausd_v_ta_acc_ref.sql` that need careful conversion to BigQuery SQL equivalents. `TO_CHAR(MAX(m.timecreated),'YYYYMMDD')` and `TO_DATE('&v_datum','YYYYMMDD')` were identified and will be converted to BigQuery's date functions.
*   **Performance of Data Ingestion**: The initial ingestion of `cds$ta_acc_ref` and `dwtk_meldungen` from Oracle to BigQuery needs a robust and performant strategy.
*   **Error Code Semantics**: The original script uses specific error codes (193, 192). If exact error code propagation is critical, a mapping to BigQuery error handling or a custom error logging mechanism will be needed.

## 8. Build Plan

The migration will involve the following steps:

1.  **Create BigQuery Datasets**:
    *   `project.dataset` (if not already existing)
2.  **Create BigQuery Tables for Data Sources**:
    *   `project.dataset.dwtk_meldungen` (schema derived from Oracle source)
    *   `project.dataset.cds_ta_acc_ref` (schema derived from Oracle source)
    *   `project.dataset.sof_ta_acc_ref` (target table schema, to be truncated and populated)
3.  **Create BigQuery Tables for Job Management and Logging**:
    *   `project.dataset.job_table` (for job status, e.g., `job_kennung`, `eintrags_nr`, `tab_name`, `status`, `created_at`, `updated_at`)
    *   `project.dataset.error_log` (for detailed error messages, e.g., `error_code`, `error_message`, `job_kennung`, `eintrags_nr`, `created_at`)
    *   `project.dataset.job_log` (for job execution results, e.g., `job_kennung`, `eintrags_nr`, `tab_name`, `record_count`, `created_at`)
4.  **Develop BigQuery Stored Procedure for Data Transformation**:
    *   **Language**: BigQuery SQL
    *   **Name**: `sp_d_ausd_v_ta_acc_ref_transform` (or similar)
    *   **Content**: Translate the SQL logic from `d_ausd_v_ta_acc_ref.sql` into BigQuery-compatible SQL.
5.  **Develop BigQuery Stored Procedure for Orchestration Logic**:
    *   **Language**: BigQuery SQL
    *   **Name**: `sp_k_ausd_v_ta_acc_ref_control` (or similar)
    *   **Content**: Implement parameter validation, job management (register, deactivate), invocation of `sp_d_ausd_v_ta_acc_ref_transform`, and record count logging as per the pseudocode provided by the CM MCP tool.
6.  **Data Ingestion**: Set up a process to continuously or periodically ingest data from the source Oracle tables (`isbert_schema.dwtk_meldungen`, `cds$ta_acc_ref`) into their respective BigQuery tables.
7.  **Testing**: Thoroughly test both stored procedures with various parameter combinations, including error scenarios, to ensure functional parity and data integrity.
8.  **Scheduling**: Integrate the `sp_k_ausd_v_ta_acc_ref_control` procedure into the target platform's scheduler (e.g., Cloud Composer/Airflow, scheduled queries).
