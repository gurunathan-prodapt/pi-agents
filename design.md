# Migration Design — vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/k_ausd_bp_ta_cntrct_dist.ksh

## 1. Purpose & Scope
This KornShell script, `k_ausd_bp_ta_cntrct_dist.ksh`, serves as a control and orchestration script for a data processing workflow. Its primary purpose is to:
*   Parse and validate input parameters (`Jobkennung`, `EintragsNr`, `Stichtag`, `wiederanlaufWert`).
*   Set up the execution environment by sourcing common utility scripts for error handling, date functions, and parameter parsing.
*   Derive "today" and "yesterday" dates.
*   Invoke a core SQL script, `d_ausd_bp_ta_cntrct_dist.sql`, to perform the main data transformation and loading.
*   Read the count of processed records from a temporary file generated by the SQL process.
*   (Commented out functionality) Potentially update a job tracking table and perform post-processing on data files.

The scope of this migration focuses on translating this KornShell orchestration logic and its dependencies into an equivalent BigQuery-native solution, primarily using BigQuery stored procedures and SQL scripting, with potential external orchestration via Cloud Composer or Dataform.

## 3. Target Architecture
The target architecture will leverage Google Cloud Platform services, primarily BigQuery, for data processing and storage.
*   **Main Logic**: The orchestration logic of the KornShell script will be migrated into a BigQuery stored procedure, tentatively named `project.dataset.sp_k_ausd_bp_ta_cntrct_dist`.
*   **Core SQL Logic**: The invoked SQL script (`d_ausd_bp_ta_cntrct_dist.sql`) will be migrated into a separate BigQuery stored procedure, e.g., `project.dataset.sp_d_ausd_bp_ta_cntrct_dist`.
*   **Data Storage**: All input and output data, as well as intermediate results, will reside in BigQuery tables. This includes a dedicated table for job tracking (`project.dataset.job_tracking_table`) and target result tables (`project.dataset.target_result_table`).
*   **Parameter Management**: Input parameters to the script will be passed as arguments to the BigQuery stored procedure. Environment variables will be replaced by either parameters, configuration tables, or constants within the stored procedure.
*   **Orchestration**: For scheduling and sequential execution, a Cloud Composer (Apache Airflow) DAG or Dataform job can be used to call the main BigQuery stored procedure and manage its dependencies.

## 4. Data Flow & Lineage
The original data flow is controlled by the KornShell script:
1.  **Environment Setup**: Script sources `.dw_init` and utility scripts (`f_alis_msgerr.ksh`, `h_alis_date.ksh`, `h_alis_parameter.ksh`, `h_alis_sqlplus.ksh`).
2.  **Parameter Input**: Command-line parameters `j`, `f`, `s`, `l` are parsed.
3.  **Validation**: Parameters are validated for presence and `Stichtag` for date format.
4.  **Date Derivation**: `gestern.ksh` is executed to get "today" and "yesterday" dates.
5.  **Core Processing**: The `starteSQLSkript` function (from `h_alis_sqlplus.ksh`) is used to execute `d_ausd_bp_ta_cntrct_dist.sql` with various parameters. This SQL script is assumed to read from source tables and write to target/staging tables.
6.  **Record Count**: The script reads `v_records` from `$DW_DIR_UTL/bert_k_ausd_bp_ta_cntrct_dist.tmp`.
7.  **Job Tracking (Commented)**: An `FOSJobErzeugeEintrag` call (commented out) would have updated a job table.
8.  **Post-Processing (Commented)**: A block of `sed`, `sort`, `join` commands (commented out) indicates potential file-based transformations and merging.

**Migrated Data Flow in BigQuery:**
1.  **Stored Procedure Invocation**: The `sp_k_ausd_bp_ta_cntrct_dist` stored procedure is invoked with `p_JobKennung`, `p_EintragsNr`, `p_Stichtag`, and `p_wiederanlaufWert` as parameters.
2.  **Parameter & Date Validation**: Inside the stored procedure, BigQuery SQL scripting (e.g., `IF`, `ASSERT`, `SAFE.PARSE_DATE`, `ERROR()`) will handle parameter validation and date format checks.
3.  **Date Derivation**: `CURRENT_DATE()` and `DATE_SUB()` will be used to derive `v_datum_heute` and `v_datum_gestern`.
4.  **Core Processing Call**: The `sp_d_ausd_bp_ta_cntrct_dist` stored procedure will be `CALL`ed from `sp_k_ausd_bp_ta_cntrct_dist`, passing relevant parameters. `sp_d_ausd_bp_ta_cntrct_dist` will perform the actual data transformations, reading from source BigQuery tables and writing to target BigQuery tables (e.g., `project.dataset.target_result_table`).
5.  **Record Count**: After `sp_d_ausd_bp_ta_cntrct_dist` completes, `sp_k_ausd_bp_ta_cntrct_dist` will execute a `SELECT COUNT(*)` query on `project.dataset.target_result_table` for the given `Stichtag` to get `v_records`.
6.  **Job Tracking**: An `INSERT` statement will be executed against `project.dataset.job_tracking_table` to log the job's status and record count.
7.  **Post-Processing (Optional)**: If the commented-out file processing is required, it will be implemented as a separate BigQuery view or stored procedure, using standard SQL transformations.

## 5. Transformation Logic
The `k_ausd_bp_ta_cntrct_dist.ksh` script primarily provides orchestration and minimal direct data transformation.

**Script's direct transformations:**
*   **Parameter Validation**: Ensures `Jobkennung`, `Stichtag`, `EintragsNr` are provided and `Stichtag` is in `DDMMYYYY` format. This will be converted to `IF/ASSERT` statements and `SAFE.PARSE_DATE` in BigQuery SQL.
*   **Date Calculation**: Calls `gestern.ksh` to determine today's and yesterday's dates. This will be replaced by `CURRENT_DATE()` and `DATE_SUB(CURRENT_DATE(), INTERVAL 1 DAY)` in BigQuery.
*   **Record Count**: Reads from a temporary file. This will be replaced by `SELECT COUNT(*)` on the BigQuery target table.

**Commented-out Post-Processing (potential transformations if activated):**
*   **Blank Character Removal**: `sed s/\\ //g` (e.g., `REGEXP_REPLACE(col, r'\\s+', '')` in BigQuery).
*   **Unique Sort**: `sort -u -k 1 -t ';'` (e.g., `SELECT DISTINCT col1, col2, ... FROM ... QUALIFY ROW_NUMBER() OVER (PARTITION BY col1 ORDER BY 1) = 1` or `GROUP BY` in BigQuery).
*   **File Join**: `join -j1 1 -j2 1 -o 2.1,1.2,2.2 -a 2 -t ';'` (e.g., `FULL OUTER JOIN` or `LEFT JOIN` in BigQuery, using appropriate `ON` conditions and `COALESCE` for output fields).

The substantial data transformation logic is presumed to be within the `d_ausd_bp_ta_cntrct_dist.sql` script, which requires separate analysis for its migration to BigQuery SQL.

## 6. External Dependencies
The original script has several external dependencies:

*   **Environment Initialization**: `. $HOME/.dw_init`
    *   **Replacement**: BigQuery stored procedures do not have a concept of sourcing environment files. Configuration values will either be hardcoded (if static), passed as parameters, or fetched from a BigQuery configuration table.
*   **Utility Scripts**:
    *   `${BERT_DIR_ROOT}/allgemein/is/util/bin/f_alis_msgerr.ksh` (Error handling)
    *   `${BERT_DIR_ROOT}/allgemein/is/util/bin/h_alis_date.ksh` (Date validation)
    *   `${BERT_DIR_ROOT}/allgemein/is/util/bin/h_alis_parameter.ksh` (Parameter validation)
    *   `${BERT_DIR_ROOT}/allgemein/is/util/bin/h_alis_sqlplus.ksh` (SQL execution wrapper, specifically `starteSQLSkript`)
    *   `${BERT_DIR_ROOT}/aufbereitung/bin/gestern.ksh` (Yesterday/Today date calculation)
    *   **Replacement**: The logic from these scripts will be re-implemented directly in BigQuery SQL within the stored procedures. Error handling will use `SELECT ERROR(...)`. Date validation will use `SAFE.PARSE_DATE` and `IF` statements. Parameter validation will use `IF/ASSERT`. `starteSQLSkript` will be replaced by a direct `CALL` to the migrated SQL stored procedure. `gestern.ksh` will be replaced by `CURRENT_DATE()` and `DATE_SUB()`.
*   **Core SQL Script**: `Name_SQLskript="${BERT_DIR_ROOT}/aufbereitung/sql/d_ausd_bp_ta_cntrct_dist.sql"`
    *   **Replacement**: This SQL script will be migrated into its own BigQuery stored procedure, `project.dataset.sp_d_ausd_bp_ta_cntrct_dist`, and invoked directly via `CALL` from the main orchestration procedure.
*   **Temporary File**: `tmpFile="$DW_DIR_UTL/bert_k_ausd_bp_ta_cntrct_dist.tmp"`
    *   **Replacement**: Direct file I/O for record counts will be replaced by `SELECT COUNT(*)` queries on the relevant BigQuery target tables.
*   **Job Tracking System (Commented)**: `FOSJobErzeugeEintrag`
    *   **Replacement**: A dedicated BigQuery job tracking table (`project.dataset.job_tracking_table`) will be created, and `INSERT` statements will be used to log job execution details.
*   **Input Data Files for Post-Processing (Commented)**: `cibasis_data24.dat`, `cibasis_data96.dat`, `cibasis_fax.dat`
    *   **Replacement**: If this logic is reactivated, these files would need to be ingested into BigQuery staging tables (e.g., via Cloud Storage and external tables or batch loads) to enable SQL-based transformations.

## 7. Unresolved / Risks
*   **`starteSQLSkript` Semantics**: The exact functionality of `starteSQLSkript` (within `h_alis_sqlplus.ksh`) needs to be fully understood. If it involves complex logic beyond simple SQL execution (e.g., transaction management, connection pooling, retry logic, error handling specific to SQL*Plus), this complexity must be carefully replicated in the BigQuery migration, potentially requiring Cloud Functions or Cloud Run for specific non-SQL tasks, or enhanced BigQuery stored procedure logic.
*   **Business Logic in SQL Script**: The details of the core business logic within `d_ausd_bp_ta_cntrct_dist.sql` are unknown and are critical for a complete migration. This requires separate analysis and design.
*   **Commented-Out Code Review**: The commented-out `sed`, `sort`, `join` block for file post-processing, and the `FOSJobDeaktivate`/`FOSJobErzeugeEintrag` calls, should be reviewed with stakeholders to confirm if they are truly obsolete or if there's a requirement to reactivate this functionality. If reactivated, the source of the data files (`cibasis_*.dat`) must be identified and a migration plan for them established.
*   **Helper Script Details**: While the general purpose of helper scripts like `f_alis_msgerr.ksh` is inferred, their full implementation (e.g., specific error codes, logging formats) might contain subtle logic that needs accurate replication in BigQuery error handling.
*   **`p_wiederanlaufWert` Usage**: The `p_wiederanlaufWert` parameter is initialized but not used in the provided script. Its intended use case (e.g., for restartability, incremental loads) needs clarification as it might influence the design of the BigQuery stored procedure for robustness.
