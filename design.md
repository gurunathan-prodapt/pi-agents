# Migration Design — vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/r_ausd_bp_ta_msisdn_his.ksh

## 1. Purpose & Scope
This shell script, `r_ausd_bp_ta_msisdn_his.ksh`, serves as a wrapper for the initial provisioning of selected base products for the BERT system. Its primary purpose is to prepare the runtime environment, parse and validate input parameters, initialize logging and error handling, determine the effective cutoff date, and then delegate the core business logic to a kernel script, `k_ausd_bp_ta_msisdn_his.ksh`. This wrapper orchestrates the execution flow and manages operational logging and status reporting, but does not perform direct data transformations itself. The migration scope covers the re-implementation of this wrapper's orchestration, parameter handling, and logging functionalities into Google BigQuery.

## 3. Target Architecture
The migration targets Google BigQuery for job orchestration and data processing. The current KornShell wrapper will be re-implemented as a BigQuery Stored Procedure.

*   **BigQuery Stored Procedure (`project.dataset.ausd_bp_ta_msisdn_his_wrapper`)**: This will encapsulate the parameter parsing, validation, date determination, and job orchestration logic of the original shell script. It will accept `p_stichtag` (cutoff date) and `p_wiederanlaufWert` (restart value) as input parameters.
*   **BigQuery Audit Tables**:
    *   `project.dataset.job_registry`: To track job executions, statuses, and metadata (e.g., `job_name`, `script_name`, `stichtag`, `created_at`, `status`).
    *   `project.dataset.job_message_log`: To store operational messages and success indicators generated by the wrapper script.
    *   `project.dataset.job_error_log`: To capture error details, messages, and timestamps for failed executions.
*   **BigQuery Stored Procedure (`project.dataset.k_ausd_bp_ta_msisdn_his`)**: A placeholder for the core business logic that is currently handled by the `k_ausd_bp_ta_msisdn_his.ksh` script. This stored procedure will be called by the `ausd_bp_ta_msisdn_his_wrapper` and will contain the actual data transformation logic, which will be subject to its own migration design.
*   **Orchestration**: The execution of the `ausd_bp_ta_msisdn_his_wrapper` stored procedure will be managed by a GCP orchestrator such as Cloud Composer (Airflow) or Cloud Workflows, providing scheduling, dependency management, and monitoring.

## 4. Data Flow & Lineage
The original script is a wrapper that orchestrates an ETL process.

**Legacy Flow:**
1.  `r_ausd_bp_ta_msisdn_his.ksh` starts execution.
2.  Environment variables are sourced from `$HOME/.dw_init`.
3.  Error handling, parameter parsing, and date utility scripts are sourced:
    *   `${BERT_DIR_ROOT}/allgemein/is/util/bin/f_alis_msgerr.ksh`
    *   `${BERT_DIR_ROOT}/allgemein/is/util/bin/h_alis_parameter.ksh`
    *   `${BERT_DIR_ROOT}/allgemein/is/util/bin/h_alis_date.ksh`
4.  Command-line parameters (`-s` for Stichtag, `-l` for Wiederanlaufwert) are parsed.
5.  A default Stichtag is determined if not provided (MIN(sysdate, maxladedatum)).
6.  Parameters are validated. If validation fails, an error message is logged, and the script exits.
7.  Job identification and logging metadata are initialized using `DWMSG_` functions.
8.  Traps are set for interrupt and error handling.
9.  The core kernel script, `${BERT_DIR_ROOT}/aufbereitung/bin/k_ausd_bp_ta_msisdn_his.ksh` (resolved as `Name_Kernskript`), is invoked with the parsed parameters and logging information.
10. Upon successful completion of the kernel script, a success message is logged, and the job status is updated.
11. If any error occurs, the `DWMSG_Fehlerbehandlung` trap is activated, logging the error and causing the script to exit with an error code.

**Target BigQuery Flow:**
1.  A Cloud Composer DAG or Cloud Workflow invokes the `project.dataset.ausd_bp_ta_msisdn_his_wrapper` BigQuery Stored Procedure.
2.  The stored procedure initializes variables, including `ProgName`, `ProgVersion`, `JobKennung`.
3.  Input parameters `p_stichtag` and `p_wiederanlaufWert` are handled, with `p_wiederanlaufWert` defaulting to `0` if NULL.
4.  `v_sysdate` is derived using BigQuery's `CURRENT_DATE()` and `FORMAT_DATE()`. `v_stichtag` is set, defaulting to `v_sysdate` if `p_stichtag` is not provided.
5.  Parameters are validated. If `v_stichtag` is NULL or empty, an error is recorded in `project.dataset.job_error_log`, and a `RAISE` statement halts execution.
6.  A new entry is inserted into `project.dataset.job_registry` to record the job's start, and `DW_EintragsNr` is retrieved.
7.  Start messages are logged into `project.dataset.job_message_log`.
8.  The stored procedure `project.dataset.k_ausd_bp_ta_msisdn_his` is invoked, passing `JobKennung`, `v_stichtag`, `DW_EintragsNr`, and `v_wiederanlaufWert`.
9.  Upon successful return from `k_ausd_bp_ta_msisdn_his`, a success message is logged into `project.dataset.job_message_log`, and the job's status in `project.dataset.job_registry` is updated to 'OK'.
10. If an error occurs during the execution of the `ausd_bp_ta_msisdn_his_wrapper` or `k_ausd_bp_ta_msisdn_his`, the `EXCEPTION WHEN ERROR` block is triggered, logging the error in `project.dataset.job_error_log`, updating the job status in `project.dataset.job_registry` to 'ERROR', and re-raising the exception.

## 5. Transformation Logic
The `r_ausd_bp_ta_msisdn_his.ksh` script primarily acts as an orchestrator and does not contain direct data transformation logic. The core business logic is delegated to the `k_ausd_bp_ta_msisdn_his.ksh` script.

The wrapper's logic will be translated as follows:
*   **Parameter Handling**: `getopts` logic will be replaced by BigQuery Stored Procedure input parameters.
*   **Defaulting Logic**: Shell `if [[ -z ... ]]` conditions will be translated to `IFNULL()` or `IF ... THEN ... END IF` constructs in BigQuery SQL.
*   **Date Determination**: Shell commands like `DWDate_Gib_Zeitraum` will be replaced by BigQuery date functions such as `CURRENT_DATE()` and `FORMAT_DATE()`.
*   **Error Handling**: Shell `set -e` and `trap` mechanisms will be replaced by BigQuery's `EXCEPTION WHEN ERROR` blocks, `RAISE` statements, and inserts into dedicated error logging tables.
*   **Logging**: `print` and `tee` commands will be replaced by `INSERT` statements into BigQuery audit tables (`job_message_log`, `job_error_log`, `job_registry`).
*   **Script Invocation**: The shell command `${Name_Kernskript} ...` will be replaced by a `CALL` statement to the `project.dataset.k_ausd_bp_ta_msisdn_his` BigQuery Stored Procedure, passing relevant parameters.

## 6. External Dependencies
The current script relies on several external components:

*   **Environment Initialization (`. $HOME/.dw_init`)**: This dependency implies a system-level environment setup. In BigQuery, this will be handled through:
    *   GCP project and dataset configuration.
    *   Stored Procedure parameters for dynamic values.
    *   Potentially, a BigQuery configuration table for static/global environment variables.
*   **Shell Utility Scripts**:
    *   `f_alis_msgerr.ksh`: Error/message framework.
    *   `h_alis_parameter.ksh`: Parameter parsing helpers.
    *   `h_alis_date.ksh`: Date utility library.
    These will be absorbed into the BigQuery Stored Procedure logic using native BigQuery SQL functions, conditional logic, and the audit logging tables.
*   **Core Kernel Script (`k_ausd_bp_ta_msisdn_his.ksh`)**: This is the most significant dependency, as it contains the actual data processing logic. This script needs to be migrated separately to a BigQuery Stored Procedure or equivalent (e.g., a Dataflow job, or a Python script running on Cloud Run/Cloud Functions if complex transformations are involved) and will be invoked via a `CALL` statement from the `ausd_bp_ta_msisdn_his_wrapper` stored procedure.
*   **Logging Infrastructure (DWMSG_ functions, log files)**: This will be replaced by dedicated BigQuery audit tables (`job_registry`, `job_message_log`, `job_error_log`) for centralized and structured logging.
*   **OS-level functionality (shell traps, `exit`)**: These will be replaced by BigQuery's procedural error handling (`EXCEPTION WHEN ERROR`, `RAISE`) and flow control.

## 7. Unresolved / Risks
*   **Core Business Logic (`k_ausd_bp_ta_msisdn_his.ksh`)**: The most significant unresolved item is the content and migration of the `k_ausd_bp_ta_msisdn_his.ksh` script. This wrapper migration assumes the core logic will be re-implemented as a BigQuery Stored Procedure, but its actual complexity and scope are unknown from this analysis. This dependency must be analyzed and migrated separately.
*   **Dynamic Source/Target Identification**: The `AL?? FOSHoleLadedatum "DWH\$TA_C_VERTRAG" v_ladedatum` comment suggests potential dynamic table referencing. If `k_ausd_bp_ta_msisdn_his.ksh` uses dynamic SQL or dynamically determines source/target tables, this needs careful consideration during its migration.
*   **Shell Traps**: While `EXCEPTION WHEN ERROR` provides robust error handling, the exact behavior of shell traps (e.g., `INT`, `STOP`, `CONT`) might have nuances that need careful mapping to BigQuery's procedural capabilities and orchestrator features.
*   **Date Logic Nuances**: The original script uses `MIN(sysdate,maxladedatum)` for date determination, but the active code uses `p_stichtag=$v_sysdate;`. This discrepancy could indicate an incomplete or changed requirement in the legacy system. The migration will follow the active code's logic.
*   **`BERT_DIR_ROOT` resolution**: The shell script uses environment variables like `BERT_DIR_ROOT`. The BigQuery stored procedure should define these as parameters or retrieve them from a configuration table.
*   **Migration Bucket**: The `semi_auto` migration bucket suggests that some manual intervention and detailed design work will be required beyond pure automated conversion, particularly for the orchestration logic and custom utility functions.
