## 3. Target Architecture

The target architecture will leverage BigQuery's capabilities for both orchestration and data processing.

- **Orchestration**: The shell script's control flow, parameter handling, and validation logic will be migrated to a **BigQuery Stored Procedure**. This stored procedure will accept input parameters and manage the execution of the core data logic. For external job scheduling and triggering, a Cloud Composer (Airflow DAG) or Cloud Workflows might be used to invoke the BigQuery Stored Procedure.
- **Data Processing**: The SQL logic within `d_ausd_bp_ta_p_basisprod.sql` will be directly translated into **BigQuery SQL**. This will either be embedded within the BigQuery Stored Procedure or called as a separate script.
- **Logging and Error Handling**: Dedicated BigQuery tables for `error_log` and `job_log` will replace the shell script's `DWMSG_MeldeFehler` and commented-out FOS job management functions.
- **Temporary Data**: Any temporary files (`tmpFile`) used for intermediate results or record counts will be replaced by temporary BigQuery tables or direct variable assignments within the stored procedure.
- **Environment Variables**: Legacy environment variables (`DW_DIR_UTL`, `BERT_DIR_ROOT`) will be replaced by BigQuery Stored Procedure parameters, session variables, or configuration parameters passed from the orchestration layer.
- **Date Functions**: Shell-based date calculations (e.g., `gestern.ksh`) will be replaced by BigQuery's native date and timestamp functions (e.g., `CURRENT_DATE()`, `DATE_SUB()`).
- **File-based Post-Processing (Commented-out Legacy)**: If the commented-out `sed`, `sort`, `join` logic is ever activated or needs to be replicated, it will be fully re-engineered using BigQuery SQL functions like `REGEXP_REPLACE`, `SELECT DISTINCT`, `ORDER BY`, and `JOIN` operations on staging tables in BigQuery.
