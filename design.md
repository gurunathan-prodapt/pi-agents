# Migration Design — vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/k_ausd_bp_ta_rn_da_vda_tk.ksh

## 1. Purpose & Scope

This job is a Korn Shell (ksh) script (`k_ausd_bp_ta_rn_da_vda_tk.ksh`) that acts as a control and orchestration script for a data processing workflow. Its primary purpose is to:
*   Initialize the execution environment by sourcing common utility scripts.
*   Parse and validate critical runtime parameters, including job identifiers, an entry number, and a processing date (`Stichtag`).
*   Perform date format validation for the `Stichtag`.
*   Orchestrate the execution of a core SQL script (`d_ausd_bp_ta_rn_da_vda_tk.sql`) that performs the actual data processing.
*   Capture the record count generated by the SQL process from a temporary file.
*   Handle error reporting and job exit conditions.

The scope of this migration is to re-implement the orchestration and parameter handling logic of this ksh script into a BigQuery-native solution, while integrating with the migrated core SQL logic.

## 3. Target Architecture

The target architecture for this job will leverage BigQuery's native capabilities for data processing and orchestration:

*   **Core Logic:** The functionality of the `k_ausd_bp_ta_rn_da_vda_tk.ksh` script, including parameter validation, date validation, date derivation, and orchestration, will be migrated into a BigQuery Stored Procedure. This stored procedure will then directly invoke the migrated SQL logic from `d_ausd_bp_ta_rn_da_vda_tk.sql` (which itself would be a separate BigQuery stored procedure or a multi-statement script).
*   **Orchestration:** The BigQuery Stored Procedure will be scheduled and managed using Google Cloud Composer (Apache Airflow), Cloud Workflows, or BigQuery Scheduled Queries. This will replace the shell script's role as a scheduler and orchestrator.
*   **Data Storage:** All data sources, including the `PoolBasisprodukt` table and any intermediate datasets, will reside in BigQuery tables (e.g., `source_project.source_dataset.PoolBasisprodukt`, `project.dataset.target_table`).
*   **Logging and Error Handling:** Custom logging for job runs and errors will be implemented by inserting records into dedicated BigQuery tables (e.g., `project.dataset.job_run_log`, `project.dataset.job_error_log`). Error conditions will utilize BigQuery's `RAISE` statement.
*   **Parameter Management:** Input parameters (`p_JobKennung`, `p_EintragsNr`, `p_Stichtag`, `p_wiederanlaufWert`) will be passed directly as arguments to the BigQuery Stored Procedure.

## 4. Data Flow & Lineage

The data flow and lineage for the migrated job will be as follows:

1.  **Invocation:** An orchestration service (e.g., Cloud Composer) invokes the main BigQuery Stored Procedure (e.g., `project.dataset.r_ausd_bp_ta_rn_da_vda_tk`) with input parameters.
2.  **Parameter and Date Validation:** The BigQuery Stored Procedure first validates the input parameters for presence and performs a `DDMMYYYY` date format check for `p_Stichtag`.
3.  **Date Derivation:** BigQuery date functions (`CURRENT_DATE()`, `DATE_SUB()`) are used to derive `p_datum_heute` and `p_datum_gestern`.
4.  **Core Data Processing:** The stored procedure then calls the migrated BigQuery SQL logic (from `d_ausd_bp_ta_rn_da_vda_tk.sql`). This SQL logic is expected to:
    *   Read from source tables (e.g., `source_project.source_dataset.PoolBasisprodukt`).
    *   Perform necessary data transformations and aggregations.
    *   Write the processed data to a target BigQuery table (e.g., `project.dataset.target_table`).
5.  **Record Count Capture:** After the core SQL processing, the stored procedure queries the target table to determine the number of processed records, replacing the temporary file mechanism.
6.  **Logging:** The job's status, input parameters, and processed record count are logged into `project.dataset.job_run_log`. Any errors encountered during execution are caught and logged into `project.dataset.job_error_log`.
7.  **Output:** The stored procedure completes, returning success or raising an error if validation or processing fails.

This flow is inferred from the static analysis of the `ksh` script and its referenced components, as direct `lineage_edges` for inter-file dependencies were not available for this specific run.

## 5. Transformation Logic

The primary transformation logic of the original `ksh` script (`k_ausd_bp_ta_rn_da_vda_tk.ksh`) is its orchestration and control flow. The actual data transformations are delegated to the invoked SQL script (`d_ausd_bp_ta_rn_da_vda_tk.sql`).

The ksh script's logic will be transformed into BigQuery SQL scripting as follows:

*   **Environment Sourcing:** The sourcing of `.dw_init` and other utility scripts will be replaced by:
    *   Defining variables directly within the BigQuery stored procedure.
    *   Using BigQuery built-in functions for common operations.
    *   Embedding the logic of simple utility scripts (like date calculation) directly into the procedure.
*   **Parameter Parsing:** The `getopts` logic for command-line arguments (`-j`, `-f`, `-s`, `-l`) will be directly mapped to `IN` parameters of the BigQuery Stored Procedure.
*   **Parameter Validation:** The checks for required parameters (`p_JobKennung`, `p_Stichtag`, `p_EintragsNr`) will be re-implemented using `IF` statements and `RAISE` for errors in BigQuery SQL.
*   **Date Validation:** The `DWDate_Datum_Check` functionality will be replaced by BigQuery's `SAFE.PARSE_DATE('%d%m%Y', p_Stichtag)` and a check for `NULL` to ensure the correct date format.
*   **Restart Value Initialization:** The `if [[ -z "$p_wiederanlaufWert" ]] then p_wiederanlaufWert=0 fi` logic will be replaced with a `DEFAULT '0'` clause for the corresponding parameter or an `IFNULL` / `COALESCE` check.
*   **Date Derivation (`gestern.ksh`):** The external `gestern.ksh` call to get today's and yesterday's dates will be replaced by `CURRENT_DATE()` and `DATE_SUB(CURRENT_DATE(), INTERVAL 1 DAY)` functions in BigQuery.
*   **SQL Script Execution (`starteSQLSkript`):** The invocation of `d_ausd_bp_ta_rn_da_vda_tk.sql` will be replaced by a direct call to its migrated BigQuery Stored Procedure counterpart, passing the necessary parameters.
*   **Record Count Capture:** The `eval "v_records=\`cat $tmpFile\`"` will be replaced by a `SELECT COUNT(*)` query against the target table produced by the core SQL logic.
*   **Error Reporting (`DWMSG_MeldeFehler`):** This will be replaced by BigQuery's `RAISE USING MESSAGE` statements and inserts into a dedicated error logging table.

The commented-out `sed`, `sort`, `join` operations involving `cibasis_data*.dat` files and `cibasisprodukt.csv` are considered inactive and will not be migrated.

## 7. Unresolved / Risks

*   **Core SQL Script (d_ausd_bp_ta_rn_da_vda_tk.sql):** The detailed transformation logic within this SQL script was not analyzed in this step and remains an external dependency for its own migration. Its specific reads/writes, performance, and complexity will directly impact the overall job.
*   **Commented-out Legacy Job Control:** The script contains commented-out calls to `FOSJobDeaktivate` and `FOSJobErzeugeEintrag` and related logic with `PoolBasisprodukt`. While currently inactive, a review should confirm if this functionality is truly obsolete or if it represents a latent requirement for future job logging/status management that needs to be brought into scope.
*   **Intermediate Flat Files:** The commented-out `sed`, `sort`, `join` sections hint at a historical pattern of processing data via flat files. If the `d_ausd_bp_ta_rn_da_vda_tk.sql` or other components still rely on generating or consuming intermediate flat files, this needs to be redesigned to use BigQuery tables or Cloud Storage for staging.
*   **Error Message Localization/Standardization:** The original script uses German error messages. For migration, these should either be kept as-is (if the target audience is the same) or standardized to English and integrated with a broader error logging framework in BigQuery.
*   **`starteSQLSkript` function:** The exact implementation of `starteSQLSkript` (how it invokes SQL*Plus, handles errors, and writes the record count to `tmpFile`) is not fully known. The BigQuery migration assumes this functionality can be fully replaced by direct BigQuery procedure calls and result set handling.

## 8. Build Plan

The migration will produce a BigQuery Stored Procedure that encapsulates the orchestration logic of the original ksh script.

**Build Output:**
*   **File:** `project.dataset.r_ausd_bp_ta_rn_da_vda_tk.sql`
*   **Language:** BigQuery SQL (Stored Procedure)

**Components to Generate:**

1.  **Main BigQuery Stored Procedure:**
    *   **Name:** `r_ausd_bp_ta_rn_da_vda_tk`
    *   **Parameters:** `p_JobKennung STRING`, `p_EintragsNr STRING`, `p_Stichtag STRING`, `p_wiederanlaufWert STRING` (all `IN` parameters).
    *   **Logic:**
        *   Declare internal variables (e.g., `v_TabName`, `v_records`, `v_datum_heute`, `v_datum_gestern`, `v_stichtag_date`, error variables).
        *   Implement parameter presence validation using `IF` conditions and `RAISE` statements.
        *   Implement `DDMMYYYY` date format validation for `p_Stichtag` using `SAFE.PARSE_DATE`.
        *   Default `p_wiederanlaufWert` to '0' if null or empty.
        *   Derive `v_datum_heute` and `v_datum_gestern` using `CURRENT_DATE()` and `DATE_SUB()`.
        *   Call the *migrated* BigQuery Stored Procedure corresponding to `d_ausd_bp_ta_rn_da_vda_tk.sql`, passing relevant parameters.
        *   After the SQL logic executes, query the target table (e.g., `project.dataset.target_table`) to get the number of processed records and assign it to `v_records`.
        *   Insert an entry into a `project.dataset.job_run_log` table with job details, parameters, and `v_records`.
        *   Implement error handling using a `BEGIN...EXCEPTION WHEN ERROR...END` block to catch errors from the core SQL logic and log them to `project.dataset.job_error_log`.

2.  **Supporting BigQuery Tables:**
    *   `project.dataset.job_run_log`: For auditing job execution (columns: `tab_name`, `job_kennung`, `eintrags_nr`, `stichtag`, `wiederanlauf_wert`, `records_processed`, `created_at`).
    *   `project.dataset.job_error_log`: For detailed error capturing (columns: `job_name`, `entry_nr`, `stichtag`, `error_message`, `created_at`).

**Overall Migration Steps:**
1.  Migrate `d_ausd_bp_ta_rn_da_vda_tk.sql` to a BigQuery-native format (e.g., a BigQuery Stored Procedure).

3.  Develop the `r_ausd_bp_ta_rn_da_vda_tk` BigQuery Stored Procedure as detailed above.
4.  Configure an orchestration tool (Cloud Composer, Scheduled Queries) to call the `r_ausd_bp_ta_rn_da_vda_tk` stored procedure.
