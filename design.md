# Migration Design — vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/k_ausd_bp_ta_bpr_apn.ksh

## 1. Purpose & Scope

This KornShell (ksh) script, `k_ausd_bp_ta_bpr_apn.ksh`, acts as a control and orchestration script. Its primary purpose is to manage the execution of a SQL script (`d_ausd_bp_ta_bpr_apn.sql`) within a larger data warehousing context.

The script performs the following key functions:
*   Initializes the execution environment by sourcing configuration files and utility scripts for error handling, date validation, and parameter parsing.
*   Parses command-line parameters (Job ID, entry number, reference date, restart value).
*   Validates the presence and format of required parameters, especially the reference date (`Stichtag`).
*   Invokes a core SQL script (`d_ausd_bp_ta_bpr_apn.sql`) with the parsed parameters.
*   Reads a record count from a temporary file generated by the SQL script execution.
*   Potentially logs job tracking information (commented out in the current version).
*   Includes commented-out sections for post-processing temporary flat files (sed, sort, join operations), indicating a historical or alternative data flow for file-based outputs.

The scope of this migration design is to convert this KornShell control script and its implied operations to a BigQuery-native solution, leveraging BigQuery Stored Procedures and SQL capabilities. The assumption is that the core data transformation logic resides within the invoked SQL script, which would also be migrated to BigQuery SQL.

## 3. Target Architecture

The target architecture will leverage BigQuery's capabilities for orchestration and data processing.

*   **Main Component:** A BigQuery Stored Procedure will encapsulate the control flow logic of the ksh script.
    *   **Naming Convention:** `project.dataset.r_ausd_bp_ta_bpr_apn`
    *   This stored procedure will accept input parameters that mirror the ksh script's command-line arguments.
*   **Data Processing:** The core data manipulation logic, currently in `d_ausd_bp_ta_bpr_apn.sql`, will be migrated into a separate BigQuery Stored Procedure or a series of BigQuery SQL statements called by the main control procedure.
    *   **Naming Convention:** `project.dataset.d_ausd_bp_ta_bpr_apn` (or similar, depending on the nature of the SQL script).
*   **Error Logging:** A dedicated BigQuery table (e.g., `project.dataset.job_error_log`) will be used to log execution errors and parameter validation failures, replacing the shell script's error handling and `DWMSG_MeldeFehler` function.
*   **Job Tracking:** A BigQuery table (e.g., `project.dataset.job_tracking`) will replace the functionality of the commented-out job entry creation (`FOSJobErzeugeEintrag`).
*   **Temporary Data:** Intermediate results that were handled via temporary files in the shell environment will be managed using BigQuery temporary tables or Common Table Expressions (CTEs).
*   **Orchestration:** The execution of the BigQuery Stored Procedure will be managed by an external orchestrator like Cloud Composer (Airflow), which can handle scheduling, parameter passing, and dependency management.

## 5. Transformation Logic

The ksh script primarily handles control flow, parameter management, and orchestration. The actual data transformation is expected to be in `d_ausd_bp_ta_bpr_apn.sql`. This section focuses on the ksh script's logic transformation.

**Original ksh Logic:**
*   **Environment Sourcing:** `. $HOME/.dw_init`, `. ${BERT_DIR_ROOT}/allgemein/is/util/bin/f_alis_msgerr.ksh`, etc.
*   **Parameter Parsing:** `getopts` for `j:f:s:l:`.
*   **Parameter Validation:** `pruefeParameterGesetzt` function calls.
*   **Date Validation:** `DWDate_Datum_Check`.
*   **Date Derivation:** `set \`gestern.ksh\``.
*   **SQL Execution:** `starteSQLSkript $p_EintragsNr $Name_SQLskript ...`.
*   **Record Count from File:** `eval "v_records=\`cat $tmpFile\`"`.
*   **Job Tracking:** `FOSJobErzeugeEintrag` (commented).
*   **File Post-processing:** `sed`, `sort`, `join` (commented).

**Target BigQuery SQL / Stored Procedure Logic:**

```sql
-- Main Control Stored Procedure
CREATE OR REPLACE PROCEDURE `project.dataset.r_ausd_bp_ta_bpr_apn`(
  IN p_JobKennung STRING,
  IN p_EintragsNr STRING,
  IN p_Stichtag STRING,
  IN p_wiederanlaufWert STRING
)
BEGIN
  DECLARE ErrNr INT64 DEFAULT 0;
  DECLARE ErrArg STRING DEFAULT '';
  DECLARE v_TabName STRING DEFAULT 'PoolBasisprodukt';
  DECLARE v_records INT64 DEFAULT 0;
  DECLARE v_datum_heute DATE;
  DECLARE v_datum_gestern DATE;
  DECLARE v_Stichtag_date DATE;

  -- Parameter Validation (replaces pruefeParameterGesetzt)
  IF p_JobKennung IS NULL OR TRIM(p_JobKennung) = '' THEN
    SET ErrNr = 1; SET ErrArg = 'Jobkennung';
  END IF;
  IF ErrNr = 0 AND (p_Stichtag IS NULL OR TRIM(p_Stichtag) = '') THEN
    SET ErrNr = 1; SET ErrArg = 'Stichtag';
  END IF;
  IF ErrNr = 0 AND (p_EintragsNr IS NULL OR TRIM(p_EintragsNr) = '') THEN
    SET ErrNr = 1; SET ErrArg = 'EintragsNr';
  END IF;

  -- Error Handling (replaces DWMSG_MeldeFehler and shell exit)
  IF ErrNr != 0 THEN
    INSERT INTO `project.dataset.job_error_log` (job_name, error_nr, error_arg, created_ts)
    VALUES ('r_ausd_bp_ta_bpr_apn', ErrNr, ErrArg, CURRENT_TIMESTAMP());
    SELECT FORMAT('FEHLER: 0 E %d %s', ErrNr, ErrArg) AS message;
    LEAVE; -- Exit procedure
  END IF;

  -- Date Validation (replaces DWDate_Datum_Check)
  SET v_Stichtag_date = SAFE.PARSE_DATE('%d%m%Y', p_Stichtag);
  IF v_Stichtag_date IS NULL THEN
    SET ErrNr = 193; SET ErrArg = p_Stichtag;
    INSERT INTO `project.dataset.job_error_log` (job_name, error_nr, error_arg, created_ts)
    VALUES ('r_ausd_bp_ta_bpr_apn', ErrNr, ErrArg, CURRENT_TIMESTAMP());
    SELECT FORMAT('FEHLER: 0 E %d %s', ErrNr, ErrArg) AS message;
    LEAVE;
  END IF;

  -- Date Derivation (replaces gestern.ksh)
  SET v_datum_heute = CURRENT_DATE();
  SET v_datum_gestern = DATE_SUB(CURRENT_DATE(), INTERVAL 1 DAY);

  -- Default Restart Value
  IF p_wiederanlaufWert IS NULL OR TRIM(p_wiederanlaufWert) = '' THEN
    SET p_wiederanlaufWert = '0';
  END IF;

  -- Call the migrated SQL script (d_ausd_bp_ta_bpr_apn.sql)
  CALL `project.dataset.d_ausd_bp_ta_bpr_apn`(
    CAST(p_EintragsNr AS STRING),
    CAST(p_EintragsNr AS STRING),
    p_JobKennung,
    p_Stichtag,
    v_datum_heute,
    v_datum_gestern,
    p_wiederanlaufWert
  );

  -- Get Record Count (replaces reading from tmpFile)
  SET v_records = (
    SELECT COUNT(*) FROM `project.dataset.target_result_table` WHERE stichtag = v_Stichtag_date
  );

  -- Job Tracking (replaces FOSJobErzeugeEintrag)
  INSERT INTO `project.dataset.job_tracking`
  (tab_name, status, mode, stichtag_from, stichtag_to, job_type, restart_flag, record_count, description, created_ts)
  VALUES
  (v_TabName, 'A', 'I', v_Stichtag_date, v_Stichtag_date, 'J', 'N', v_records, 'Initialbefuellung', CURRENT_TIMESTAMP());

  SELECT ' ---------- ENDE Datenverarbeitung ----------' AS message;
END;

-- For the commented-out file processing (if needed):
-- Example: Cleanse, sort, and join operations for flat files
CREATE OR REPLACE TABLE `project.dataset.cibasis_data24_clean` AS
SELECT DISTINCT REGEXP_REPLACE(line, r' ', '') AS line
FROM `project.dataset.cibasis_data24_raw`;
-- Similar tables for cibasis_data96_clean and cibasis_fax_clean

CREATE OR REPLACE TABLE `project.dataset.cibasis_24_96_tmp` AS
SELECT
  COALESCE(a.key, b.key) AS key,
  a.col1 AS data24_col1,
  a.col2 AS data24_col2,
  b.col2 AS data96_col2
FROM (
  SELECT SPLIT(line, ';')[OFFSET(0)] AS key, SPLIT(line, ';')[OFFSET(1)] AS col1, SPLIT(line, ';')[OFFSET(2)] AS col2
  FROM `project.dataset.cibasis_data24_clean`
) a
FULL OUTER JOIN (
  SELECT SPLIT(line, ';')[OFFSET(0)] AS key, SPLIT(line, ';')[OFFSET(1)] AS col1, SPLIT(line, ';')[OFFSET(2)] AS col2
  FROM `project.dataset.cibasis_data96_clean`
) b
ON a.key = b.key;
-- Similar logic for cibasisprodukt_csv with appropriate joins.
```

## 6. External Dependencies

The original ksh script has several implicit and explicit external dependencies:

*   **Shell Utilities & Environment:**
    *   `. $HOME/.dw_init`, `${BERT_DIR_ROOT}` environment variables: These define the execution context.
    *   **Replacement:** In BigQuery, these will be replaced by:
        *   Explicit parameters to the stored procedure.
        *   BigQuery project/dataset names for object qualification.
        *   Configuration variables managed by the orchestrator (e.g., Airflow variables).
*   **Utility KornShell Scripts:**
    *   `f_alis_msgerr.ksh` (error handling)
    *   `h_alis_date.ksh` (date validation)
    *   `h_alis_parameter.ksh` (parameter parsing)
    *   `h_alis_sqlplus.ksh` (SQL*Plus wrapper)
    *   `gestern.ksh` (date calculation)
    *   **Replacement:**
        *   Error handling will be integrated into the BigQuery Stored Procedure using `IF`/`ELSE` blocks and logging to a BigQuery error log table.
        *   Date validation will use BigQuery's `SAFE.PARSE_DATE`.
        *   Parameter parsing is handled inherently by the stored procedure's input arguments.
        *   SQL*Plus wrapper functionality is made obsolete by direct BigQuery SQL execution.
        *   Date calculations will use BigQuery date functions like `CURRENT_DATE()` and `DATE_SUB()`.
*   **External SQL Script:**
    *   `${BERT_DIR_ROOT}/aufbereitung/sql/d_ausd_bp_ta_bpr_apn.sql`: This is the core data processing component.
    *   **Replacement:** This SQL script needs to be migrated to a BigQuery-compatible SQL Stored Procedure or a series of SQL statements. It will be called directly by the main control procedure. The specific details of its migration depend on its content (e.g., Oracle SQL to BigQuery SQL).
*   **Temporary Files:**
    *   `$DW_DIR_UTL/bert_k_ausd_bp_ta_bpr_apn.tmp`: Used for record count.
    *   `cibasis_data24.dat`, `cibasis_data96.dat`, `cibasis_fax.dat`, `cibasis_24_96.tmp`, `cibasisprodukt.csv` (commented-out): These are flat files used for intermediate and final outputs in a legacy workflow.
    *   **Replacement:**
        *   Record counts will be obtained directly from BigQuery tables using `COUNT(*)` and stored in procedure variables or audit tables.
        *   If the commented-out file processing is activated, flat files would typically be staged in Cloud Storage, then ingested into BigQuery staging tables, and all subsequent transformations would occur within BigQuery using SQL.
*   **Job Tracking System:**
    *   Implicitly referenced by `FOSJobErzeugeEintrag` (commented).
    *   **Replacement:** A BigQuery table (`project.dataset.job_tracking`) will be created to store job metadata and execution status.
