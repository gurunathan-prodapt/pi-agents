## 1. LINEAGE & INTEGRATION CONTEXT

### 1.1 Upstream & Downstream Relationships
* **Source Pattern:** These UC4 JOBI (Job Include) scripts act as synchronization barriers (gatekeepers) between legacy Ab Initio ETL graph completions and the initiation of downstream incremental Data Warehouse (DWH) loading jobs.
* **Upstream Producers:** 
  - External processes (or an Ab Initio graph coordinator) update the global state tracking object (`dw_adm_ab_initio_var` / `DW.ADM_AB_INITIO_VAR`) to `'go'` once the base data processing is complete.
* **Downstream Consumers:**
  - Incremental DWH processing pipelines (e.g. `DWH_KERN` load stages) can only proceed once the `START_INC` task finishes successfully.
* **Orchestration Flow:**
  ```
  [Ab Initio ETL Processing / External State Update]
                         │
                         ▼
        ┌──────────────────────────────────┐
        │  DW.DWH_ADM_PRUEFE_AB_INITIO_    │  <-- Polls status loop until 'go'
        │           START_INC              │
        └──────────────────────────────────┘
                         │ (Status = 'go')
                         ▼
          ┌──────────────────────────────┐
          │     DWH Incremental Jobs     │  <-- Incremental transformations & loads
          └──────────────────────────────┘
                         │
                         ▼
        ┌──────────────────────────────────┐
        │  DW.DWH_ADM_PRUEFE_AB_INITIO_    │  <-- Marks run state as 'fertig' (complete)
        │            ENDE_INC              │
        └──────────────────────────────────┘
  ```

### 1.2 External System Replacements
* **UC4 Variable Object (`DW.ADM_AB_INITIO_VAR`)** $\rightarrow$ **Airflow Variables (JSON-serialized)**:
  - In the legacy environment, UC4 handles synchronization across decoupled processing engines (Ab Initio vs. UC4 Engine) using global variables.
  - In GCP, this state repository is replaced by Airflow's native metadata store using **Airflow Variables** (`dw_adm_ab_initio_var` JSON store) or a lightweight operational status table in BigQuery, ensuring both Cloud Composer tasks and external Cloud Composer/Cloud Functions processes can read and update process states.

## 4. ENVIRONMENT-SPECIFIC CONFIGURATION

To implement this plan successfully in production, configure the following Airflow variables:

1. **Airflow Variable Configuration:**
   Create an Airflow variable named `dw_adm_ab_initio_var` with a JSON-structured payload representing the legacy UC4 map:
   ```json
   {
     "STATUS_DWH": "wait",
     "STATUS_OTHER_APP": "active"
   }
   ```
2. **Execution Context Tuning:**
   * `poke_interval`: Set to `10` seconds to mimic UC4's polling intervals closely.
   * `timeout`: Configured to `3600` (1 hour) inside the PythonSensor tasks as a safeguard against endless looping if an external system crashes and fails to flag the state as `'go'`.

## 5. RISKS & MANUAL ACTIONS

* **Airflow Variable Performance & Database Locking:** 
  In high-frequency loops, polling Airflow's variables database table directly can cause lock contention. If this sensor executes very frequently, update the callable to query the status from a dedicated metadata table in Cloud SQL/BigQuery instead, or use Airflow's `reschedule` mode instead of `poke` mode (`mode='reschedule'`) to free up worker execution slots.
* **External State Synchronization:** 
  The component that writes the `"STATUS_DWH": "go"` must be migrated concurrently to update the designated Airflow Variable (via Airflow's REST API or Direct Variable update) to prevent deadlocks in downstream DWH processing tasks.
