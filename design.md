# Migration Design Document: ausd_bp_ta_bpr_basis

This migration design document provides the technical blueprint for converting the legacy KornShell and Oracle SQL pipeline `ausd_bp_ta_bpr_basis` into a modern cloud architecture using **Cloud Composer (Airflow)** and **Dataform** on **Google Cloud Platform (GCP)**.

---

## 1. Executive Summary

### Source Technology Stack
- **KornShell (KSH) Wrapper**: `r_ausd_bp_ta_bpr_basis.ksh` (initializes, validates parameters, and sets up logging).
- **KornShell (KSH) Control Script**: `k_ausd_bp_ta_bpr_basis.ksh` (checks parameters, calculates dates, and runs SQL).
- **Oracle PL/SQL Script**: `d_ausd_bp_ta_bpr_basis.sql` (truncates tables and processes SIM / product data).

### Prescribed Migration Pattern (High Confidence)
- **Orchestration**: Cloud Composer (Apache Airflow) DAG to replace the KSH wrapper/control scripts.
- **Data Transformation**: Dataform SQLX files to replace the step-by-step SQL scripts executing on BigQuery.
- **Storage & Processing**: Google Cloud BigQuery.

### Deviation Justification
> **No deviation from the prescribed pattern is made.** The design strictly adheres to the high-confidence DE classification pattern by implementing **Dataform SQLX models** for database transformations and **Cloud Composer (Airflow)** for job scheduling, parameter validation, and Dataform compilation/execution invocation.

## 2. Lineage and Data Flow Architecture

```
               [isbert_schema.dwtk_meldungen] (System metadata)
                             │
                             ▼
  [rma$ta_sim] ───┐     (Dataform)
                  ├─► [sof$ta_sim] (Step 02) ────────┐
  [rma$ta_sim_card_type]                             │
                                                     ├─► [sof$ta_bpr_basis] (Step 03)
  [sof$ta_bpr_basis_his] ────────────────────────────┘
```

### Upstream Tables
- `isbert_schema.dwtk_meldungen`: Contains system messages/metadata utilized to retrieve the execution date (`v_datum`).
- `rma$ta_sim` (mapped to BigQuery `carmen.rma$ta_sim` via external/synced dataset): Primary SIM card registry.
- `rma$ta_sim_card_type` (mapped to BigQuery `carmen.rma$ta_sim_card_type`): Lookup table for card type names.
- `sof$ta_bpr_basis_his` (mapped to BigQuery `sof$ta_bpr_basis_his`): Historical product instances.

### Downstream / Target Tables
- `sof$ta_sim`: Staging/temporary table populated in Step 02.
- `sof$ta_bpr_basis`: Final output product table populated in Step 03.

## 3. Dataform Transformation Logic (SQLX)

Below is the verbatim logic and converted BigQuery SQL generated by the specialized migration tooling.

### Verbatim Conversion Tool Output (HQL/SQL to BQSQL)
```sql
-- Step 00: derive v_datum equivalent
DECLARE v_datum STRING DEFAULT (
  SELECT COALESCE(FORMAT_DATE('%Y%m%d', DATE(MAX(m.timecreated))), '19000101')
  FROM `isbert_schema.dwtk_meldungen` m
  WHERE m.job_kennung = 'BERT_DROP_TEMP_TABLE'
);

-- Step 01: truncate target tables
TRUNCATE TABLE `sof$ta_sim`;
TRUNCATE TABLE `sof$ta_bpr_basis`;

-- Step 02: insert latest valid SIM records
INSERT INTO `sof$ta_sim` (
  iccid,
  sim_card_type_id,
  card_type_name
)
SELECT
  CONCAT(sim.iccid_mi, '-', sim.iccid_ii, '-', sim.iccid_iai, '-', sim.iccid_nr, '-', sim.iccid_cd) AS iccid,
  sim.sim_card_type_id,
  card.card_type_name
FROM `rma$ta_sim` sim
JOIN `rma$ta_sim_card_type` card
  ON card.sim_card_type_id = sim.sim_card_type_id
WHERE DATE(sim.insert_at) <= PARSE_DATE('%Y%m%d', v_datum)
  AND (sim.modified_at IS NULL OR DATE(sim.modified_at) > PARSE_DATE('%Y%m%d', v_datum))
  AND DATE(sim.valid_from) <= PARSE_DATE('%Y%m%d', v_datum)
  AND (sim.valid_to IS NULL OR DATE(sim.valid_to) > PARSE_DATE('%Y%m%d', v_datum))
  AND DATE(card.insert_at) <= PARSE_DATE('%Y%m%d', v_datum)
  AND (card.modified_at IS NULL OR DATE(card.modified_at) > PARSE_DATE('%Y%m%d', v_datum));

-- Step 03: insert latest valid basis product instances
INSERT INTO `sof$ta_bpr_basis` (
  cntrct_id,
  bpr_id,
  bpr_instance_id,
  iccid,
  imsi_mcc,
  imsi_mnc,
  imsi_hlr,
  imsi_si,
  valid_to,
  slave_number,
  e_id,
  card_type_name
)
SELECT
  bp.cntrct_id,
  bp.bpr_id,
  bp.bpri_com_id AS bpr_instance_id,
  bp.iccid,
  bp.imsi_mcc,
  bp.imsi_mnc,
  bp.imsi_hlr,
  bp.imsi_si,
  COALESCE(bp.valid_to, DATE '4712-12-31') AS valid_to,
  bp.slave_number,
  bp.e_id,
  sim.card_type_name
FROM (
  SELECT
    bp1.*,
    MAX(COALESCE(bp1.valid_to, DATE '4712-12-31')) OVER (
      PARTITION BY bp1.cntrct_id, bp1.bpr_id
    ) AS max_valid_to
  FROM `sof$ta_bpr_basis_his` bp1
) bp
LEFT JOIN `sof$ta_sim` sim
  ON bp.iccid = sim.iccid
WHERE COALESCE(bp.valid_to, DATE '4712-12-31') = bp.max_valid_to;
```

## 4. Target Execution Plan & Dataform Mapping

To implement this according to the **Dataform** pattern, the above queries will be split into two incremental or table-type SQLX files in a Dataform repository.

### Target File 1: `definitions/sof_ta_sim.sqlx`
- **Type**: `table` (or incremental)
- **Description**: Recreates and populates `sof$ta_sim` with latest active SIM records based on the extracted metadata date `v_datum`.
- **Logic**:
```sql
config {
  type: "table",
  name: "sof_ta_sim",
  schema: "isbert_schema",
  dependencies: ["dwtk_meldungen", "rma_ta_sim", "rma_ta_sim_card_type"]
}

WITH v_datum_cte AS (
  SELECT COALESCE(FORMAT_DATE('%Y%m%d', DATE(MAX(m.timecreated))), '19000101') AS v_datum
  FROM ${ref("dwtk_meldungen")} m
  WHERE m.job_kennung = 'BERT_DROP_TEMP_TABLE'
)

SELECT
  CONCAT(sim.iccid_mi, '-', sim.iccid_ii, '-', sim.iccid_iai, '-', sim.iccid_nr, '-', sim.iccid_cd) AS iccid,
  sim.sim_card_type_id,
  card.card_type_name
FROM ${ref("rma_ta_sim")} sim
JOIN ${ref("rma_ta_sim_card_type")} card
  ON card.sim_card_type_id = sim.sim_card_type_id
CROSS JOIN v_datum_cte
WHERE DATE(sim.insert_at) <= PARSE_DATE('%Y%m%d', v_datum_cte.v_datum)
  AND (sim.modified_at IS NULL OR DATE(sim.modified_at) > PARSE_DATE('%Y%m%d', v_datum_cte.v_datum))
  AND DATE(sim.valid_from) <= PARSE_DATE('%Y%m%d', v_datum_cte.v_datum)
  AND (sim.valid_to IS NULL OR DATE(sim.valid_to) > PARSE_DATE('%Y%m%d', v_datum_cte.v_datum))
  AND DATE(card.insert_at) <= PARSE_DATE('%Y%m%d', v_datum_cte.v_datum)
  AND (card.modified_at IS NULL OR DATE(card.modified_at) > PARSE_DATE('%Y%m%d', v_datum_cte.v_datum))
```

### Target File 2: `definitions/sof_ta_bpr_basis.sqlx`
- **Type**: `table`
- **Description**: populates `sof$ta_bpr_basis` using historical data and joins on the newly populated `sof_ta_sim` table.
- **Logic**:
```sql
config {
  type: "table",
  name: "sof_ta_bpr_basis",
  schema: "isbert_schema",
  dependencies: ["sof_ta_sim", "sof_ta_bpr_basis_his"]
}

SELECT
  bp.cntrct_id,
  bp.bpr_id,
  bp.bpri_com_id AS bpr_instance_id,
  bp.iccid,
  bp.imsi_mcc,
  bp.imsi_mnc,
  bp.imsi_hlr,
  bp.imsi_si,
  COALESCE(bp.valid_to, DATE '4712-12-31') AS valid_to,
  bp.slave_number,
  bp.e_id,
  sim.card_type_name
FROM (
  SELECT
    bp1.*,
    MAX(COALESCE(bp1.valid_to, DATE '4712-12-31')) OVER (
      PARTITION BY bp1.cntrct_id, bp1.bpr_id
    ) AS max_valid_to
  FROM ${ref("sof_ta_bpr_basis_his")} bp1
) bp
LEFT JOIN ${ref("sof_ta_sim")} sim
  ON bp.iccid = sim.iccid
WHERE COALESCE(bp.valid_to, DATE '4712-12-31') = bp.max_valid_to
```

## 5. Orchestration (Cloud Composer Airflow DAG)

The Airflow DAG will replace the behavior of `r_ausd_bp_ta_bpr_basis.ksh` and `k_ausd_bp_ta_bpr_basis.ksh`. It manages job variables, executes parameter validations (such as checking key date formats), and triggers the compilation and execution of the Dataform models defined above.

### High-Level Airflow DAG Pseudocode

```python
import datetime
from airflow import DAG
from airflow.providers.google.cloud.operators.dataform import DataformCreateCompilationResultOperator, DataformWriteApiOperator
from airflow.operators.python import PythonOperator
from airflow.exceptions import AirflowException

def validate_parameters(**kwargs):
    # Retrieve runtime variables or default parameter dates
    stichtag = kwargs['dag_run'].conf.get('stichtag', datetime.datetime.now().strftime('%d%m%Y'))
    
    # Python alternative to the legacy DWDate_Datum_Check DDMMYYYY
    try:
        datetime.datetime.strptime(stichtag, '%d%m%Y')
    except ValueError:
        raise AirflowException(f"Validation failed: Parameter Stichtag '{stichtag}' is not in DDMMYYYY format.")
    
    print(f"Parameter Stichtag validated successfully: {stichtag}")

default_args = {
    'owner': 'composer',
    'start_date': datetime.datetime(2023, 1, 1),
    'retries': 1,
}

with DAG(
    'ausd_bp_ta_bpr_basis_orchestration',
    default_args=default_args,
    schedule_interval='@daily',
    catchup=False
) as dag:

    # 1. Parameter Validation step
    validate_params = PythonOperator(
        task_id='validate_params',
        python_callable=validate_parameters,
        provide_context=True,
    )

    # 2. Trigger compilation of the Dataform workflow
    compile_dataform = DataformCreateCompilationResultOperator(
        task_id="compile_dataform",
        project_id="gcp-project-id",
        region="us-central1",
        repository_id="bert-data-transforms",
        compilation_result={
            "git_commitish": "main"
        },
    )

    # 3. Execute Dataform tags relating to the ausd_bp_ta_bpr_basis flow
    execute_dataform = DataformWriteApiOperator(
        task_id="execute_dataform",
        project_id="gcp-project-id",
        region="us-central1",
        repository_id="bert-data-transforms",
        # Optionally pass v_datum as a Dataform compilation override if needed dynamically
    )

    validate_params >> compile_dataform >> execute_dataform
```

## 6. Environment and Design Considerations

### Configuration Mapping
- **`&v_carmen` Database Link**: Replaced with proper BigQuery project/dataset references (`gcp-project.carmen_dataset.*`).
- **`v_datum` Variable Extraction**: Handled natively in modern BigQuery SQL via CTEs in Dataform, removing the need for shell `sed` or temporary disk operations.
- **Oracle Performance Hints**: All performance hints such as `/*+ parallel(sim,4) */` have been entirely removed because BigQuery scales execution and performance automatically.
- **Transactional Integrity**: BigQuery natively auto-commits DML queries; hence, `COMMIT` commands have been successfully cleaned from the operational scripts.
