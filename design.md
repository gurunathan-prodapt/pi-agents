# Migration Design — k_ausd_v_ta_action_assoc.ksh

## 1. Purpose & Scope
This job, `k_ausd_v_ta_action_assoc.ksh`, is part of an ETL workflow designed to mirror Carmen associations of contracts to actions. It orchestrates the process of updating the `ta_action_assoc` data. The primary business purpose is to synchronize contract-to-action associations from a source system (Carmen DB, specifically `cds$ta_action_assoc`) into a data warehouse table (`sof$ta_action_assoc`). The job ensures that the target table reflects the current state of production-flagged, valid records from the source, filtered by a specific date (`v_datum`) derived from a metadata table (`isbert_schema.dwtk_meldungen`).

  TRUNCATE TABLE sof_ta_action_assoc;

  -- Insert new data based on filtered source records
  INSERT INTO sof_ta_action_assoc(cntrct_id, rv_action_id)
  SELECT
    ac.cntrct_id,
    ac.rv_action_id
  FROM cds_ta_action_assoc ac
  WHERE DATE(ac.insert_at) <= PARSE_DATE('%Y%m%d', v_datum)
    AND DATE(ac.valid_from) <= PARSE_DATE('%Y%m%d', v_datum)
    AND ac.is_production = 1
    AND (ac.modified_at IS NULL OR DATE(ac.modified_at) > PARSE_DATE('%Y%m%d', v_datum))
    AND (ac.valid_to IS NULL OR DATE(ac.valid_to) > PARSE_DATE('%Y%m%d', v_datum));

### 5. Transformation Logic
The transformation logic, primarily encapsulated in the original `d_ausd_v_ta_action_assoc.sql` script, involves:
- **Date Determination**: A critical date (`v_datum`) is dynamically determined by querying the `isbert_schema.dwtk_meldungen` table for the maximum `timecreated` associated with `job_kennung = 'BERT_DROP_TEMP_TABLE'`. If no such date is found, a default of '19000101' is used.
- **Truncate and Load**: The target table `sof$ta_action_assoc` is truncated, and then reloaded with data from `cds$ta_action_assoc`.
- **Filtering**: Records are selected based on several conditions:
    - `insert_at` must be less than or equal to `v_datum`.
    - `valid_from` must be less than or equal to `v_datum`.
    - `is_production` must be `1`.
    - `modified_at` must be NULL or greater than `v_datum`.
    - `valid_to` must be NULL or greater than `v_datum`.
- **Column Mapping**: `cntrct_id` and `rv_action_id` are directly mapped from the source `cds$ta_action_assoc` to `sof$ta_action_assoc`.

The BigQuery SQL provided in Section 4 accurately reflects this logic. All Oracle-specific functions (`TO_DATE`, `NVL`) have been replaced with their BigQuery equivalents (`PARSE_DATE`, `COALESCE`). The `TRUNCATE TABLE` and `INSERT INTO ... SELECT` statements are directly compatible. The `DEFINE`, `COLUMN`, `SPOOL`, `WHENEVER SQLERROR`, `SET`, and `PROMPT` statements from the original SQL*Plus script are environment/tooling specific and will be handled by the Airflow task logic.

## 6. External Dependencies
The original job has the following external dependencies:

- **Oracle Database (Carmen DB)**: The `d_ausd_v_ta_action_assoc.sql` script explicitly uses a DB link (`@pcrs1`) to access `cds$ta_action_assoc`. This indicates `cds$ta_action_assoc` resides in an external Oracle database.
    - **Replacement Strategy**: The `cds$ta_action_assoc` table needs to be migrated or replicated to BigQuery. This could involve:
        - **Data Transfer Service (DTS)**: For ongoing replication of `cds$ta_action_assoc` into BigQuery.
        - **Batch Load**: If the data is relatively static or can tolerate daily/periodic loads, export from Oracle and load into BigQuery using Cloud Storage and BigQuery's load jobs.
        - **Federated Queries**: As a temporary or niche solution, BigQuery can query external data sources (like Cloud SQL for PostgreSQL or MySQL, which could host a replicated Carmen DB, or even directly against certain Oracle data if a suitable connector is available and performance is acceptable), but direct Oracle DB Link equivalent for BigQuery is not typical for production ETL. The preferred approach is to ingest the data into BigQuery.
- **Oracle Database (`isbert_schema.dwtk_meldungen`)**: This table, also in Oracle, is used to determine the `v_datum`.
    - **Replacement Strategy**: Similar to `cds$ta_action_assoc`, this metadata table should be ingested into BigQuery.
- **UNIX Host (DWHDWH1P)**: The UC4 job runs on a specific UNIX host.
    - **Replacement Strategy**: This will be replaced by the Google Cloud environment, with Airflow orchestrating tasks on managed services like BigQuery.
- **Legacy Shell Utilities (`.dw_init`, `f_alis_msgerr.ksh`, `h_alis_date.ksh`, `h_alis_parameter.ksh`)**: These are sourced by the KornShell scripts for environment setup, error handling, and parameter parsing.
    - **Replacement Strategy**: These functionalities will be re-implemented in Python within the Airflow DAG's tasks. Airflow provides robust mechanisms for environment variables, parameter passing, and logging, negating the need for custom shell utilities.

## 7. Unresolved / Risks
- **`v_carmen` DB Link**: The `d_ausd_v_ta_action_assoc.sql` explicitly uses `&v_carmen` which is defined as `\"@pcrs1\"`. This confirms an external Oracle dependency. The tool did not explicitly identify `@pcrs1` as an external system, but the SQL code clearly shows its usage. This needs to be actively managed and migrated into BigQuery. The BigQuery SQL conversion assumed the tables `cds$ta_action_assoc` and `isbert_schema.dwtk_meldungen` will be available directly in BigQuery, implying prior migration/replication.
- **Parameter Handling**: The KornShell scripts handle parameters (`-j` for JobKennung, `-f` for EintragsNr). The Airflow DAG will need to be designed to either:
    - Pass these as Airflow DAG run parameters.
    - Derive these values dynamically within the Python task before executing the BigQuery SQL.
    The current BigQuery SQL has `DECLARE v_datum STRING;` implying that `v_datum` is an internal variable and not an external parameter passed. The `job_kennung = 'BERT_DROP_TEMP_TABLE'` condition is hardcoded. This aspect requires careful review to ensure it matches desired behavior.
- **Error Handling and Logging**: The original shell scripts use custom error handling and logging utilities (`f_alis_msgerr.ksh`, `DWMSG_MeldeFehler`, `DWMSG_Logdateiname`, etc.). These need to be properly translated to Airflow's logging mechanisms and error handling (e.g., `on_failure_callback`).
- **Scheduling**: The UC4 job has no explicit schedule in the provided XML, marked as `schedule: None`. This will need to be explicitly defined for the Airflow DAG based on business requirements.
- **`sof$ta_action_assoc` table**: The BigQuery SQL references `sof_ta_action_assoc` without a schema/dataset prefix. This assumes it's in the default project/dataset or implicitly resolved. Best practice for BigQuery is to always use fully qualified names (`project.dataset.table`).
