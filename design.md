# Migration Design — vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/k_ausd_v_ta_discount_rr.ksh

## 1. Purpose & Scope
This migration job, identified by `run_id 5af228f1-3847-4cc6-9310-ed82ed19407c`, is designed to port an existing KornShell script (`k_ausd_v_ta_discount_rr.ksh`) and its dependent Oracle SQL script (`d_ausd_v_ta_discount_rr.sql`) to Google Cloud Platform, specifically targeting BigQuery for data processing and a BigQuery Stored Procedure for orchestration.

The original KornShell script acts as a control script for a related SQL script. Its primary responsibilities include:
*   Handling environment setup.
*   Parsing command-line parameters (`-j p_JobKennung`, `-f p_EintragsNr`).
*   Performing basic error checking and parameter validation.
*   Executing an Oracle SQL script (`d_ausd_v_ta_discount_rr.sql`) using a helper function (`starteSQLSkript`).
*   Capturing the record count from a temporary file after SQL execution.
*   Managing job entries in a job table (implicitly via the `starteSQLSkript` function).
*   Ignoring active jobs and deactivating older active jobs.

The embedded Oracle SQL script (`d_ausd_v_ta_discount_rr.sql`) performs data transformation by reading from several Oracle source tables and inserting/merging into target Oracle tables.

The business purpose of this job is to process and prepare discount-related data, likely for reporting or further analytical use, by extracting, transforming, and loading information from various source tables into aggregated or derived target tables.

## 3. Target Architecture
The migration target platform is Google Cloud BigQuery. The existing two-tier architecture (Shell script orchestration + SQL data transformation) will be re-platformed as follows:

*   **Orchestration Layer:** The KornShell script's logic will be refactored into a BigQuery Stored Procedure. This procedure will handle parameter validation, job control (e.g., checking for active jobs, logging), and the execution of the data transformation logic.
*   **Data Transformation Layer:** The Oracle SQL script's logic will be converted into standard BigQuery SQL statements. These statements will be embedded directly within the BigQuery Stored Procedure or called via `EXECUTE IMMEDIATE`.
*   **Scheduling:** The job will be scheduled using Cloud Composer (Airflow) or Cloud Scheduler, triggering the BigQuery Stored Procedure.
*   **Data Storage:** All source and target tables currently residing in Oracle will be migrated to BigQuery tables.

**BigQuery Component Layout:**
*   **BigQuery Dataset:** A dedicated dataset (e.g., `isrpt_isbert_stage`) will host the migrated tables and stored procedures.
*   **Stored Procedure:** `sp_ausd_v_ta_discount_rr` (or similar name) will encapsulate the orchestration logic.
*   **Target Tables:**
    *   `sof_ta_discount_rr` (replacing Oracle `SOF$TA_DISCOUNT_RR`)
    *   `via` (replacing Oracle `VIA`)
    *   Supporting tables for job control and logging (e.g., `job_table`, `job_log`).
*   **Source Tables:**

    *   `cds_ta_discount_bc_assoc` (replacing Oracle `CDS$TA_DISCOUNT_BC_ASSOC`)

**Original KSH Script Key Elements:**

*   **Parameter Validation:** `pruefeParameterGesetzt` function calls.
*   **Error Handling:** `DWMSG_MeldeFehler` and `exit` with error codes.

*   **SQL Execution:** `starteSQLSkript $p_EintragsNr $Name_SQLskript $p_EintragsNr $p_JobKennung`.

  IN p_JobKennung STRING,
  IN p_EintragsNr STRING

BEGIN
  DECLARE v_TabName STRING DEFAULT 'ta_discount_rr';
  DECLARE v_records INT64 DEFAULT 0;
  DECLARE v_err_msg STRING DEFAULT '';

  -- Parameter validation (replaces pruefeParameterGesetzt)
  IF p_JobKennung IS NULL OR TRIM(p_JobKennung) = '' THEN
    SET v_err_msg = 'Jobkennung fehlt';
    -- Log error and raise exception
    INSERT INTO `project.dataset.job_log` (job_kennung, eintrags_nr, status, message, created_at)
    VALUES (p_JobKennung, p_EintragsNr, 'ERROR', v_err_msg, CURRENT_TIMESTAMP());
    RAISE USING MESSAGE = v_err_msg;
  END IF;
  -- Similar validation for p_EintragsNr

  -- Deactivate older active jobs (derived from script's intent)
  UPDATE `project.dataset.job_table`
  SET active_flag = FALSE, updated_at = CURRENT_TIMESTAMP()
  WHERE job_name = v_TabName AND active_flag = TRUE AND eintrags_nr <> p_EintragsNr;

  -- Ignore currently active jobs (derived from script's intent)

  VALUES (v_TabName, p_JobKennung, p_EintragsNr, TRUE, CURRENT_TIMESTAMP());

  -- Execute core SQL logic (replaces invocation of d_ausd_v_ta_discount_rr.sql)
  -- This is where the converted Oracle SQL will be placed
  -- Example: EXECUTE IMMEDIATE `CALL project.dataset.sp_process_discount_data(p_JobKennung, p_EintragsNr);`;
  -- Or inline the SQL directly.

  -- Capture record count (replaces reading from temp file)
  SET v_records = (SELECT COUNT(*) FROM `project.dataset.target_table` WHERE job_kennung = p_JobKennung AND eintrags_nr = p_EintragsNr);

### 5.2. Data Transformation Logic (Oracle SQL to BigQuery SQL)
The `d_ausd_v_ta_discount_rr.sql` performs an `INSERT INTO` statement based on a complex `SELECT` query joining multiple tables.

**Original Oracle SQL Key Elements:**
*   **Variable Definition:** `DEFINE v_carmen = "@pcrs1"`, `COLUMN s_datum new_value v_datum noprint`, `SELECT NVL(TO_CHAR(MAX(m.timecreated),'YYYYMMDD'),'19000101') AS s_datum FROM isbert_schema.dwtk_meldungen m WHERE m.job_kennung = 'BERT_DROP_TEMP_TABLE';` to set `v_datum`.
*   **Session Settings:** `START ../trace.sql.cfg`, `SPOOL`, `WHENEVER SQLERROR CONTINUE/EXIT FAILURE`, `SET TIMING ON`, `SET SERVEROUTPUT ON`.
*   **Truncation:** `isbert_schema.DWPA_UTIL_SKRIPT.runstatement(0, 'TRUNCATE TABLE sof$ta_discount_rr');`
*   **Main Transformation:** `INSERT INTO sof$ta_discount_rr(...) SELECT ... FROM ... WHERE ...;`
    *   Involves `cds$ta_discount_bc_assoc`, `cds$ta_discount`, `cds$ta_care_description`, `cds$ta_disc_vector`, `cds$ta_disc_invoice_item`.
    *   Joins are based on `discount_id`, `cds_description_id`, `disc_invoice_item_id`.
    *   Filters on `LANGUAGE = 1` and various date columns (`insert_at`, `modified_at`, `valid_from`, `valid_to`) compared to `&v_datum`.
    *   Includes Oracle hints: `/*+ parallel(...) full(...) */`.
    *   Uses Oracle functions: `NVL`, `TO_CHAR`, `TO_DATE`.
*   **Commit:** `commit;`

**Converted BigQuery SQL (Conceptual):**
This logic will be translated into a BigQuery `INSERT INTO` statement within the main stored procedure or a separate called procedure.

```sql
-- Inside sp_ausd_v_ta_discount_rr or a dedicated data transformation stored procedure

-- Variable for date determination (replaces Oracle COLUMN/SELECT)
DECLARE v_process_date STRING;
SET v_process_date = (
  SELECT
    IFNULL(FORMAT_DATE('%Y%m%d', MAX(m.timecreated)), '19000101')
  FROM
    `project.dataset.dwtk_meldungen` AS m
  WHERE
    m.job_kennung = 'BERT_DROP_TEMP_TABLE'
);

-- Truncation (replaces DWPA_UTIL_SKRIPT.runstatement)
TRUNCATE TABLE `project.dataset.sof_ta_discount_rr`;

-- Main Data Transformation (replaces Oracle INSERT ... SELECT)
INSERT INTO `project.dataset.sof_ta_discount_rr` (
  cntrct_id,
  discount_id,
  disc_vector_ty,
  cntrct_obj_version,
  cntrct_template_id,
  disc_invoice_item_id,
  rabatt,
  rabatthoehe,
  rabattierte_rech_pos
)
SELECT
  da.cntrct_id,
  da.discount_id,
  d.disc_vector_ty,
  da.cntrct_obj_version,
  d.cntrct_template_id,
  d.disc_invoice_item_id,
  cd.cds_description AS rabatt,
  dv.CALC_RULE_VALUE AS rabatthoehe,
  cdii.CDS_DESCRIPTION AS rabattierte_rech_pos
FROM
  `project.dataset.cds_ta_discount_bc_assoc` AS da
JOIN
  `project.dataset.cds_ta_discount` AS d ON da.discount_id = d.discount_id
JOIN
  `project.dataset.cds_ta_care_description` AS cd ON cd.cds_description_id = d.CDS_DESCRIPTION_ID
JOIN
  `project.dataset.cds_ta_disc_vector` AS dv ON d.discount_id = dv.discount_id
    AND d.disc_vector_ty = dv.disc_vector_ty
    AND d.obj_version = dv.discount_obj_version
JOIN
  `project.dataset.cds_ta_disc_invoice_item` AS dii ON d.DISC_INVOICE_ITEM_ID = dii.DISC_INVOICE_ITEM_ID
JOIN
  `project.dataset.cds_ta_care_description` AS cdii ON dii.CDS_DESCRIPTION_ID = cdii.CDS_DESCRIPTION_ID
WHERE
  cd.LANGUAGE = 1
  AND cdii.LANGUAGE = 1
  AND da.insert_at <= PARSE_DATE('%Y%m%d', v_process_date)
  AND (da.modified_at IS NULL OR da.modified_at > PARSE_DATE('%Y%m%d', v_process_date))
  AND d.insert_at <= PARSE_DATE('%Y%m%d', v_process_date)
  AND (d.modified_at IS NULL OR d.modified_at > PARSE_DATE('%Y%m%d', v_process_date))
  AND d.valid_from <= PARSE_DATE('%Y%m%d', v_process_date)
  AND (d.valid_to IS NULL OR d.valid_to > PARSE_DATE('%Y%m%d', v_process_date))
  AND dv.insert_at <= PARSE_DATE('%Y%m%d', v_process_date)
  AND (dv.modified_at IS NULL OR dv.modified_at > PARSE_DATE('%Y%m%d', v_process_date))
  AND d.is_production = 1
  AND dii.insert_at <= PARSE_DATE('%Y%m%d', v_process_date)
  AND (dii.modified_at IS NULL OR dii.modified_at > PARSE_DATE('%Y%m%d', v_process_date));
```

### 6.3. Utility Shell Scripts
*   **Original Role:** Scripts like `f_alis_msgerr.ksh`, `h_alis_date.ksh`, `h_alis_parameter.ksh`, `h_alis_sqlplus.ksh` are sourced for error handling, date utilities, parameter parsing, and SQL*Plus invocation. `.dw_init` is for environment initialization.

Environment initialization will be handled by the Cloud Composer environment or BigQuery's execution context.

## 7. Unresolved / Risks

*   **Complexity of `starteSQLSkript`:** The exact logic within the `starteSQLSkript` function (beyond just executing the SQL) is not fully known. It is assumed to handle job table entries and writing to the temporary file. This implicit logic needs to be fully understood and re-implemented in the BigQuery Stored Procedure.
*   **Oracle `/*+ parallel(...) full(...) */` hints:** These performance hints are Oracle-specific. While BigQuery automatically handles parallelism, a careful review of the query performance in BigQuery is necessary to ensure optimal execution without these hints. Indexing and partitioning strategies in BigQuery might be different.
*   **Oracle `WHENEVER SQLERROR`:** This error handling mechanism needs to be translated to BigQuery's error handling within stored procedures (e.g., `BEGIN...EXCEPTION` blocks).
*   **`v_carmen = "@pcrs1"` DB Link:** This indicates a potential cross-database dependency. While it's assumed to be replaced by direct BigQuery table references, the specific implications of data consistency and latency for `pcrs1` need to be assessed during migration.
*   **Historical Data:** The SQL script uses date filtering (`insert_at`, `modified_at`, `valid_from`, `valid_to`) against a `v_datum` derived from `dwtk_meldungen`. Ensure that historical data is correctly migrated and that the date logic behaves identically in BigQuery.
*   **Unresolved Targets/External Systems:** The initial query for `unresolved_targets` and `external_systems` returned empty results, indicating that all dependencies were successfully mapped within the lineage. However, the presence of specific Oracle packages (`DWPA_UTIL_SKRIPT`) and DB links (`@pcrs1`) highlight implicit external system interactions that have been identified and addressed in this design.
*   **Semi-Automatic Migration:** The `semi_auto` bucket confirms that direct 1:1 translation might not be possible, requiring some manual refactoring and re-implementation, particularly for the shell scripting constructs and Oracle-specific PL/SQL features.
