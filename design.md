# Migration Design — vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/r_ausd_v_ta_discount.ksh

## 1. Purpose & Scope
The original script `r_ausd_v_ta_discount.ksh` is a KornShell wrapper responsible for orchestrating the reconciliation of contract data for the `ta_discount` table. Its main functions include setting up the execution environment, parsing command-line parameters, managing custom logging (`DWMSG_` functions), implementing error handling, and invoking a core processing script, `k_ausd_v_ta_discount.ksh`.

The scope of this migration is to re-platform this orchestration and data processing workflow from its legacy KornShell environment to Google Cloud Platform. The target architecture will leverage Cloud Composer (Apache Airflow) for workflow orchestration and BigQuery for data storage and transformation.

## 3. Target Architecture
The migrated solution will utilize the following Google Cloud services:
- **Cloud Composer (Apache Airflow):** This will be the primary orchestration engine, replacing the KornShell wrapper. It will manage task dependencies, scheduling, and overall workflow execution.
- **BigQuery:** The `ta_discount` table and any related datasets will be migrated to BigQuery. All data transformation and reconciliation logic, primarily derived from `k_ausd_v_ta_discount.ksh`, will be implemented as BigQuery SQL queries.
- **Cloud Storage:** Potentially used for staging data, storing configuration files, or temporary outputs if required by the translated `k_ausd_v_ta_discount.ksh` logic.
- **Cloud Logging & Monitoring:** All logs generated by the Airflow DAG and BigQuery jobs will be centralized in Cloud Logging. Cloud Monitoring will provide dashboards and alerts for workflow health and performance.

## 5. Transformation Logic
The `r_ausd_v_ta_discount.ksh` script primarily acts as an orchestration layer rather than directly performing data transformations. The actual data reconciliation logic is encapsulated within `k_ausd_v_ta_discount.ksh`.

**A. `r_ausd_v_ta_discount.ksh` (Orchestration Logic):**
- **Legacy:** KornShell script handling sequential execution, environment sourcing, parameter validation, and custom logging.
- **Target (Airflow DAG in Python):**
    - The entire workflow will be represented as a Python-based Airflow DAG.
    - **Environment Initialization:** General environment variables will be managed by Cloud Composer. Any specific legacy environment sourcing will be replaced by direct assignment in Python or by calling small shell scripts via `BashOperator` if necessary.
    - **Parameter Handling:** Command-line parameters like `-j` and `-f` will be converted to Airflow DAG parameters, which can be passed during manual triggers or defined for scheduled runs.
    - **Custom Logging (`DWMSG_` functions) & Error Trapping (`trap`):** These will be entirely replaced by Airflow's native logging system (integrated with Cloud Logging) and its robust error handling, retry mechanisms, and alerting (e.g., email or PagerDuty integrations).
    - **Invoking `k_ausd_v_ta_discount.ksh`:** This will be replaced by an Airflow operator that executes the translated core processing logic.

**B. `k_ausd_v_ta_discount.ksh` (Core Processing Logic):**
- **Legacy:** This script is assumed to contain the primary data reconciliation logic for `ta_discount`, likely involving SQL operations.
- **Target (BigQuery SQL):** The detailed logic from `k_ausd_v_ta_discount.ksh` will need to be extracted and translated into BigQuery-compatible SQL. This SQL will then be executed using a `BigQueryOperator` within the Airflow DAG. If `k_ausd_v_ta_discount.ksh` includes non-SQL data manipulation (e.g., shell commands for file processing), those parts will be re-implemented in Python and potentially run using a `PythonOperator` or via a `DataprocStartSparkBatchOperator` for larger-scale data processing.
