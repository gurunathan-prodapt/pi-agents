# Migration Design — vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/r_ausd_v_ta_notice.ksh

## 1. Purpose & Scope
This migration job focuses on the transformation of a legacy KornShell script suite designed for the reconciliation of contract data related to the `ta_notice` table. The primary objective is to re-implement this batch process natively within Google BigQuery, ensuring functional equivalence while leveraging BigQuery's capabilities for data processing, logging, and orchestration.

The job, named `r_ausd_v_ta_notice.ksh`, acts as a wrapper script. It orchestrates the execution of a core control script (`k_ausd_v_ta_notice.ksh`), which in turn executes a SQL script (`d_ausd_v_ta_notice.sql`). The overall purpose is to extract current production contract notice records, filtered by a specific cutoff date, from a source system (identified as an Oracle database via DB link) and load them into a target table (`sof$ta_notice`), after truncating existing data. The process includes robust error handling and logging mechanisms.

The scope of this migration includes:
- Conversion of KornShell scripting logic to BigQuery stored procedures.
- Translation of Oracle SQL DDL/DML to BigQuery SQL syntax.
- Replacement of file-based logging and temporary data exchange with BigQuery-native solutions (e.g., audit tables, variables).
- Addressing external dependencies such as Oracle DB links and custom shell utility functions.
- Integration into a modern orchestration framework (e.g., Cloud Composer).

## 3. Target Architecture
The migrated solution will reside entirely within Google Cloud Platform, primarily utilizing BigQuery.

- **BigQuery Stored Procedures:** The KornShell scripts (`r_ausd_v_ta_notice.ksh`, `k_ausd_v_ta_notice.ksh`) will be re-implemented as BigQuery stored procedures. These procedures will handle the job orchestration, parameter passing, and execution of data manipulation logic.
  - `project.dataset.r_ausd_v_ta_notice` (wrapper procedure)
  - `project.dataset.k_ausd_v_ta_notice` (core logic procedure)
- **BigQuery Tables:**
  - `project.dataset.sof_ta_notice`: The target table for the reconciled contract data.
  - `project.dataset.cds_ta_notice`: The source table, an equivalent of the legacy `cds$ta_notice` from the Oracle system. This could be populated via a data transfer service, external table, or other ingestion methods.
  - `project.dataset.dwtk_meldungen`: An audit/log table storing job execution metadata, equivalent to `isbert_schema.dwtk_meldungen`.
  - `project.dataset.job_log`: A new BigQuery audit table to capture detailed job execution logs, replacing file-based logging and messages.
- **Orchestration:** The job's execution will be managed by a modern scheduler, such as Cloud Composer (Airflow), replacing the legacy UC4 scheduler dependency.
- **Data Ingestion:** The source `cds$ta_notice` data, currently accessed via an Oracle DB link (`@pcrs1`), will need a dedicated ingestion pipeline to BigQuery. Options include:
  - **BigQuery Data Transfer Service:** For recurring transfers from on-premise databases.
  - **Federated Queries:** If real-time access to a transactional database is required (e.g., Cloud SQL).
  - **Change Data Capture (CDC):** Using tools like Datastream to replicate changes from the source Oracle database to BigQuery.
  - **Batch Export/Load:** Periodic exports from Oracle to Cloud Storage, followed by BigQuery loads.

## 4. Data Flow & Lineage
The data flow in the target BigQuery environment will be as follows:

1.  **Orchestration (e.g., Cloud Composer DAG):** Triggers the `r_ausd_v_ta_notice` BigQuery stored procedure. This replaces the UC4 job scheduling.
2.  **`project.dataset.r_ausd_v_ta_notice` (BigQuery Stored Procedure):**
    *   Initiates logging to `project.dataset.job_log`.
    *   Determines the processing cutoff date (`v_datum`) by querying `project.dataset.dwtk_meldungen` for the latest `timecreated` associated with `job_kennung = 'BERT_DROP_TEMP_TABLE'`. This replaces the Oracle SQL `DEFINE` and `SELECT NVL(TO_CHAR(MAX(m.timecreated)...` logic.
    *   Calls the `project.dataset.k_ausd_v_ta_notice` BigQuery stored procedure, passing the job identifier, entry number, and the derived cutoff date.
    *   Logs success or failure to `project.dataset.job_log`.
3.  **`project.dataset.k_ausd_v_ta_notice` (BigQuery Stored Procedure):**
    *   Performs parameter validation.
    *   `TRUNCATE TABLE project.dataset.sof_ta_notice;` (replaces the `isbert_schema.DWPA_UTIL_SKRIPT.runstatement(0, 'TRUNCATE TABLE sof$ta_notice');` call).
    *   Executes an `INSERT INTO ... SELECT` statement to populate `project.dataset.sof_ta_notice` from `project.dataset.cds_ta_notice`. The filtering logic remains the same.
    *   Calculates the number of inserted records using `SELECT COUNT(*)` and records it.
    *   Logs execution details and record counts to `project.dataset.job_log`.

**Simplified Lineage:**
`Cloud Composer (or equivalent)` -> `BQ SP r_ausd_v_ta_notice` -> `BQ SP k_ausd_v_ta_notice` -> `BQ Table cds_ta_notice` (READS) -> `BQ Table sof_ta_notice` (WRITES)
Also, `BQ SP r_ausd_v_ta_notice` and `BQ SP k_ausd_v_ta_notice` will interact with `BQ Table dwtk_meldungen` (READS) and `BQ Table job_log` (WRITES).

## 5. Transformation Logic
The core transformation logic involves filtering and loading data based on date criteria and an `is_production` flag.

**Legacy Oracle SQL (`d_ausd_v_ta_notice.sql`):**
```sql
SELECT
        n.cntrct_id,
        n.valid_from,
        n.valid_to,
        n.entry_date_of_notice
FROM
        cds$ta_notice     &v_carmen     n
WHERE
        n.insert_at <= TO_DATE('&v_datum','YYYYMMDD')
AND     (   n.modified_at IS NULL
         OR n.modified_at > TO_DATE('&v_datum','YYYYMMDD')     )
AND     (   n.valid_to IS NULL
         OR n.valid_to > TO_DATE('&v_datum','YYYYMMDD')        )
AND     n.is_production = 1;
```

**Migrated BigQuery SQL (`k_ausd_v_ta_notice` Stored Procedure):**
```sql
  TRUNCATE TABLE `project.dataset.sof_ta_notice`;

  INSERT INTO `project.dataset.sof_ta_notice`
  (
    cntrct_id,
    valid_from,
    valid_to,
    entry_date_of_notice
  )
  SELECT
    n.cntrct_id,
    n.valid_from,
    n.valid_to,
    n.entry_date_of_notice
  FROM `project.dataset.cds_ta_notice` n
  WHERE n.insert_at <= PARSE_DATE('%Y%m%d', v_datum)
    AND (n.modified_at IS NULL OR n.modified_at > PARSE_DATE('%Y%m%d', v_datum))
    AND (n.valid_to IS NULL OR n.valid_to > PARSE_DATE('%Y%m%d', v_datum))
    AND n.is_production = 1;
```
- **Date Conversion:** `TO_DATE('&v_datum','YYYYMMDD')` is replaced by BigQuery's `PARSE_DATE('%Y%m%d', v_datum)`.
- **DB Link:** The `&v_carmen` (Oracle DB link) is removed, assuming `project.dataset.cds_ta_notice` is already available in BigQuery.
- **Table Truncation:** The `TRUNCATE TABLE` statement directly replaces the Oracle `isbert_schema.DWPA_UTIL_SKRIPT.runstatement`.
- **Variable Handling:** KornShell script variables (`$DW_EintragsNr`, `$JobKennung`, `v_TabName`) and SQL*Plus `DEFINE`/`COLUMN NEW_VALUE` are replaced by BigQuery stored procedure parameters (`p_job_kennung`, `p_eintrags_nr`, `v_datum`) and `DECLARE` statements.

## 7. Unresolved / Risks
-   **Oracle DB Link (`@pcrs1`):** This is a significant dependency that requires careful handling. The current design assumes `cds$ta_notice` is made available in BigQuery. The mechanism for this data ingestion (e.g., Data Transfer Service, Datastream, batch load) needs to be defined and implemented. Risk: Data freshness and latency requirements from the source system must be met by the chosen ingestion method.
-   **Proprietary Shell Utilities:** The scripts source several utility `.ksh` files (e.g., `f_alis_msgerr.ksh`, `h_alis_parameter.ksh`, `h_alis_date.ksh`, `h_alis_sqlplus.ksh`). While their basic functionalities (error handling, parameter parsing, date manipulation, SQL execution) can be replicated in BigQuery stored procedures and orchestration, any complex or highly customized logic within these utilities needs to be thoroughly analyzed and re-implemented. Risk: Missing subtle logic or side effects of these utilities.
-   **File-based Logging and Tracing:** The existing scripts rely on file redirection (`>> $LogDatei 2>&1`), `spool` commands, and temporary files (`tmpFile`) for logging and data exchange. These need to be completely replaced with BigQuery-native logging (e.g., `job_log` table inserts, BigQuery native logging features, Cloud Logging). Risk: Loss of historical log data or difficulty in auditing if not properly migrated.
-   **Error Handling (`set -eu`, `trap`, `WHENEVER SQLERROR`):** The KornShell `set -eu` and `trap` commands, along with Oracle SQL*Plus `WHENEVER SQLERROR`, provide specific error handling semantics. These will be replaced by BigQuery's `BEGIN...EXCEPTION...END` blocks and explicit error handling within stored procedures. Risk: Behavioral differences in error propagation or recovery that need careful testing.
-   **UC4 Orchestration:** The job is currently invoked by UC4. While the script logic is migrated to BigQuery, the overall job scheduling and dependency management previously handled by UC4 need to be recreated in a new orchestration tool like Cloud Composer. Risk: Incomplete mapping of UC4 job dependencies or scheduling complexities.
-   **Data Freshness:** The SQL script determines `v_datum` from `dwtk_meldungen`. Ensuring that this `dwtk_meldungen` table (or its BigQuery equivalent) is up-to-date and accurately reflects the state of upstream jobs is critical.
