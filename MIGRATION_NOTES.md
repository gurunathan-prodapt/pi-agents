# MIGRATION_NOTES.md

## 1. Summary

This document details the migration of the KornShell wrapper script `vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/r_ausd_v_ta_vvl_upgrade.ksh`. This script was responsible for orchestrating a contract data reconciliation job for the `ta_vvl_upgrade` table, including environment setup, parameter parsing, logging, and invoking a core "kernel" script.

The job has been migrated to the Google Cloud Platform, specifically utilizing BigQuery's scripting capabilities. The legacy KornShell orchestration logic has been re-implemented as a BigQuery Stored Procedure, and its custom logging and status tracking mechanisms have been replaced by dedicated BigQuery tables. The core data reconciliation logic, originally in `k_ausd_v_ta_vvl_upgrade.ksh`, is now expected to reside in a separate BigQuery Stored Procedure.

## 2. Generated Artifacts

The migration process generated the following BigQuery artifacts:

*   **`ddl/job_log.sql`**
    *   **Role:** This DDL script creates the `job_log` table in BigQuery. This table serves as the central repository for all log messages generated by the migrated job, replacing the custom `DWMSG_*` logging framework and filesystem log files. It captures timestamps, job identifiers, severity levels, and detailed messages.
*   **`ddl/job_status.sql`**
    *   **Role:** This DDL script creates the `job_status` table in BigQuery. This table tracks the overall execution status of each job run, including job number, identifier, current status (e.g., 'RUNNING', 'OK', 'ERROR'), relevant `stichtag`, and last update timestamp. It replaces the status tracking functionality of the legacy `DWMSG_*` utilities.
*   **`procedures/r_ausd_v_ta_vvl_upgrade_bq.sql`**
    *   **Role:** This BigQuery Stored Procedure is the direct replacement for the original `r_ausd_v_ta_vvl_upgrade.ksh` KornShell wrapper script. It handles parameter parsing, job metadata initialization, logging to `job_log`, status updates in `job_status`, and orchestrates the execution of the core data reconciliation logic by calling the `k_ausd_v_ta_vvl_upgrade` BigQuery Stored Procedure. It also incorporates robust error handling using BigQuery's `BEGIN...EXCEPTION...END` block.
*   **`procedures/k_ausd_v_ta_vvl_upgrade.sql`**
    *   **Role:** This is a placeholder BigQuery Stored Procedure. It is intended to house the migrated core data reconciliation logic that was originally contained within `k_ausd_v_ta_vvl_upgrade.ksh`. The `r_ausd_v_ta_vvl_upgrade_bq` procedure calls this procedure to perform the actual business logic. **Note:** This procedure currently contains only a placeholder message and requires full implementation based on the original kernel script's logic.

## 3. Key Design Decisions

*   **BigQuery Scripting for Orchestration:** The decision to use BigQuery SQL scripts/stored procedures for orchestration directly replaces the KornShell environment. This leverages BigQuery's native capabilities, simplifies dependency management (no external shell utilities), and aligns with a cloud-native data platform strategy.
*   **Centralized Logging and Status Tables:** The custom `DWMSG_*` logging and error handling framework, which wrote to filesystem logs and potentially custom status files, has been replaced by two dedicated BigQuery tables (`job_log` and `job_status`). This provides a structured, queryable, and centralized mechanism for monitoring job execution and status, improving observability and debugging.
*   **BigQuery `BEGIN...EXCEPTION...END` for Error Handling:** The KornShell `trap` mechanism for signal handling and error capture has been translated into BigQuery's `BEGIN...EXCEPTION...END` blocks. This provides structured error handling within the SQL context, allowing for graceful failure, logging of errors, and status updates.
*   **Procedure Parameters for Configuration:** Environment variables and sourced init files (`. $HOME/.dw_init`) are replaced by BigQuery Stored Procedure parameters and `DECLARE` variables. This makes the job's configuration explicit and manageable within the BigQuery environment.
*   **`CALL` Statement for Kernel Script Invocation:** The execution of the core kernel script (`k_ausd_v_ta_vvl_upgrade.ksh`) via shell command has been replaced by a BigQuery `CALL` statement to a corresponding BigQuery Stored Procedure (`k_ausd_v_ta_vvl_upgrade`). This maintains the separation of orchestration and core logic while keeping the entire workflow within BigQuery.
*   **Trade-offs:**
    *   **Loss of Direct Filesystem Access:** The direct ability to write to local log files is replaced by structured logging in BigQuery tables. While this enhances queryability, it changes the immediate access pattern for logs.
    *   **Dependency on Kernel Script Migration:** The wrapper's functionality is heavily dependent on the successful and accurate migration of the `k_ausd_v_ta_vvl_upgrade.ksh` script into its BigQuery stored procedure counterpart. This is a critical path item.
    *   **Complexity of `DWMSG_*` Mapping:** While the general logging and status concepts are mapped, the exact nuances and specific functions of the `DWMSG_*` utilities required careful analysis to ensure full functional parity.

## 4. Manual Steps Before Go-Live

Before the migrated job can be put into production, the following manual steps must be completed:

1.  **BigQuery Dataset Creation:** Ensure the target BigQuery dataset (`project.dataset` in the generated code) exists. If not, create it:
    ```bash
    bq mk --dataset --default_table_expiration 36000 `project:dataset`
    ```
2.  **IAM Permissions:** Grant appropriate IAM roles to the service account or user that will execute these BigQuery procedures. This typically includes:
    *   `BigQuery Data Editor` (or `BigQuery User` if only executing and not modifying data in other tables) on the target dataset.
    *   `BigQuery Job User` at the project level to run BigQuery jobs.
3.  **Deploy DDLs:** Execute the `ddl/job_log.sql` and `ddl/job_status.sql` scripts to create the necessary logging and status tables.
    ```bash
    bq query --use_legacy_sql=false < ddl/job_log.sql
    bq query --use_legacy_sql=false < ddl/job_status.sql
    ```
4.  **Migrate and Deploy `k_ausd_v_ta_vvl_upgrade.sql`:**
    *   **CRITICAL:** The `procedures/k_ausd_v_ta_vvl_upgrade.sql` file is currently a placeholder. The full business logic from the original `k_ausd_v_ta_vvl_upgrade.ksh` must be accurately translated into BigQuery SQL and implemented within this stored procedure.
    *   Once implemented, deploy the stored procedure:
        ```bash
        bq query --use_legacy_sql=false < procedures/k_ausd_v_ta_vvl_upgrade.sql
        ```
5.  **Deploy `r_ausd_v_ta_vvl_upgrade_bq.sql`:**
    *   Deploy the main orchestration stored procedure:
        ```bash
        bq query --use_legacy_sql=false < procedures/r_ausd_v_ta_vvl_upgrade_bq.sql
        ```
6.  **Configuration Management:**
    *   Review the original `$HOME/.dw_init` and any other environment variables or configuration files used by the KornShell script.
    *   If any critical configuration values were present, determine if they need to be passed as parameters to `r_ausd_v_ta_vvl_upgrade_bq`, hardcoded (if static), or stored in a BigQuery configuration table.
7.  **Scheduling:** Establish a scheduling mechanism for the `r_ausd_v_ta_vvl_upgrade_bq` stored procedure. Options include:
    *   **Cloud Scheduler:** For simple time-based triggers.
    *   **Cloud Composer (Airflow):** For complex workflows, dependency management, and integration with other GCP services.
    *   **Cloud Workflows:** For orchestrating serverless tasks.

## 5. Known Gaps & Unresolved References

The following items were identified during the migration design and remain as known gaps or require further follow-up:

*   **`k_ausd_v_ta_vvl_upgrade.ksh` Content:** The full functionality, complexity, and specific data transformation logic of the original `k_ausd_v_ta_vvl_upgrade.ksh` script are unknown. Its accurate migration into the `k_ausd_v_ta_vvl_upgrade` BigQuery Stored Procedure is the most critical unresolved item and will dictate the overall success and data integrity of the migrated job.
*   **Unhandled `getopts` Parameters (`-s`, `-l`):** The original KornShell script declared parameters `-s` (stichtag) and `-l` (log level) but the provided design document did not explicitly detail their handling beyond parsing.
    *   `p_stichtag_str` is now a parameter for the BQ procedure, addressing `-s`.
    *   `p_log_level` is also a parameter, but its internal usage within `r_ausd_v_ta_vvl_upgrade_bq` is currently limited to being passed. If the original script used this to filter log messages or change logging behavior, that logic needs to be added to the BQ procedure or the `job_log` table's consumption.
*   **Environment Variables (`$HOME/.dw_init`, `BERT_DIR_ROOT`):** The exact content and usage of variables loaded from `$HOME/.dw_init` and `BERT_DIR_ROOT` were not fully cataloged. Any critical variables that influenced the original script's behavior (e.g., database connection details, file paths, specific configurations) need to be identified and mapped to BigQuery parameters, `DECLARE` variables, or potentially a BigQuery configuration table.
*   **Full `DWMSG_*` Functionality Mapping:** While the core logging and status updates are covered, the precise functionality of every `DWMSG_*` function (e.g., specific error codes, detailed message formatting, side effects) needs to be verified against the BigQuery implementation to ensure no loss of information or behavior.

A successful validation means:
*   The `r_ausd_v_ta_vvl_upgrade_bq` procedure completes without unhandled BigQuery errors.
*   The `job_log` table contains a complete and accurate sequence of events for each job run, including start, kernel script call, completion, and any informational or error messages.
*   The `job_status` table correctly reflects the final status of each job run as 'OK' for successful executions and 'ERROR' for simulated failures.
*   The `k_ausd_v_ta_vvl_upgrade` procedure (once implemented) correctly executes its intended data reconciliation logic, producing accurate results in the target tables.

## 7. Rollback Procedure

In the event that the migrated job encounters critical issues post-go-live, the following rollback procedure can be initiated:

1.  **Stop New Executions:** Immediately halt any scheduled or manual executions of the `project.dataset.r_ausd_v_ta_vvl_upgrade_bq` BigQuery Stored Procedure.
2.  **Revert Scheduling:** Re-enable the original scheduling mechanism for the legacy `r_ausd_v_ta_vvl_upgrade.ksh` KornShell script.
3.  **Verify Legacy System Functionality:** Confirm that the original KornShell script and its dependencies are fully operational and can resume processing without issues.
4.  **Data Integrity Check (if `k_ausd_v_ta_vvl_upgrade` modified data):** If the `k_ausd_v_ta_vvl_upgrade` BigQuery Stored Procedure made any data modifications to production tables, assess the impact of these changes. Depending on the nature of the changes, a data rollback or correction might be necessary. This is highly dependent on the specific logic within `k_ausd_v_ta_vvl_upgrade`.
5.  **Deactivate/Delete BigQuery Artifacts (Optional):** Once the legacy system is stable and confirmed to be running, the migrated BigQuery procedures and DDLs can be optionally deactivated or deleted to avoid accidental execution or resource consumption.
    *   `DROP PROCEDURE IF EXISTS `project.dataset.r_ausd_v_ta_vvl_upgrade_bq`;`
    *   `DROP PROCEDURE IF EXISTS `project.dataset.k_ausd_v_ta_vvl_upgrade`;`
    *   `DROP TABLE IF EXISTS `project.dataset.job_log`;`
    *   `DROP TABLE IF EXISTS `project.dataset.job_status`;`
    *   **Note:** Deleting tables will result in loss of historical log and status data. Consider archiving if needed.

The primary goal of the rollback is to quickly restore the original, stable processing environment while minimizing data impact.
