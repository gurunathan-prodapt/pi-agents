# MIGRATION_NOTES.md

## 1. Summary

This document details the migration of the KornShell wrapper script `vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/r_ausd_v_ta_barrier_zusgf.ksh`. The script, which orchestrates the execution of a core data reconciliation process for the `ta_barrier_zusgf` table, has been migrated from a Unix/Linux environment to Google Cloud's BigQuery.

The original KornShell script's functionality, including environment setup, parameter parsing, logging, and error handling, has been re-implemented as a BigQuery Stored Procedure. This new stored procedure will invoke a separate BigQuery Stored Procedure that encapsulates the core business logic previously contained in `k_ausd_v_ta_barrier_zusgf.ksh`.

**Target Platform:** Google Cloud BigQuery

## 2. Generated Artifacts

The migration process has resulted in the following BigQuery artifacts:

*   **`sql/sp/sp_vertragsdatenabgleich.sql`**:
    *   **Role:** This file contains the Data Definition Language (DDL) for the main BigQuery Stored Procedure, `my_project.my_dataset.Vertragsdatenabgleich`. This SP is the direct replacement for the original `r_ausd_v_ta_barrier_zusgf.ksh` wrapper script. It handles parameter parsing, job initialization, logging to BigQuery tables, error trapping, and the invocation of the core business logic stored procedure.
*   **`my_project.my_dataset.job_registry` (Table)**:
    *   **Role:** This table serves as a central registry for all migrated jobs. It tracks job metadata such as `job_id`, `job_name`, `start_time`, `end_time`, and `status` (e.g., 'RUNNING', 'OK', 'FAILED'). It replaces the file-based status tracking of the legacy system.
*   **`my_project.my_dataset.job_log` (Table)**:
    *   **Role:** This table stores detailed log messages generated during the execution of the stored procedure. It captures `job_id`, `log_time`, `level` (INFO, ERROR), and the `message` itself, replacing the file-based log files (`LogDatei`) of the original script.
*   **`my_project.my_dataset.job_error` (Table)**:
    *   **Role:** This table is dedicated to recording specific error details when a job fails. It stores `job_id`, `error_time`, `error_code`, and `error_message`, providing structured error reporting that was previously handled by shell error traps and `DWMSG_Fehlerbehandlung` functions.
*   **`my_project.my_dataset.k_ausd_v_ta_barrier_zusgf` (Stored Procedure - *Prerequisite*)**:
    *   **Role:** This is the BigQuery Stored Procedure that encapsulates the core business logic previously found in `k_ausd_v_ta_barrier_zusgf.ksh`. While not directly generated by this specific migration, its existence and deployment are a critical prerequisite for the `Vertragsdatenabgleich` SP to function correctly.

## 3. Key Design Decisions

The following key design decisions were made to adapt the KornShell script to the BigQuery environment:

*   **Orchestration via BigQuery Stored Procedure:** The entire wrapper logic, including environment setup, parameter handling, and error trapping, was translated into a BigQuery Stored Procedure (`Vertragsdatenabgleich`). This leverages BigQuery's procedural capabilities (`BEGIN...END`, `DECLARE`, `CALL`, `EXCEPTION WHEN ERROR THEN`) for control flow.
*   **Separation of Wrapper and Core Logic:** The original script's design, where a wrapper invoked a core script, was preserved. The `Vertragsdatenabgleich` SP acts as the wrapper, calling a separate BigQuery Stored Procedure (`k_ausd_v_ta_barrier_zusgf`) for the core business logic. This maintains modularity and allows for independent development and testing of the core process.
*   **Structured Logging to BigQuery Tables:** All file-based logging and status tracking (`LogDatei`, `DWMSG_*` functions) were replaced with `INSERT` statements into dedicated BigQuery tables (`job_registry`, `job_log`, `job_error`). This provides structured, queryable, and centralized logging, improving observability and auditing capabilities compared to scattered log files.
*   **Parameter Mapping:** Command-line arguments (`-h`, `-s`, `-l`) from `getopts` were directly mapped to input parameters (`p_h`, `p_s`, `p_l`) of the BigQuery Stored Procedure. This simplifies invocation and type safety.
*   **UUID for Job Identification:** Instead of sequential or date-based job IDs, `GENERATE_UUID()` is used to create unique `job_id` values (`v_dw_eintrags_nr`). This ensures global uniqueness and avoids potential collisions in a distributed environment.
*   **BigQuery Exception Handling:** Shell `trap` mechanisms for error handling were replaced by BigQuery's `BEGIN...EXCEPTION WHEN ERROR THEN...END;` blocks. This provides robust, structured error capture and allows for logging error details to `job_error` and signaling failure to the caller via `SIGNAL SQLSTATE`.
*   **Replacement of Shell Utilities:**
    *   `date` command replaced by `CURRENT_DATE()` and `FORMAT_DATE()`.
    *   `tee` command functionality replaced by `INSERT` statements into logging tables.
    *   Environment variables (`$HOME`, `${BERT_DIR_ROOT}`) are either replaced by explicit SP parameters, configuration tables, or hardcoded values where appropriate (e.g., `v_job_kennung`).

## 4. Manual Steps Before Go-Live

Before the `Vertragsdatenabgleich` stored procedure can be deployed and executed, the following manual steps must be completed:

1.  **Create BigQuery Dataset:**
    *   Ensure the target dataset `my_project.my_dataset` exists in your BigQuery project. If not, create it:
        ```sql
        CREATE SCHEMA IF NOT EXISTS `my_project.my_dataset`
        OPTIONS(
            location="US" -- Or your desired region
        );
        ```

2.  **Create Logging and Audit Tables:**
    *   Execute the following DDL statements to create the `job_registry`, `job_log`, and `job_error` tables:

        ```sql
        -- job_registry table
        CREATE TABLE IF NOT EXISTS `my_project.my_dataset.job_registry` (
            job_id STRING NOT NULL,
            job_name STRING NOT NULL,
            start_time TIMESTAMP NOT NULL,
            end_time TIMESTAMP,
            status STRING NOT NULL, -- e.g., 'RUNNING', 'OK', 'FAILED'
            error_message STRING,
            last_updated TIMESTAMP
        );

        -- job_log table
        CREATE TABLE IF NOT EXISTS `my_project.my_dataset.job_log` (
            job_id STRING NOT NULL,
            log_time TIMESTAMP NOT NULL,
            level STRING NOT NULL, -- e.g., 'INFO', 'WARNING', 'ERROR'
            message STRING NOT NULL
        );

        -- job_error table
        CREATE TABLE IF NOT EXISTS `my_project.my_dataset.job_error` (
            job_id STRING NOT NULL,
            error_time TIMESTAMP NOT NULL,
            error_code INT64,
            error_message STRING NOT NULL
        );
        ```

3.  **Migrate and Deploy Core Business Logic SP:**
    *   The core script `k_ausd_v_ta_barrier_zusgf.ksh` **must be migrated and deployed** as a BigQuery Stored Procedure named `my_project.my_dataset.k_ausd_v_ta_barrier_zusgf` *before* deploying `Vertragsdatenabgleich`. The wrapper SP will `CALL` this core SP. Ensure its parameters match the expected `(v_job_kennung STRING, v_dw_eintrags_nr STRING)`.

4.  **IAM Permissions:**
    *   The service account or user executing the `Vertragsdatenabgleich` stored procedure must have the following BigQuery IAM roles:
        *   `BigQuery Data Editor` on `my_project.my_dataset` (to `INSERT` into `job_registry`, `job_log`, `job_error` and `UPDATE` `job_registry`).
        *   `BigQuery Data Viewer` on `my_project.my_dataset` (if the core SP reads data).
        *   `BigQuery Job User` (to run queries and stored procedures).
        *   `BigQuery Data Editor` on any datasets/tables accessed or modified by the `k_ausd_v_ta_barrier_zusgf` core SP.

5.  **Scheduling:**
    *   Integrate the execution of `my_project.my_dataset.Vertragsdatenabgleich` into your chosen BigQuery orchestration tool (e.g., Cloud Composer, Cloud Scheduler, Dataform, or a custom solution).
    *   Example `CALL` statement for scheduling:
        ```sql

            p_h => FALSE,
        ```

## 5. Known Gaps & Unresolved References

*   **Core Script (`k_ausd_v_ta_barrier_zusgf.ksh`) Content:** The most significant gap is the actual content and complexity of the core script `k_ausd_v_ta_barrier_zusgf.ksh`. This migration assumes it can be fully translated into a BigQuery Stored Procedure. If it contains complex file system operations, external system calls (e.g., SFTP, specific databases not directly accessible by BigQuery), or non-SQL logic, its migration will require further analysis, potentially involving Cloud Functions, Dataflow, or other GCP services.
*   **Shell-specific Behaviors:** While the most critical shell constructs have been addressed, subtle differences in `trap` semantics (asynchronous vs. synchronous exception handling) or specific environment variable interactions might require fine-tuning during testing.
*   **`p_s` and `p_l` Parameter Usage:** The original KornShell script's `getopts` parsed `-s` and `-l` parameters, but the provided design document and generated code do not show these being passed down to the core `k_ausd_v_ta_barrier_zusgf` SP. If these parameters were intended for the core logic, the `CALL` statement within `Vertragsdatenabgleich` and the signature of `k_ausd_v_ta_barrier_zusgf` will need to be updated accordingly. Currently, they are accepted by the wrapper but not utilized further.

## 6. Validation

To validate the successful migration and functionality of the `Vertragsdatenabgleich` stored procedure:

1.  **Execute the Stored Procedure:**
    *   Run the stored procedure with various parameter combinations.
    *   **Success Case:**
        ```sql
        CALL `my_project.my_dataset.Vertragsdatenabgleich`(p_h => FALSE, p_s => 'test_s', p_l => 'test_l');
        ```
    *   **Usage Display Case:**
        ```sql
        CALL `my_project.my_dataset.Vertragsdatenabgleich`(p_h => TRUE, p_s => NULL, p_l => NULL);
        ```
    *   **Error Case (simulated):** To test error handling, you might temporarily modify the `k_ausd_v_ta_barrier_zusgf` SP to `RAISE` an error, or call `Vertragsdatenabgleich` with invalid parameters if such validation is added.

2.  **Check `job_registry` Table:**
    *   Query `my_project.my_dataset.job_registry` to verify the job's status.
    *   **Passing Criteria:**
        *   For successful runs, `status` should be 'OK' and `end_time` should be populated.
        *   For failed runs, `status` should be 'FAILED' and `error_message` should contain relevant details.
        *   A new entry with a unique `job_id` should appear for each execution.

3.  **Check `job_log` Table:**
    *   Query `my_project.my_dataset.job_log` filtering by the `job_id` obtained from `job_registry`.
    *   **Passing Criteria:**
        *   All expected log messages (e.g., "Job started", "Job-Nr", "JobKennung", "Stichtag Info", "Die Abarbeitung wurde ohne erkennbare Fehler beendet") should be present in chronological order.
        *   For usage display (`p_h => TRUE`), only the usage message should be logged.

4.  **Check `job_error` Table (for failed runs):**
    *   Query `my_project.my_dataset.job_error` filtering by the `job_id` of a failed run.
    *   **Passing Criteria:**
        *   An entry should exist for the failed job, containing the `error_time`, `error_code`, and `error_message` from the BigQuery exception.

5.  **Verify Core Logic Execution:**
    *   Ensure that the `k_ausd_v_ta_barrier_zusgf` stored procedure was indeed called and that its intended data transformations or reconciliation steps were performed correctly. This will involve checking the target tables or outputs of the core SP.

## 7. Rollback Procedure

In case of issues or a need to revert the migration, follow these steps:

1.  **Deactivate New BigQuery Job:**
    *   If the `Vertragsdatenabgleich` stored procedure was integrated into a scheduler (e.g., Cloud Composer, Cloud Scheduler), disable or delete the corresponding job/DAG to prevent further executions.

2.  **Delete BigQuery Stored Procedure:**
    *   Delete the migrated stored procedure from BigQuery:
        ```sql
        DROP PROCEDURE IF EXISTS `my_project.my_dataset.Vertragsdatenabgleich`;
        ```
    *   If the core SP `k_ausd_v_ta_barrier_zusgf` was also newly deployed as part of this migration, consider dropping it as well, or reverting it to a previous stable version if it's shared.

3.  **Revert to Legacy Script:**
    *   Ensure the original KornShell script `r_ausd_v_ta_barrier_zusgf.ksh` and its dependencies are available and correctly configured in the legacy environment.
    *   Re-enable or re-schedule the execution of the original KornShell script in its legacy scheduler.
