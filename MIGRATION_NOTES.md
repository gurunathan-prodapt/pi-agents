# Migration Notes: TEST.NEW_HOUSEKEEPING_JOB

This document details the migration of the operational logging and telemetry library `h_alis_meldungen.ksh` to Google BigQuery.

---

## 1. Summary

The source component `h_alis_meldungen.ksh` is a KornShell (`ksh`) library module that provides a centralized framework for operational metadata logging, job tracking, error routing, and audit telemetry. It translates local script variables and execution boundaries into transactional database updates against an Oracle package (`CCR$VS_MELDUNG`) using embedded `sqlplus` calls.

This utility has been migrated to **Google BigQuery Standard SQL Stored Procedures**. 
* **Source Component:** `vobs/dw_source/isccr/allgemein/is/bin/h_alis_meldungen.ksh`
* **Target Platform:** Google BigQuery
* **Migration Pattern:** Shell Script / PL-SQL Logging Package to BigQuery Stored Procedures and Native Logging Tables.

---

## 2. Generated Artifacts

The migration process has consolidated the shell utility functions and the underlying Oracle package APIs into a single, self-contained SQL deployment script.

| File Path | Role | Description |
| :--- | :--- | :--- |
| `ccr_metadata_dataset/procedures/h_alis_meldungen.sql` | **Target SQL Script** | Contains DDL statements to create the underlying logging tables (`MELDUNG`, `MELDUNG_LOG`), base system procedures (simulating the Oracle package), and the reusable wrapper procedures (simulating the shell module routines). |

---

## 3. Key Design Decisions

### Modularity & Encapsulation
* **Stored Procedure Mapping:** Direct PL/SQL package calls and shell functions are mapped to BigQuery `CALL` statements. This preserves the original operational signatures, allowing downstream pipelines to transition with minimal interface changes.
* **Decoupled Logging Store:** The script includes DDL to create local BigQuery tables (`MELDUNG` and `MELDUNG_LOG`) to store execution states and logs, replacing the dependency on the Oracle database instance.

### Error Handling & Parameter Validation
* **Halting Execution:** Parameter validation failures (e.g., missing entry IDs or invalid date formats) are mapped to BigQuery `ERROR()` statements. This ensures that calling scripts or orchestrators fail immediately and explicitly, matching the legacy `exit 2` behavior.
* **Safe Date Parsing:** Legacy Oracle date formats (e.g., `DD.MM.YYYY`) are dynamically translated to BigQuery standard format strings using a `CASE` statement inside `SAFE.PARSE_DATE` to prevent runtime casting crashes.

### Dynamic Calculations
* **Timezone-Aware Filenames:** Dynamic log filenames generated by local shell system calls (`date '+%Y%m%d_%H%M'`) are calculated natively inside BigQuery using `FORMAT_DATETIME` with an explicit `'Europe/Berlin'` timezone parameter to maintain parity with legacy date keys.
* **Sequence Generation:** Oracle sequence generation is simulated using a random 9-digit integer generator (`RAND()`) to ensure unique tracking IDs across concurrent runs without requiring a centralized sequence object.

## 4. Manual Steps Before Go-Live

Before executing or referencing these procedures in production, complete the following setup steps:

### Schema & Dataset Creation
1. Ensure the target BigQuery dataset (configured as `ccr_metadata_dataset` in the script) exists in your target Google Cloud project and region.
2. Execute the DDL statements in `h_alis_meldungen.sql` to create the `MELDUNG` and `MELDUNG_LOG` tables.

### IAM & Permissions
Grant the following IAM roles to the service accounts executing the pipelines (e.g., Cloud Composer/Airflow workers, Dataform service accounts):
* **`roles/bigquery.dataEditor`** on the target dataset (to write log entries).
* **`roles/bigquery.user`** on the project level (to run query jobs and execute procedures).

### Connection Strings & Environment Variables
* Replace references to the Oracle connection string `$CCR_ORAUSER` in your orchestration tool with the appropriate BigQuery connection context.
* Map the legacy local log path variable `$CCR_DIR_PROT` to a Cloud Storage (GCS) URI prefix (e.g., `gs://your-environment-log-bucket/logs`) when calling the log filename procedures.

---

## 5. Known Gaps & Unresolved References

* **Transactional Commit Semantics:** BigQuery does not support explicit PL/SQL-style `COMMIT` or `ROLLBACK` commands within these procedures. Operations are committed automatically per statement. If multi-statement transactional integrity is required for a job, the calling orchestrator must wrap the calls in a `BEGIN TRANSACTION ... COMMIT TRANSACTION` block.
* **Redesign (B4) Orchestration Alignment:** While these procedures replicate the shell-to-database logging pattern, modern GCP architectures typically leverage **Cloud Logging** or **Cloud Monitoring** for pipeline telemetry. A future redesign phase should evaluate migrating these table-based logs to native Google Cloud structured logs.

## 6. Validation

To validate the deployment and functionality of the migrated procedures, execute the following test suite in your BigQuery console:

```sql
-- 1. Initialize a tracking ID variable
DECLARE test_entry_id INT64;
DECLARE generated_log_name STRING;

-- 2. Test ID Generation
CALL `ccr_metadata_dataset.CCRMSG_ErmittleNr`(test_entry_id);
SELECT test_entry_id AS generated_id;

-- 3. Test Entry Creation
CALL `ccr_metadata_dataset.CCRMSG_ErzeugeEintrag`(
  test_entry_id, 
  'TEST_JOB_MIGRATION', 
  'test_pipeline_v1', 
  'gs://my-bucket/logs/test.log', 
  '--param1=val1'
);

-- 4. Test Auxiliary Metadata Updates
CALL `ccr_metadata_dataset.CCRMSG_SetzeStichtag`(test_entry_id, '31.12.2023', 'DD.MM.YYYY');
CALL `ccr_metadata_dataset.CCRMSG_SetzeAnzahl`(test_entry_id, 5000);
CALL `ccr_metadata_dataset.CCRMSG_SetzeZusatzinfos`(test_entry_id, 'Migration Validation Run');

-- 5. Test Log Message Routing
CALL `ccr_metadata_dataset.CCRMSG_LogInfo`(test_entry_id, 'Validation test: Info message successfully logged.');
CALL `ccr_metadata_dataset.CCRMSG_LogWarn`(test_entry_id, 'Validation test: Warning message successfully logged.');

-- 6. Test Log Filename Generation
CALL `ccr_metadata_dataset.CCRMSG_Logdateiname`(generated_log_name, test_entry_id, 'TEST_JOB_MIGRATION', 'gs://my-bucket/logs');
SELECT generated_log_name AS computed_gcs_path;

-- 7. Test Completion State
CALL `ccr_metadata_dataset.CCRMSG_Fertig`(test_entry_id);

-- 8. Verify Results in Tables
SELECT * FROM `ccr_metadata_dataset.MELDUNG` WHERE eintrags_nr = test_entry_id;
SELECT * FROM `ccr_metadata_dataset.MELDUNG_LOG` WHERE eintrags_nr = test_entry_id ORDER BY log_timestamp ASC;
```

### Definition of "Passing"
* The test script executes without compilation or runtime errors.
* The query on `MELDUNG` returns exactly one row with `status = 'SUCCESS'`, `anzahl = 5000`, and `stichtag = '2023-12-31'`.
* The query on `MELDUNG_LOG` returns the logged `INFO` and `WARNING` messages with correct timestamps.
* The computed GCS path matches the pattern: `gs://my-bucket/logs/TEST_JOB_MIGRATION_[YYYYMMDD_HHMM]_[ID].log`.

## 7. Rollback Procedure

In the event of a deployment failure or critical issue during go-live, execute the following steps to roll back:

1. **Drop Target Procedures:** Run the following commands to remove the newly deployed procedures:
   ```sql
   DROP PROCEDURE IF EXISTS `ccr_metadata_dataset.CCRMSG_ErmittleNr`;
   DROP PROCEDURE IF EXISTS `ccr_metadata_dataset.CCRMSG_ErzeugeEintrag`;
   DROP PROCEDURE IF EXISTS `ccr_metadata_dataset.CCRMSG_SetzeStichtag`;
   DROP PROCEDURE IF EXISTS `ccr_metadata_dataset.CCRMSG_SetzeAnzahl`;
   DROP PROCEDURE IF EXISTS `ccr_metadata_dataset.CCRMSG_SetzeDateiname`;
   DROP PROCEDURE IF EXISTS `ccr_metadata_dataset.CCRMSG_SetzeZusatzinfos`;
   DROP PROCEDURE IF EXISTS `ccr_metadata_dataset.CCRMSG_LogDebug`;
   DROP PROCEDURE IF EXISTS `ccr_metadata_dataset.CCRMSG_LogInfo`;
   DROP PROCEDURE IF EXISTS `ccr_metadata_dataset.CCRMSG_LogWarn`;
   DROP PROCEDURE IF EXISTS `ccr_metadata_dataset.CCRMSG_Fehler`;
   DROP PROCEDURE IF EXISTS `ccr_metadata_dataset.CCRMSG_Fertig`;
   DROP PROCEDURE IF EXISTS `ccr_metadata_dataset.CCRMSG_Logdateiname`;
   DROP PROCEDURE IF EXISTS `ccr_metadata_dataset.CCRMSG_Logdateiname_Parallel`;
   ```
2. **Retain Logging Tables (Optional):** To preserve historical execution logs generated during the cutover window, do **not** drop the `MELDUNG` and `MELDUNG_LOG` tables unless a clean-slate reset is explicitly required.
3. **Revert Orchestration:** Revert your orchestration tool (e.g., Airflow DAGs, Shell wrappers) to point back to the legacy KornShell script (`h_alis_meldungen.ksh`) and the Oracle database environment (`$CCR_ORAUSER`).
