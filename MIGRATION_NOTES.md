# MIGRATION_NOTES.md

## 1. Summary

The KornShell orchestration script `vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/r_ausd_bp_ta_bpr_opt_text.ksh` has been migrated to Google BigQuery. This migration involved translating the shell script's parameter handling, date calculation, logging, error management, and restart logic into a BigQuery Stored Procedure. Additionally, the core data processing logic, originally residing in the invoked kernel script (`k_ausd_bp_ta_bpr_opt_text.ksh`) and SQL file (`d_ausd_bp_ta_bpr_opt_text.sql`), has been integrated directly into the BigQuery Stored Procedure.

The target platform is Google BigQuery, leveraging its native Stored Procedure capabilities for orchestration and SQL for data transformation. The original DWMSG logging framework has been replaced with dedicated BigQuery audit and log tables.

## 2. Generated Artifacts

The migration produced the following BigQuery artifacts:

*   **`sql/ddl/sof_ta_bpr_opt_text.sql`**
    *   **Role:** Defines the Data Definition Language (DDL) for the target table `project.dataset.sof_ta_bpr_opt_text`. This table is intended to store the processed Basisprodukt (Base Product) options and descriptions, serving as the final output for the BERT system and FOS. It replaces the output generated by the original KornShell script and its associated SQL.

*   **`sql/ddl/job_audit.sql`**
    *   **Role:** Defines the DDL for the `project.dataset.job_audit` table. This table is used to record high-level execution details for BigQuery jobs, including start/end times, overall status (SUCCESS/FAILED), job-specific parameters (`stichtag`, `wiederanlaufwert`), and summary messages. It replaces the audit-related functionalities of the original DWMSG framework.

*   **`sql/ddl/job_log.sql`**
    *   **Role:** Defines the DDL for the `project.dataset.job_log` table. This table captures detailed log messages generated during the execution of BigQuery jobs and stored procedures, including timestamps, log levels (INFO, ERROR), and specific messages. It replaces the detailed logging functionalities of the original DWMSG framework.

*   **`sql/procedures/ausd_bp_ta_bpr_opt_text.sql`**
    *   **Role:** This is the main BigQuery Stored Procedure (`project.dataset.ausd_bp_ta_bpr_opt_text`) that encapsulates the entire migrated logic. It performs:
        *   Parameter parsing and validation (`p_stichtag_str`, `p_wiederanlaufWert`).
        *   Defaulting of `stichtag` to the current date if not provided.
        *   Error handling and logging into `job_audit` and `job_log` tables.
        *   Implementation of the restart logic: deleting records from the target table based on `cntrct_id` if `p_wiederanlaufWert` is greater than 0, or truncating the table for a full load.
        *   The core data transformation logic, which involves joining `project.dataset.sof_ta_bpr_optionen` and `project.dataset.sof_ta_bpr_beschr` and inserting the results into `project.dataset.sof_ta_bpr_opt_text`.

## 3. Key Design Decisions

*   **BigQuery Stored Procedure for Orchestration**: The shell script's orchestration logic (parameter handling, date calculations, logging, restart logic) was directly translated into a BigQuery Stored Procedure. This decision was made because the wrapper's complexity was manageable within SQL, avoiding the overhead of external services like Cloud Functions or Cloud Composer for this specific job's wrapper logic.
*   **Direct Integration of Core Logic**: The data extraction and transformation logic, originally in `k_ausd_bp_ta_bpr_opt_text.ksh` and `d_ausd_bp_ta_bpr_opt_text.sql`, was embedded directly into the BigQuery Stored Procedure. This simplifies deployment, reduces inter-component dependencies, and leverages BigQuery's native SQL processing capabilities.
*   **Dedicated BigQuery Logging and Auditing**: The custom DWMSG framework was replaced by inserts into `project.dataset.job_audit` and `project.dataset.job_log` tables. This provides a standardized, BigQuery-native approach to logging and auditing, allowing for easier monitoring and analysis of job executions.
*   **Explicit Date Handling**: The `DDMMYYYY` date format used in the source script is explicitly handled using `PARSE_DATE('%d%m%Y', ...)` in BigQuery, ensuring correct interpretation and preventing ambiguity.
*   **Restart Logic Implementation**: The restart mechanism (`p_wiederanlaufWert`) is implemented as a `DELETE` operation on the target table for records with `cntrct_id >= p_wiederanlaufWert`. For a full load (when `p_wiederanlaufWert` is 0), the target table is truncated. This directly mirrors the described behavior of the original script.
*   **Source Table Assumption**: The generated code assumes the existence of source tables `project.dataset.sof_ta_bpr_optionen` and `project.dataset.sof_ta_bpr_beschr` with columns `cntrct_id`, `bpr_id`, and `pds_description`. This was derived from the inferred core logic.


    ```bash
    bq query --use_legacy_sql=false < sql/ddl/sof_ta_bpr_opt_text.sql
    bq query --use_legacy_sql=false < sql/ddl/job_audit.sql
    bq query --use_legacy_sql=false < sql/ddl/job_log.sql
    ```

## 5. Known Gaps & Unresolved References

*   **Missing Core Filtering Logic**: The `MIGRATION DESIGN DOCUMENT` explicitly described complex filtering conditions for the kernel script (`k_ausd_bp_ta_bpr_opt_text.ksh`), including `GUELTIG_VON <= v_stichtag`, `v_stichtag < GUELTIG_BIS`, and `LADEDATUM < v_stichtag`. The generated BigQuery Stored Procedure's `INSERT ... SELECT` statement *does not include these date-based filtering conditions*. It only performs a simple `INNER JOIN` between the two source tables. This is a significant functional gap and requires immediate follow-up to ensure the migrated job produces the correct dataset.
*   **Source Table DDLs**: The DDLs for the source tables (`project.dataset.sof_ta_bpr_optionen` and `project.dataset.sof_ta_bpr_beschr`) were not provided as part of this migration and are assumed to exist with the necessary columns (`cntrct_id`, `bpr_id`, `pds_description`). Their schema and data types should be verified against the original DWH sources.
*   **UC4 Orchestration Migration**: While mentioned, the detailed plan for migrating the UC4 job to Cloud Composer or BigQuery Scheduled Queries is outside the scope of this document. This remains a separate, dependent task.
*   **Error Handling Granularity**: The BigQuery Stored Procedure provides general error messages. If the original DWMSG framework had highly specific error codes or detailed contextual messages that are critical for operational support, further refinement of the BigQuery error handling might be necessary.
*   **Performance of `DELETE` for Restart**: For extremely large target tables, the `DELETE` operation in the restart logic might be performance-intensive. While it mirrors the original behavior, a `MERGE` statement could offer better performance for upsert-like scenarios if the original intent was more nuanced than a simple delete-and-insert.

## 7. Rollback Procedure

In case of critical issues or failure during go-live, the following rollback procedure should be followed:

1.  **Stop New Orchestration**: Immediately pause or disable the new BigQuery Scheduled Query or Cloud Composer DAG that invokes `project.dataset.ausd_bp_ta_bpr_opt_text`.
2.  **Re-enable Legacy Job**: Re-enable the original UC4 job (`DW.BERT_AUSD_BP_TA_BPR_OPT_TEXT.xml`) to resume execution of `r_ausd_bp_ta_bpr_opt_text.ksh`.
3.  **Data Restoration (if necessary)**:
    *   If `project.dataset.sof_ta_bpr_opt_text` was truncated or modified by the new procedure and its data is critical for downstream systems, restore it to its state prior to the migration attempt. This might involve:
        *   Restoring from a BigQuery table snapshot or a time-travel query if the changes were recent.
        *   Loading data from a backup.
        *   Running the original legacy job to regenerate the data.
    *   The `job_audit` and `job_log` tables are append-only and typically do not require rollback, but their data can be ignored or archived.
4.  **Remove BigQuery Artifacts (Optional)**: If the rollback is permanent or for a significant period, consider dropping the BigQuery Stored Procedure and the newly created DDLs (`sof_ta_bpr_opt_text`, `job_audit`, `job_log`) to avoid confusion or accidental execution.
    ```sql

    -- DROP TABLE IF EXISTS `project.dataset.job_audit`;
    ```

5.  **Root Cause Analysis**: Investigate the reason for the rollback and address the identified issues before attempting re-migration.
