# MIGRATION_NOTES.md

## 1. Summary

This document outlines the migration of the legacy job `vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/k_ausd_bp_ta_bcp_msisdn.ksh`. The original Korn Shell script, likely responsible for data preparation or bulk copy operations related to "PoolBasisprodukt" and MSISDN data, has been migrated to a modern cloud-native architecture.

The target platform for this migration is Google Cloud Platform (GCP), utilizing Apache Airflow for workflow orchestration and Google BigQuery for data processing and storage.

## 2. Generated Artifacts

The migration process generated the following file:

*   **`dags/d_ausd_bp_ta_bcp_msisdn.py`**
    *   **Role**: This is an Apache Airflow Directed Acyclic Graph (DAG) definition file. It orchestrates the execution of data processing tasks in BigQuery. Specifically, it dynamically constructs a BigQuery SQL statement based on runtime parameters and executes it to process and load data into the `PoolBasisprodukt` table.

## 3. Key Design Decisions

The following key design decisions were made during the migration:

*   **Apache Airflow for Orchestration**: Airflow was chosen as the primary orchestration tool due to its robust scheduling capabilities, monitoring features, retry mechanisms, and native integration with GCP services. This replaces the scheduling and execution logic previously handled by the KSH script.
*   **Google BigQuery for Data Processing and Storage**: BigQuery was selected for its serverless, highly scalable, and cost-effective data warehousing capabilities. All data transformation logic is intended to be translated into standard SQL, leveraging BigQuery's analytical power.
*   **Dynamic SQL Generation via PythonOperator**: The DAG uses a `PythonOperator` (`build_sql`) to dynamically construct the BigQuery SQL query at runtime. This allows for flexible parameterization (e.g., `p_JobKennung`, `p_Stichtag`) to be passed from Airflow DAG run configurations directly into the SQL, enhancing reusability and adaptability.
*   **Single BigQueryExecuteQueryOperator**: The entire data processing logic for the `PoolBasisprodukt` table is encapsulated within a single BigQuery SQL statement executed by one `BigQueryExecuteQueryOperator`. This simplifies the DAG structure, minimizes task overhead, and allows BigQuery to optimize the end-to-end query execution.
*   **Parameterization for Flexibility**: The DAG is designed to accept key parameters (e.g., `p_JobKennung`, `p_EintragsNr`, `p_Stichtag`) from the Airflow DAG run configuration. This makes the DAG highly configurable and adaptable to different execution contexts or historical data processing needs.
*   **Idempotent Table Creation**: The BigQuery SQL includes `CREATE TABLE IF NOT EXISTS` for the target `PoolBasisprodukt` table, ensuring that the table is created only if it doesn't already exist, making the DAG more resilient to initial runs or schema changes.
*   **Append-Only Write Disposition**: The `write_disposition="WRITE_APPEND"` is used, meaning new data generated by each DAG run will be appended to the `PoolBasisprodukt` table. This assumes the underlying SQL logic handles potential duplicates if idempotency for specific runs is required.
*   **Airflow Variables for Environment Configuration**: Critical environment-specific values (GCP project, BigQuery datasets, location) are referenced using Airflow Variables (`var.value.gcp_project`, `var.value.bq_dataset`, etc.). This promotes environment-agnostic DAG deployment and simplifies configuration management.

## 4. Manual Steps Before Go-Live

Before deploying and running the migrated job in a production environment, the following manual steps must be completed:

1.  **BigQuery Dataset Creation**:
    *   Ensure the target BigQuery dataset (`{{ var.value.bq_dataset }}`) exists in your GCP project.
    *   Ensure the source BigQuery dataset (`{{ var.value.source_dataset }}`) exists and contains the `source_table` (see Known Gaps).
2.  **Airflow Variables Configuration**:
    *   Set the following Airflow Variables in your Airflow environment (Admin -> Variables):
        *   `gcp_project`: Your GCP Project ID (e.g., `your-gcp-project-id`).
        *   `bq_dataset`: The BigQuery dataset where the `PoolBasisprodukt` table will reside (e.g., `data_warehouse`).
        *   `source_dataset`: The BigQuery dataset containing the `source_table` (e.g., `raw_data`).
        *   `bq_location`: The BigQuery dataset location (e.g., `EU`, `US`).
3.  **GCP IAM Permissions**:
    *   The Airflow service account (associated with the `google_cloud_default` connection) must have the necessary IAM roles and permissions in GCP:
        *   `BigQuery Data Editor` on the `{{ var.value.bq_dataset }}` dataset to create/write to `PoolBasisprodukt`.
        *   `BigQuery Data Viewer` on the `{{ var.value.source_dataset }}` dataset to read from `source_table`.
        *   `BigQuery Job User` to run BigQuery jobs.
4.  **Source Table Definition**:
    *   The `source_table` referenced in the BigQuery SQL must exist in the `{{ var.value.source_dataset }}` and its schema must align with the expectations of the transformation logic (once implemented).
5.  **Scheduling Configuration**:
    *   The DAG is currently configured with `schedule_interval=None`, meaning it will only run when manually triggered or via an external trigger. If scheduled execution is required, update the `schedule_interval` parameter in the DAG file.

## 5. Known Gaps & Unresolved References

The following items have been identified as gaps or require further attention/redesign:

1.  **Core Transformation Logic Placeholder**: The most significant gap is that the BigQuery SQL contains a placeholder for the actual transformation logic:
    ```sql
    FROM (
        -- Replace this source query with the actual BigQuery transformation logic
        SELECT
            *
        FROM `{{{{ var.value.gcp_project }}}}.{{{{ var.value.source_dataset }}}}.source_table`
        WHERE 1 = 1
          AND DATE(_PARTITIONTIME) BETWEEN DATE_SUB(PARSE_DATE('%d%m%Y', '{p_stichtag}'), INTERVAL 1 DAY)
                                      AND PARSE_DATE('%d%m%Y', '{p_stichtag}')
    )
    ```
    The detailed business logic from the original `k_ausd_bp_ta_bcp_msisdn.ksh` script that processes data and prepares it for the `PoolBasisprodukt` table has *not yet been translated* into BigQuery SQL. This requires a thorough analysis of the legacy script.
2.  **`source_table` Schema and Content**: The exact schema, data types, and content of the `source_table` are unknown. This table needs to be identified, potentially migrated, and its structure understood to correctly implement the transformation logic.
3.  **Idempotency for `WRITE_APPEND`**: With `write_disposition="WRITE_APPEND"`, re-running the DAG with the same parameters will append duplicate records to `PoolBasisprodukt`. If idempotency (ensuring the same output regardless of how many times it's run for the same input) is a requirement, the BigQuery SQL needs to be modified to handle this (e.g., using `MERGE` statements, or `DELETE` + `INSERT` based on a unique key and `p_Stichtag`).
4.  **Error Handling and Logging**: While Airflow provides basic task logging, any specific custom error handling, alerting, or detailed logging mechanisms present in the original KSH script may need to be explicitly replicated or enhanced within the BigQuery SQL or Airflow tasks.
5.  **Original KSH Script Functionality**: A complete understanding of all operations performed by `k_ausd_bp_ta_bcp_msisdn.ksh` (e.g., specific BCP commands, file manipulations, external system interactions) is required to ensure all functionalities are covered in the BigQuery migration.

## 7. Rollback Procedure

In case of issues or unexpected behavior after deployment, follow these steps to roll back to the previous state:

1.  **Deactivate/Delete Airflow DAG**:
    *   In the Airflow UI, set the `d_ausd_bp_ta_bcp_msisdn` DAG to "Off" (unpause).
    *   If necessary, delete the DAG file from the Airflow DAGs folder to prevent accidental re-deployment.
2.  **Revert BigQuery Data (if necessary)**:
    *   If incorrect data was written to `PoolBasisprodukt`, choose one of the following options:
        *   **Delete specific rows**: If the inserted rows can be uniquely identified (e.g., by `created_at` timestamp, `job_kennung`, `stichtag`), execute a `DELETE` statement in BigQuery.
        *   **Time Travel**: Utilize BigQuery's time travel feature to restore the `PoolBasisprodukt` table to a state before the problematic DAG run. This is typically available for up to 7 days.
        *   **Drop and Recreate**: If the impact is contained and the table can be easily recreated, drop the `PoolBasisprodukt` table. The DAG will recreate it on its next successful run (after issues are resolved).
3.  **Resume Legacy Job**:
    *   Re-enable or restart the original `vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/k_ausd_bp_ta_bcp_msisdn.ksh` job in its legacy environment.
4.  **Clean Up Airflow Variables (Optional)**:
    *   If the migration is completely abandoned, remove the Airflow Variables (`gcp_project`, `bq_dataset`, `source_dataset`, `bq_location`) that were specifically created for this DAG.
