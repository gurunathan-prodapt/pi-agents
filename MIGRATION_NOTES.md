# MIGRATION_NOTES.md

## 1. Summary

This document outlines the migration of the KornShell wrapper script `r_ausd_bp_ta_bpr_beschr.ksh` from a legacy Unix environment to Google BigQuery and Cloud Composer. The original script served as an ETL job orchestrator, responsible for parameter parsing, environment setup, logging, error handling, and invoking a core data processing script (`k_ausd_bp_ta_bpr_beschr.ksh`). Its purpose was the initial provisioning of selected base products for the BERT system, extracting contract cache data from the Data Warehouse (DWH) for the Forderungsscoring (FOS) system, including a restart mechanism.

The migration transforms the orchestrational and core data processing logic into a BigQuery Stored Procedure (`project.dataset.ausd_bp_ta_bpr_beschr`). The scheduling and execution management are handled by an Apache Airflow DAG deployed on Cloud Composer. This shift centralizes the ETL process within Google Cloud's data warehousing and orchestration services.

This table is used to store high-level metadata for each job execution, including `job_id`, `job_name`, `start_time`, `end_time`, `status`, `parameters`, and `error_message`. It replaces the implicit job status tracking and summary logging of the original shell script.
*   **`ddl/project.dataset.job_log.sql`**
    *   **Role**: Defines the schema for the `job_log` table in BigQuery. This table captures detailed, step-by-step log messages during job execution, including `job_id`, `log_timestamp`, `log_level`, and `message`. It replaces the filesystem-based log files (`>> $LogDatei`) generated by the original shell script.
*   **`ddl/project.dataset.ta_vertrag_cache.sql`**
    *   **Role**: Defines the assumed schema for the source table `ta_vertrag_cache` in BigQuery. This table is expected to hold the contract cache data from the DWH, which the job processes. *   **`ddl/project.dataset.fos_tabelle.sql`**
    *   **Role**: Defines the assumed schema for the target table `fos_tabelle` in BigQuery. This table receives the processed data for the FOS system. The schema is inferred from the migration design document and needs verification against the actual `k_ausd_bp_ta_bpr_beschr.ksh` content.
*   **`stored_procedures/project.dataset.ausd_bp_ta_bpr_beschr.sql`**
    *   **Role**: This is the core BigQuery Stored Procedure that encapsulates the entire logic of the original KornShell script. It handles:
        *   Parameter parsing and defaulting (`p_stichtag_string`, `p_wiederanlaufWert`).
        *   Date validation and conversion.
        *   Logging to `job_audit` and `job_log` tables.
        *   Error handling using `EXCEPTION WHEN ERROR`.
        *   The core data processing logic (DELETE and INSERT statements) derived from the described functionality of `k_ausd_bp_ta_bpr_beschr.ksh`, including the restart mechanism.
*   **`dags/r_ausd_bp_ta_bpr_beschr_dag.py`**
    *   **Role**: An Apache Airflow DAG (Python script) designed to orchestrate and schedule the execution of the BigQuery Stored Procedure. It defines the job's schedule, parameters, and the task to call the `ausd_bp_ta_bpr_beschr` stored procedure, replacing the legacy shell-based scheduling.

## 3. Key design decisions

1.  **Consolidated Logic into BigQuery Stored Procedure**:
    *   **Decision**: The KornShell wrapper (`r_ausd_bp_ta_bpr_beschr.ksh`) and its invoked core script (`k_ausd_bp_ta_bpr_beschr.ksh`) are combined into a single BigQuery Stored Procedure.
    *   **Rationale**: This centralizes the entire ETL logic within BigQuery, leveraging its native capabilities for data processing, parameter handling, and error management. It eliminates the need for separate shell scripts and their execution environments.
    *   **Trade-offs**: Increases the complexity of the SQL code within the stored procedure, as it now includes orchestrational logic (parameter validation, logging) in addition to data transformation. Requires careful translation of shell constructs to BigQuery SQL.

2.  **Structured Logging and Auditing in BigQuery Tables**:
    *   **Decision**: Replaced filesystem-based log files with dedicated BigQuery tables (`job_audit`, `job_log`).
    *   **Rationale**: Provides structured, queryable, and centralized logging and auditing capabilities. This allows for easier monitoring, debugging, and historical analysis of job runs compared to parsing text files.
    *   **Trade-offs**: Adds overhead of `INSERT` statements for each log entry, potentially impacting performance for very verbose logging. Requires DDL deployment for these tables.

3.  **Cloud Composer (Apache Airflow) for Orchestration**:
    *   **Decision**: Utilized Cloud Composer (Airflow) to schedule and trigger the BigQuery Stored Procedure.
    *   **Rationale**: Airflow offers robust scheduling, dependency management, monitoring, and parameter passing capabilities, which are superior to traditional shell-based cron jobs. It integrates seamlessly with BigQuery.
    *   **Trade-offs**: Introduces a new technology stack (Python, Airflow) and requires managing an Airflow environment.

4.  **Native BigQuery Constructs for Shell Functionality**:
    *   **Decision**: Translated shell parameter parsing (`getopts`), date utilities (`h_alis_date.ksh`), and error handling (`trap`) into BigQuery Stored Procedure parameters, native date functions (`PARSE_DATE`, `CURRENT_DATE`), and `EXCEPTION WHEN ERROR` blocks, respectively.
    *   **Rationale**: Leverages BigQuery's built-in features, reducing external dependencies and simplifying the overall architecture.
    *   **Trade-offs**: Requires understanding and adapting to BigQuery's specific SQL dialect and error handling mechanisms.

5.  **Direct Integration of Restart Logic**:
    *   **Decision**: The `p_wiederanlaufWert` (restart value) and associated conditional `DELETE` logic are directly implemented within the BigQuery Stored Procedure's SQL.
    *   **Rationale**: Maintains the original job's restartability and idempotency within the new BigQuery environment, ensuring consistent data processing.
    *   **Trade-offs**: The exact interpretation of the `DELETE` condition for `v_final_wiederanlaufWert = 0` (full table clear vs. specific partition/date clear) required an assumption based on the design document and needs verification.

## 4. Manual steps before go-live

Before the migrated job can go live, the following manual steps must be completed:

1.  **BigQuery Dataset Creation**:
    *   Ensure the BigQuery dataset `project.dataset` (replace `project` and `dataset` with actual project ID and dataset name) exists. If not, create it.
2.  **DDL Deployment**:
    *   Execute the DDL scripts for the audit and log tables:
        *   `ddl/project.dataset.job_audit.sql`
        *   `ddl/project.dataset.job_log.sql`
    *   **Crucial**: Review and deploy the DDLs for the source and target data tables:
        *   `ddl/project.dataset.ta_vertrag_cache.sql`
        *   `ddl/project.dataset.fos_tabelle.sql`
        *   **Action Required**: The schemas for `ta_vertrag_cache` and `fos_tabelle` are *assumed* based on the design document. A thorough analysis of the original `k_ausd_bp_ta_bpr_beschr.ksh` script is required to accurately define the columns, data types, and any partitioning/clustering strategies for these tables. Adjust the DDLs accordingly before deployment.
3.  **BigQuery Stored Procedure Deployment**:
    *   Deploy the `stored_procedures/project.dataset.ausd_bp_ta_bpr_beschr.sql` script to create the BigQuery Stored Procedure.
4.  **IAM/Permissions Configuration**:
    *   **BigQuery Service Account**: Create or identify a Google Cloud service account that will be used by Cloud Composer to interact with BigQuery. This service account requires:
        *   `BigQuery Data Editor` role on `project.dataset` (to insert/update `job_audit`, `job_log`, `fos_tabelle`).
        *   `BigQuery Data Viewer` role on `project.dataset` (to read `ta_vertrag_cache`).
        *   `BigQuery Job User` role on the project (to run BigQuery jobs, including stored procedures).
    *   **Cloud Composer Environment**: Ensure the Cloud Composer environment's service account has the necessary permissions to execute BigQuery jobs using the dedicated BigQuery service account (if different).
5.  **Airflow Connection Setup**:
    *   In your Cloud Composer (Airflow) environment, ensure the `google_cloud_default` connection is correctly configured and points to the GCP project where BigQuery resources reside. If a specific service account key is needed, configure it within this connection.
6.  **Airflow DAG Deployment**:
    *   Upload the `dags/r_ausd_bp_ta_bpr_beschr_dag.py` file to the DAGs folder of your Cloud Composer environment.
7.  **Scheduling Configuration**:
    *   Adjust the `schedule` parameter in the Airflow DAG (`dags/r_ausd_bp_ta_bpr_beschr_dag.py`) to match the desired execution frequency of the original legacy job.
8.  **Secrets Management (if applicable)**:
    *   While no explicit secrets were identified in the provided context, if the original `k_ausd_bp_ta_bpr_beschr.ksh` script accessed any sensitive credentials (e.g., database passwords), these must be securely stored in Google Secret Manager and accessed by the BigQuery Stored Procedure or Airflow DAG.

## 5. Known gaps & unresolved references

The following items are identified as gaps or require further investigation and resolution:

1.  **Core Logic of `k_ausd_bp_ta_bpr_beschr.ksh`**:
    *   **Gap**: The actual SQL logic, table names, column names, and specific filtering/transformation rules within the original `k_ausd_bp_ta_bpr_beschr.ksh` script were *not available* for direct analysis. The generated BigQuery Stored Procedure's core data processing logic (DELETE and INSERT statements) is based on assumptions derived from the migration design document's high-level description.
    *   **Action Required**: A detailed analysis of `k_ausd_bp_ta_bpr_beschr.ksh` is **critical**. The generated SQL for `INSERT` and `DELETE` operations, including column mappings, `WHERE` clauses (especially for `Gueltig_von`, `Gueltig_bis`, `LADEDATUM`, `FOSHoleLadedatum`, and `DWH_VERTRAG_ID`), and any other transformations (e.g., `FOS_ATTRIBUTE_1`, `FOS_PROVISION_VALUE`) must be verified and adjusted to precisely match the legacy behavior.
2.  **Source and Target Table Schemas (`ta_vertrag_cache`, `fos_tabelle`)**:
    *   **Gap**: The DDLs for `project.dataset.ta_vertrag_cache` and `project.dataset.fos_tabelle` are placeholders with inferred columns.
    *   **Action Required**: These schemas must be fully defined based on the actual data structures used by `k_ausd_bp_ta_bpr_beschr.ksh`. This includes all relevant columns, their precise data types, nullability constraints, and potential partitioning/clustering keys for performance optimization in BigQuery.
3.  **`FOSHoleLadedatum` Logic**:
    *   **Gap**: The condition `tvc.FOSHoleLadedatum IS NULL` in the `WHERE` clause is an example based on the design document's phrasing "if FOSHoleLadedatum was active". The exact logic for how `FOSHoleLadedatum` influences data selection needs to be confirmed.
    *   **Action Required**: Verify the precise filtering logic related to `FOSHoleLadedatum` from the original script.
4.  **`DWH_VERTRAG_ID` Data Type**:
    *   **Gap**: The `CAST(tvc.DWH_VERTRAG_ID AS INT64)` in the restart logic assumes `DWH_VERTRAG_ID` can be safely cast to an integer for comparison with `v_final_wiederanlaufWert`.
    *   **Action Required**: Confirm the actual data type of `DWH_VERTRAG_ID` in the source system and ensure the comparison logic is robust for its type. If it's a string that can contain non-numeric characters, the comparison logic needs adjustment.
5.  **Restart `DELETE` Scope**:
    *   **Gap**: The `DELETE FROM project.dataset.fos_tabelle WHERE TRUE;` statement for `v_final_wiederanlaufWert = 0` implies a full table clear. While this aligns with "deletion of already provisioned table content when no active, uncollected contract cache exists" for a full refresh, it might be too broad if the original script only cleared specific partitions or date ranges.
    *   **Action Required**: Confirm the exact scope of the `DELETE` operation in the legacy script when a full refresh is triggered. Adjust the `WHERE` clause in the BigQuery `DELETE` statement if it needs to be more granular (e.g., `WHERE FOS_PROVISION_DATE = v_stichtag`).
6.  **Complexity of Helper Scripts**:
    *   **Gap**: The content of helper scripts like `f_alis_msgerr.ksh`, `h_alis_parameter.ksh`, `h_alis_date.ksh` was not fully analyzed. While basic replacements were made, any complex business logic embedded within these helpers might require specific BigQuery UDFs or additional logic within the stored procedure.
    *   **Action Required**: Review these helper scripts for any non-trivial logic that might not have been fully captured by the migration tool's inference.

## 6. Validation

Validation of the migrated job involves several steps to ensure functional equivalence, data integrity, and performance.

1.  **Unit Testing of BigQuery Stored Procedure**:
    *   **How to run**: Execute the `project.dataset.ausd_bp_ta_bpr_beschr` stored procedure directly in BigQuery with various input parameters.
        *   Test with valid `p_stichtag_string` (e.g., '01012023') and `p_wiederanlaufWert` (e.g., 0, 1000).
        *   Test with `p_stichtag_string` as `NULL` or empty string (should default to `CURRENT_DATE()`).
        *   Test with `p_wiederanlaufWert` as `NULL` (should default to 0).
        *   Test with invalid `p_stichtag_string` (e.g., '99999999') to verify error handling.
        *   Test with an empty source table (`ta_vertrag_cache`).
        *   Test with data that should trigger the `DELETE` logic (`p_wiederanlaufWert = 0`).
    *   **"Passing" means**:
        *   The procedure completes without unhandled errors.
        *   For valid inputs, data is correctly inserted into `project.dataset.fos_tabelle` according to the expected transformation logic.
        *   The `job_audit` and `job_log` tables are populated with correct status, parameters, and detailed messages.
        *   Error conditions are gracefully handled, and `job_audit` reflects an 'ERROR' status with an appropriate message.

2.  **Data Validation (Functional Equivalence)**:
    *   **How to run**:
        1.  Select a representative set of historical `Stichtag` and `Wiederanlaufwert` combinations from the legacy system.
        2.  Run the legacy `r_ausd_bp_ta_bpr_beschr.ksh` script for these combinations, capturing its output in `fos_tabelle` (or its equivalent).
        3.  Run the migrated Airflow DAG (or directly the BigQuery SP) with the *exact same* input parameters.
        4.  Compare the data in the BigQuery `project.dataset.fos_tabelle` with the output from the legacy system.
    *   **"Passing" means**:
        *   Row counts in `project.dataset.fos_tabelle` match the legacy output.
        *   All column values in `project.dataset.fos_tabelle` are identical to the legacy output for corresponding records.
        *   Data types and formats in BigQuery match the expected output.
        *   The restart mechanism (conditional `DELETE` and `DWH_VERTRAG_ID` filtering) produces identical results to the legacy system.

3.  **Orchestration Validation (Airflow DAG)**:
    *   **How to run**: Trigger the `r_ausd_bp_ta_bpr_beschr_dag` in Cloud Composer manually and observe its execution.
    *   **"Passing" means**:
        *   The DAG runs successfully, and all tasks complete.
        *   The `call_bigquery_sp` task successfully invokes the BigQuery Stored Procedure.
        *   Airflow logs show successful execution and parameter passing.

4.  **Performance and Resource Utilization**:
    *   **How to run**: Monitor BigQuery job execution times and slot consumption for the stored procedure. Compare against legacy script execution times (if available).
    *   **"Passing" means**:
        *   Job completes within acceptable timeframes.
        *   BigQuery resource consumption (slots) is within expected limits.

## 7. Rollback procedure

In case of issues or failures after deploying the migrated job, follow these steps to roll back to the legacy system:

1.  **Immediate Action (if failure detected quickly)**:
    *   **Disable New Job**: Immediately pause or disable the `r_ausd_bp_ta_bpr_beschr_dag` in Cloud Composer to prevent further executions of the migrated job.
    *   **Re-enable Legacy Job**: Re-enable the original `r_ausd_bp_ta_bpr_beschr.ksh` script and its legacy scheduling mechanism (e.g., cron job).

2.  **Data Integrity Check and Restoration**:
    *   **Assess Impact**: Determine the extent of data corruption or incorrect data generated by the migrated job in `project.dataset.fos_tabelle`.
    *   **Restore Data**:
        *   If `project.dataset.fos_tabelle` was significantly altered or corrupted, restore it from the most recent valid backup.
        *   Alternatively, if the legacy job can safely re-process and overwrite the affected data, run the legacy `r_ausd_bp_ta_bpr_beschr.ksh` script with the appropriate parameters to correct the data in the target system.
    *   **Audit/Log Tables**: The `job_audit` and `job_log` tables are append-only and typically do not require rollback, as they record the history of job runs, including failures.

3.  **Revert Deployment**:
    *   **BigQuery Stored Procedure**: If necessary, revert the BigQuery Stored Procedure to a previous, known-good version, or drop it if it's causing issues and the legacy system is fully operational.
    *   **Airflow DAG**: Remove or revert the `dags/r_ausd_bp_ta_bpr_beschr_dag.py` file from the Cloud Composer DAGs folder.

4.  **Root Cause Analysis**:
    *   Analyze the `job_audit` and `job_log` tables in BigQuery, along with Cloud Composer logs, to identify the root cause of the failure.
    *   Review the generated code, design decisions, and manual steps for any discrepancies or errors.

5.  **Re-plan and Re-deploy**:
    *   Once the root cause is identified and a fix is implemented, update the BigQuery Stored Procedure and/or Airflow DAG.
    *   Repeat the validation steps before attempting another go-live.
