# MIGRATION_NOTES.md: EXIS_SD_APT_NNA_DATA

## 1. Summary

This document details the migration of the `EXIS_SD_APT_NNA_DATA` job, a legacy UC4 (Automic) UNIX job responsible for exporting telephone system master data. The original job generated a compressed CSV file (`DWHM_APT_NNA_Daten_<yyyymmddhhmmss>.csv.gz`) and distributed it to a target system.

The job has been re-platformed to Google Cloud Platform (GCP). The new architecture leverages:
*   **Cloud Composer (Airflow)** for orchestration and scheduling.
*   **Dataproc** for executing data processing logic via PySpark.
*   **Google Cloud Storage (GCS)** for storing PySpark scripts, configuration files, and the final exported data.

## 2. Generated Artifacts

The migration process has generated the following key artifacts:

*   **`dags/dw_dwh_exis_sd_apt_nna_data.py`**
    *   **Role:** This is the Airflow Directed Acyclic Graph (DAG) definition. It orchestrates the execution of the data export process on GCP. Specifically, it defines a task to submit a PySpark job to a Dataproc cluster.
    *   **Location:** This file should be uploaded to the DAGs folder of your Cloud Composer environment.

*   **`pyspark_scripts/exis_sd_apt_nna_data.py`**
    *   **Role:** This PySpark script re-implements the core data extraction, transformation, and loading (ETL) logic previously contained within the `r_exis_v2` executable and its configuration. It connects to the source system, processes the telephone system master data, and writes the output to GCS.
    *   **Location:** This file should be uploaded to a designated GCS bucket, e.g., `gs://<YOUR_BUCKET_NAME>/pyspark_scripts/`.

*   **`gs://<YOUR_BUCKET_NAME>/exports/nna_data/DWHM_APT_NNA_Daten_<yyyymmddhhmmss>.csv.gz`**
    *   **Role:** This represents the final output file generated by the PySpark job. It is a gzipped CSV file containing the exported telephone system master data, with a dynamic timestamp in its filename.
    *   **Location:** This file will be created by the PySpark job in the specified GCS export bucket.

## 3. Key Design Decisions

The following key design decisions were made for this migration:

*   **Cloud Composer for Orchestration:** Airflow, managed by Cloud Composer, was chosen for its robust scheduling capabilities, ability to manage complex workflows, and native integration with other GCP services. This provides a modern, scalable, and observable orchestration layer compared to the legacy UC4 system.
*   **Dataproc for Data Processing:** Dataproc was selected to run the PySpark job due to its fully managed nature, scalability, and cost-effectiveness (especially when using ephemeral clusters). It provides a powerful and flexible environment for re-implementing the data processing logic that was previously in a custom UNIX executable.
*   **PySpark for Logic Re-implementation:** Given the data export nature of the original job, PySpark was chosen as the language and framework for re-implementing the business logic. It offers strong capabilities for data manipulation, connectivity to various data sources, and efficient handling of large datasets.
*   **Google Cloud Storage (GCS) for File Management:** GCS serves as the central repository for all artifacts (DAGs, PySpark scripts, configuration files) and the final output data. Its high durability, availability, scalability, and seamless integration with Airflow and Dataproc make it ideal for this purpose.
*   **Ephemeral Dataproc Clusters (Recommended):** While the generated DAG uses a placeholder for a cluster name, the design encourages the use of ephemeral Dataproc clusters. This approach creates a cluster only when the job runs and tears it down afterward, optimizing costs and resource utilization.
*   **IAM Service Accounts and Secret Manager for Security:** To adhere to GCP's security best practices, a dedicated IAM Service Account will be used for the Dataproc job, granting only the necessary permissions. Sensitive credentials (e.g., for source database access) will be securely stored and retrieved from Google Secret Manager.
*   **Direct GCS Output:** The PySpark script writes the compressed CSV directly to GCS, simplifying file transfer and making the output immediately available for downstream processes or storage.
*   **Manual Re-implementation of `r_exis_v2`:** Due to the black-box nature of the original `r_exis_v2` executable, a decision was made to fully re-implement its functionality in PySpark. This ensures transparency, maintainability, and adaptability within the new cloud environment.

## 4. Manual Steps Before Go-Live

Before the migrated job can go live, several manual steps and configurations are required:

1.  **GCP Project Configuration:**
    *   Update the `GCP_PROJECT_ID`, `DATAPROC_REGION`, `DATAPROC_CLUSTER_NAME`, and `GCS_BUCKET` placeholders in `dags/dw_dwh_exis_sd_apt_nna_data.py` with your actual GCP environment details.
    *   Ensure the `GCS_BUCKET` variable in the DAG points to the correct bucket for PySpark scripts and output.

2.  **Dataproc Cluster Setup:**
    *   **Provision Dataproc Cluster:** If using a persistent cluster, ensure it is provisioned and running in the specified `DATAPROC_REGION`. If using ephemeral clusters (recommended), configure the `DataprocSubmitJobOperator` to create a new cluster for each run or use Dataproc Serverless.
    *   **Initialization Actions:** If the PySpark job requires specific libraries or configurations on the Dataproc cluster (e.g., JDBC drivers for the source database), these should be included in Dataproc initialization actions.

3.  **GCS Bucket and Folder Structure:**
    *   Create the necessary GCS buckets and folders:
        *   A bucket for Airflow DAGs (usually managed by Cloud Composer).
        *   `gs://<YOUR_BUCKET_NAME>/pyspark_scripts/` for the `exis_sd_apt_nna_data.py` script.
        *   `gs://<YOUR_BUCKET_NAME>/config/` for the `h_exis_apt_nna_daten.var` configuration file (if applicable).
        *   `gs://<YOUR_BUCKET_NAME>/exports/nna_data/` for the output CSV files.

4.  **IAM Permissions:**
    *   Create a dedicated GCP Service Account for the Dataproc job.
    *   Grant this Service Account the following minimum IAM roles:
        *   `Dataproc Worker` (or equivalent for Dataproc Serverless)
        *   `Storage Object Viewer` for `gs://<YOUR_BUCKET_NAME>/pyspark_scripts/` and `gs://<YOUR_BUCKET_NAME>/config/`.
        *   `Storage Object Creator` and `Storage Object Admin` for `gs://<YOUR_BUCKET_NAME>/exports/nna_data/`.
        *   Permissions to access Google Secret Manager (e.g., `Secret Manager Secret Accessor`) if credentials are used.
        *   Network access permissions to the source database (if external).

5.  **Source Database Connectivity and Secrets:**
    *   **Identify Source Database:** Determine the exact database system, hostname, port, database name, and schema for the telephone system master data.
    *   **Network Connectivity:** Ensure the Dataproc cluster has network access to the source database (e.g., via VPC peering, Cloud VPN, or Private Service Connect).
    *   **Connection Strings/Credentials:** Store the source database username, password, and any other sensitive connection parameters in Google Secret Manager. The PySpark script will need to be updated to retrieve these secrets.

6.  **PySpark Script Completion (`pyspark_scripts/exis_sd_apt_nna_data.py`):**
    *   **Reverse Engineer `r_exis_v2`:** This is the most critical step. Analyze the original `r_exis_v2` executable and `h_exis_apt_nna_daten.var` configuration to understand the exact data extraction queries, transformation logic, and formatting requirements.
    *   **Implement Data Extraction:** Replace the placeholder in `exis_sd_apt_nna_data.py` with actual PySpark code to connect to the source database (e.g., using JDBC) and extract the required master data.
    *   **Implement Transformation Logic:** Translate all identified transformation rules (filtering, column selection, data type conversions, aggregations, etc.) into PySpark DataFrame operations.
    *   **Configuration Handling:** If `h_exis_apt_nna_daten.var` contains dynamic or significant configuration, implement logic in the PySpark script to read and parse this file from GCS.

7.  **Airflow DAG Scheduling:**
    *   **Define Schedule:** Determine the exact `schedule` (e.g., `timedelta(days=1)` for daily, `cron` string for specific times) for the `dw_dwh_exis_sd_apt_nna_data` DAG based on the original UC4 schedule and business requirements. The current DAG is set to `None` (manual trigger).
    *   **Review `retries`:** The DAG is currently configured with `retries=0`. Review operational requirements and adjust this value if automatic retries are desired.

8.  **External Distribution (if applicable):**
    *   If the "target system" for distribution is external to GCS (e.g., an SFTP server, another cloud provider), additional Airflow tasks will need to be added to the DAG to handle this distribution (e.g., `GCSToSFTPOperator`, custom PythonOperator). This will also require corresponding IAM permissions and potentially network configurations.

## 5. Known Gaps & Unresolved References

The following items are known gaps or require further investigation and resolution:

*   **`r_exis_v2` Executable Logic (B4 Item):** The most significant gap is the lack of detailed understanding of the `r_exis_v2` executable and its associated configuration file `h_exis_apt_nna_daten.var`. This is currently a "black box."
    *   **Resolution:** A thorough reverse-engineering effort or direct consultation with Subject Matter Experts (SMEs) familiar with the original code is **mandatory** to accurately re-implement the data extraction and transformation logic in PySpark.
*   **Source Database Details:** The specific database system (e.g., Oracle, SQL Server, PostgreSQL), hostname, port, database name, and schema for the telephone system master data are not yet identified.
    *   **Resolution:** This information must be obtained from the `r_exis_v2` analysis or SMEs.
*   **Original Job Schedule:** The UC4 XML definition did not contain explicit scheduling information.
    *   **Resolution:** The business-driven schedule for this export job needs to be confirmed and configured in the Airflow DAG's `schedule` parameter.
*   **Broader Workflow Context:** This migration focuses on a single UC4 job. If `EXIS_SD_APT_NNA_DATA` is part of a larger, dependent UC4 workflow (e.g., a `JOBP` or `JSCH`), those dependencies are not addressed in this design.
    *   **Resolution:** A broader analysis of the UC4 environment is needed to identify and migrate any upstream/downstream dependencies.
*   **GCP Placeholders:** All `YOUR_GCP_PROJECT_ID`, `YOUR_DATAPROC_REGION`, `YOUR_DATAPROC_CLUSTER_NAME`, and `YOUR_BUCKET_NAME` values are placeholders.
    *   **Resolution:** These must be replaced with actual environment-specific values during implementation.
*   **Error Handling and Retries Policy:** The Airflow DAG is currently configured with `retries=0`.
    *   **Resolution:** Review the operational requirements for retries and failure notifications (e.g., Slack, PagerDuty) and adjust the DAG's `retries` and `on_failure_callback` as needed.
*   **External Distribution Mechanism:** The original job "distributes it to the target system," but the specifics of this distribution are unclear.
    *   **Resolution:** The target system and distribution method must be identified. If it's an external system, additional Airflow tasks (e.g., SFTP, API calls) will be required.
*   **`h_exis_apt_nna_daten.var` Content:** The content and usage of this configuration file are unknown.
    *   **Resolution:** Its contents need to be analyzed during the `r_exis_v2` reverse engineering phase to determine how its parameters should be passed to or used by the PySpark script.

## 6. Validation

Validation of the migrated `EXIS_SD_APT_NNA_DATA` job involves several stages to ensure functional correctness, data integrity, and performance.

### How to Run Tests:

1.  **Deploy to Development/Staging Environment:**
    *   Ensure all manual steps (Section 4) are completed in a non-production GCP environment.
    *   Upload `dags/dw_dwh_exis_sd_apt_nna_data.py` to your Cloud Composer DAGs folder.
    *   Upload `pyspark_scripts/exis_sd_apt_nna_data.py` (with implemented logic) to `gs://<YOUR_BUCKET_NAME>/pyspark_scripts/`.

2.  **Trigger the Airflow DAG:**
    *   From the Airflow UI, unpause the `dw_dwh_exis_sd_apt_nna_data` DAG.
    *   Manually trigger a DAG run.

3.  **Monitor Execution:**
    *   Observe the DAG run in the Airflow UI for task status (running, success, failure).
    *   Check Dataproc job logs in Cloud Logging for detailed PySpark execution output, warnings, and errors.
    *   Verify the creation of the output file in the specified GCS bucket (`gs://<YOUR_BUCKET_NAME>/exports/nna_data/`).

### What "Passing" Means:

A successful migration and validation means all of the following criteria are met:

*   **Airflow DAG Completion:** The `dw_dwh_exis_sd_apt_nna_data` DAG completes successfully without any failed tasks.
*   **Dataproc Job Success:** The underlying Dataproc PySpark job finishes with a "SUCCEEDED" status.
*   **Output File Generation:**
    *   A gzipped CSV file named `DWHM_APT_NNA_Daten_<yyyymmddhhmmss>.csv.gz` is generated in the correct GCS path (`gs://<YOUR_BUCKET_NAME>/exports/nna_data/`).
    *   The filename adheres to the expected naming convention, including the dynamic timestamp.
*   **Data Integrity and Format:**
    *   The content of the generated CSV file matches the data produced by the legacy UC4 job for the same period. This is the most critical validation step and may require a byte-by-byte comparison or a row-count and checksum comparison.
    *   The CSV format (delimiter, header, quoting, encoding) is identical to the legacy output.
    *   All expected columns are present, and data types are correct.
*   **Performance:** The PySpark job completes within acceptable timeframes, comparable to or better than the legacy job, and utilizes Dataproc resources efficiently.
*   **Resource Utilization:** Dataproc cluster resources (CPU, memory, disk) are within expected bounds, and no resource exhaustion is observed.
*   **Logging and Monitoring:** All relevant logs are captured in Cloud Logging, and no unexpected errors or warnings are present.
*   **User Acceptance Testing (UAT):** Business users confirm that the exported data meets their requirements and expectations.

## 7. Rollback Procedure

In the event that the migrated `EXIS_SD_APT_NNA_DATA` job encounters critical issues after go-live, the following rollback procedure should be followed to revert to the legacy UC4 system:

1.  **Immediate Action - Disable New Job:**
    *   **Pause Airflow DAG:** In the Cloud Composer Airflow UI, immediately pause the `dw_dwh_exis_sd_apt_nna_data` DAG to prevent any further runs.
    *   **Delete/Archive DAG (Optional):** If the issue is severe and requires extensive investigation, consider deleting or archiving the DAG from the Composer environment to ensure it cannot be accidentally re-enabled.

2.  **Re-enable Legacy Job:**
    *   **Activate UC4 Job:** Re-enable and/or manually trigger the original `DW.DWH_EXIS_SD_APT_NNA_DATA` job in the UC4 (Automic) system.
    *   **Verify Legacy Execution:** Monitor the UC4 job to ensure it runs successfully and produces the expected output, confirming the legacy system is fully operational.

3.  **Cleanup (Post-Rollback):**
    *   **GCS Output:** If the migrated job produced any erroneous or incomplete output files in GCS, these should be reviewed and potentially deleted or moved to an archive location to avoid confusion.
    *   **Dataproc Resources:** If ephemeral Dataproc clusters were used, they will automatically terminate. If a persistent cluster was used, ensure it is still available for future testing or other workloads.

4.  **Root Cause Analysis:**
    *   Thoroughly investigate the reason for the rollback. This includes reviewing Airflow task logs, Dataproc job logs, Cloud Logging, and any generated output files.
    *   Identify the specific issue (e.g., data discrepancy, performance bottleneck, infrastructure failure, incorrect logic).
    *   Develop a remediation plan and re-test extensively in a staging environment before attempting another go-live.
