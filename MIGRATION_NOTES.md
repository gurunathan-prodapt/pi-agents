# MIGRATION_NOTES.md

## 1. Summary

This document details the migration of the ETL job orchestrated by `r_ausd_v_ta_disc_zusgf.ksh`. The original job, comprising KornShell scripts (`r_ausd_v_ta_disc_zusgf.ksh`, `k_ausd_v_ta_disc_zusgf.ksh`) and an Oracle PL/SQL script (`d_ausd_v_ta_disc_zusgf.sql`), was responsible for data reconciliation and population of the `SOF$TA_DISC_ZUSGF` table in an Oracle database.

The job has been migrated to **Google Cloud Platform (GCP)**, leveraging the following services:
*   **Orchestration**: Google Cloud Composer (Apache Airflow)
*   **Data Warehouse**: Google BigQuery
*   **Data Transformation**: PySpark on Dataproc Serverless for complex logic, and BigQuery SQL for final data loading.

The migration involved refactoring the KornShell orchestration into an Airflow DAG, rewriting Oracle PL/SQL transformation logic (especially the pipelined table function) into PySpark, and translating standard SQL operations into BigQuery SQL.

## 2. Generated Artifacts

The migration process generated the following artifacts:

*   **`src/pyspark/concat_discounts_spark.py`**
    *   **Role**: This PySpark script replicates the complex logic of the Oracle `concat_discounts` pipelined table function. It reads discount data from the BigQuery equivalent of `SOF$TA_DISCOUNT`, groups discounts by contract, concatenates them into a single string with a specified length limit (500 characters), and writes the result to a BigQuery staging table (`ta_disc_zusgf_spark_staging`). This addresses the `Stored_Proc_Transform` pattern.

*   **`src/sql/ta_disc_zusgf_insert.sql`**
    *   **Role**: This BigQuery SQL script performs the final `INSERT` operation into the target `SOF_TA_DISC_ZUSGF` table. It joins data from the BigQuery source table (`SOF_TA_DISCOUNT`) with the processed, concatenated discount information generated by the PySpark job (from `ta_disc_zusgf_spark_staging`). This addresses the `Bulk_Load_Stage_To_Final` pattern.

*   **`dags/bert/r_ausd_v_ta_disc_zusgf_dag.py`**
    *   **Role**: This Apache Airflow DAG orchestrates the entire ETL process on GCP. It replaces the original UC4 job and KornShell scripts. The DAG defines the sequence of tasks:
        1.  Truncating the target BigQuery table (`SOF_TA_DISC_ZUSGF`).
        2.  Executing the `concat_discounts_spark.py` PySpark job on Dataproc Serverless.
        3.  Executing the `ta_disc_zusgf_insert.sql` BigQuery SQL script to load data into the final target table.
    *   It handles environment setup, parameter passing, and integrates with GCP services for logging and monitoring. This addresses the `Orchestration` and `Dynamic_SQL_substitution` patterns.

## 3. Key Design Decisions

*   **Orchestration Replatforming to Cloud Composer (Airflow)**:
    *   **Why**: Airflow provides a robust, scalable, and cloud-native solution for scheduling, monitoring, and managing complex ETL workflows. It replaces the legacy UC4 scheduler and custom KornShell wrapper scripts, offering better visibility, error handling, and integration with other GCP services.
    *   **Trade-offs**: Requires learning Airflow concepts and Python for DAG development. Initial setup and configuration of Cloud Composer can be complex.

*   **Data Warehouse Migration to BigQuery**:
    *   **Why**: BigQuery offers petabyte-scale analytics, serverless architecture, and cost-effectiveness, making it an ideal target for data warehousing. It provides superior performance and scalability compared to the legacy Oracle database for analytical workloads.
    *   **Trade-offs**: Requires refactoring Oracle-specific SQL and PL/SQL constructs. Data type mappings and performance tuning for BigQuery are necessary.

*   **Complex PL/SQL Pipelined Function Rewritten to PySpark on Dataproc Serverless**:
    *   **Why**: The Oracle pipelined table function (`concat_discounts`) is a highly Oracle-specific feature that cannot be directly translated to BigQuery SQL. PySpark on Dataproc Serverless provides a powerful, scalable, and managed environment for complex data transformations, especially those involving grouping, aggregation, and custom logic like string concatenation with length limits. Dataproc Serverless eliminates the need to manage Spark clusters.
    *   **Trade-offs**: Introduces a new technology stack (PySpark) and requires expertise in Spark development. Adds an additional component to the architecture, potentially increasing operational complexity and cost if not optimized.

*   **Final Data Load using BigQuery SQL**:
    *   **Why**: After the complex transformation (concatenation) is handled by PySpark, the final `INSERT INTO` operation is a straightforward bulk load. BigQuery SQL is highly optimized for such operations, providing efficient and performant data ingestion into the target table.
    *   **Trade-offs**: None significant, as this is a standard and efficient BigQuery operation.

*   **Replacement of Legacy Helper Scripts and Utilities**:
    *   **Why**: Custom KornShell helper scripts (`.dw_init`, `f_alis_msgerr.ksh`, `h_alis_parameter.ksh`, `h_alis_date.ksh`, `h_alis_sqlplus.ksh`) and Oracle utility packages (`DWPA_UTIL_SKRIPT`) have been replaced by Airflow's native features (parameters, macros, operators), Python's standard library, and GCP's managed services (Cloud Logging, Cloud Monitoring). This reduces technical debt, improves maintainability, and leverages cloud-native capabilities.
    *   **Trade-offs**: Requires mapping legacy functionality to new cloud-native equivalents.

## 4. Manual Steps Before Go-Live

The following manual steps are required to prepare the GCP environment and deploy the migrated job:

1.  **GCP Project Setup**:
    *   Ensure a GCP Project is created and configured.
    *   Enable necessary APIs: BigQuery API, Cloud Composer API, Dataproc API, Cloud Storage API, Cloud Logging API, Cloud Monitoring API.

2.  **BigQuery Dataset Creation**:
    *   Create the following BigQuery datasets:
        *   `your_source_dataset` (e.g., `isbert_schema_migrated`)
        *   `your_target_dataset` (e.g., `isbert_schema_migrated`)
        *   `your_staging_dataset` (e.g., `isbert_staging`)

3.  **BigQuery Table Creation & Data Migration**:
    *   Migrate source data from Oracle to BigQuery:
        *   `isbert_schema.dwtk_meldungen` -> `your_source_dataset.dwtk_meldungen`
        *   `SOF$TA_DISCOUNT` -> `your_source_dataset.SOF_TA_DISCOUNT`
    *   Create the target table in BigQuery:
        *   `SOF$TA_DISC_ZUSGF` -> `your_target_dataset.SOF_TA_DISC_ZUSGF` (schema must match the expected output).
    *   Create the staging table for PySpark output:
        *   `your_staging_dataset.ta_disc_zusgf_spark_staging` (schema will be inferred by PySpark on first write, but pre-creating with appropriate types is recommended).

4.  **Cloud Storage (GCS) Bucket Creation**:
    *   Create a GCS bucket, e.g., `your-gcs-staging-bucket`. This bucket will be used for:
        *   Storing the PySpark script (`concat_discounts_spark.py`).
        *   Temporary files generated by Dataproc Serverless.
        *   BigQuery temporary data for Spark-BigQuery connector.

5.  **IAM Permissions Configuration**:
    *   **Cloud Composer Service Account**: Ensure the service account associated with your Cloud Composer environment has the following roles:
        *   `BigQuery Data Editor` (for `your_source_dataset`, `your_target_dataset`, `your_staging_dataset`)
        *   `Dataproc Editor` (to submit Dataproc Serverless jobs)
        *   `Storage Object Admin` (for `your-gcs-staging-bucket`)
        *   `Service Account User` (on the Dataproc Serverless service account, if different)
    *   **Dataproc Serverless Service Account**: If using a dedicated service account for Dataproc Serverless batches (recommended), ensure it has:
        *   `BigQuery Data Editor` (for `your_source_dataset`, `your_target_dataset`, `your_staging_dataset`)
        *   `Storage Object Admin` (for `your-gcs-staging-bucket`)

6.  **Airflow Environment Configuration**:
    *   **GCP Connection**: Verify or create an Airflow connection named `google_cloud_default` configured for your GCP project.
    *   **Airflow Variables/Parameters**: Update the placeholder values in `dags/bert/r_ausd_v_ta_disc_zusgf_dag.py` or configure them as Airflow Variables:
        *   `GCP_PROJECT_ID`
        *   `GCP_REGION`
        *   `BIGQUERY_DATASET_SOURCE`
        *   `BIGQUERY_DATASET_TARGET`
        *   `BIGQUERY_DATASET_STAGING`
        *   `GCS_TEMP_BUCKET`
        *   `PYSPARK_GCS_PATH` (ensure this points to the uploaded PySpark script).

7.  **Upload PySpark Script to GCS**:
    *   Upload `src/pyspark/concat_discounts_spark.py` to the GCS path specified by `PYSPARK_GCS_PATH` (e.g., `gs://your-gcs-staging-bucket/dags_resources/pyspark/concat_discounts_spark.py`).

8.  **Deploy Airflow DAG**:
    *   Upload `dags/bert/r_ausd_v_ta_disc_zusgf_dag.py` and `src/sql/ta_disc_zusgf_insert.sql` to your Cloud Composer DAGs folder.

9.  **Scheduling**:
    *   Configure the desired schedule for the `bert_ausd_v_ta_disc_zusgf_etl` DAG in the Airflow UI, replacing the legacy UC4 schedule.

## 5. Known Gaps & Unresolved References

*   **Source Data Migration Prerequisite**: The design explicitly states that `isbert_schema.dwtk_meldungen` and `SOF$TA_DISCOUNT` must first be migrated to BigQuery. This migration is outside the scope of *this* job's migration but is a critical prerequisite.
*   **Dataproc Serverless Configuration**: The `DataprocSubmitSparkJobOperator` in the DAG is a generic Spark job submission. For optimal Dataproc Serverless integration, using `DataprocCreateBatchOperator` with a `pyspark_batch` configuration is recommended if available and preferred in the Airflow environment. The provided DAG includes commented-out code demonstrating this alternative. The specific service account for Dataproc Serverless (`your-dataproc-service-account`) also needs to be defined and configured.
*   **GCS Staging Bucket Placeholder**: The `your-gcs-staging-bucket` placeholder in `concat_discounts_spark.py` and `dags/bert/r_ausd_v_ta_disc_zusgf_dag.py` must be replaced with an actual, existing GCS bucket name.
*   **GCP Project/Region Placeholders**: `your-gcp-project-id`, `your-gcp-region`, `your_source_dataset`, `your_target_dataset`, `your_staging_dataset` in the DAG need to be updated with actual environment values.
*   **Oracle PL/SQL Rewrite Complexity**: The rewrite of the pipelined table function to PySpark was identified as a "Complex" task. While the PySpark script aims to replicate the logic, thorough testing is crucial to ensure functional equivalence and handle all edge cases of the original Oracle implementation.
*   **Performance Tuning**: Initial deployment may require performance tuning for both PySpark (e.g., memory, cores, partitions) and BigQuery (e.g., clustering, partitioning, query optimization) depending on data volumes.
*   **Cost Optimization**: Monitoring Dataproc Serverless and BigQuery costs post-migration is essential to ensure cost efficiency.
*   **Error Handling and Alerting**: While Airflow provides native error handling, specific alerting mechanisms (e.g., email, PagerDuty via Cloud Monitoring) should be configured for critical job failures.
