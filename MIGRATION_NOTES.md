# MIGRATION_NOTES.md

## 1. Summary

The ETL job `vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/r_ausd_v_ta_notice.ksh`, along with its dependencies `k_ausd_v_ta_notice.ksh` and `d_ausd_v_ta_notice.sql`, has been migrated from a KornShell/Oracle SQL*Plus environment to Google Cloud BigQuery.

The original job is an ETL workflow for the reconciliation of contract data into the `ta_notice` table. It acts as a wrapper script, orchestrating the execution of core data processing logic, handling command-line parameters, initializing the execution environment, managing error logging, and updating job status. The core data manipulation involves truncating and inserting data into the `sof$ta_notice` table based on `cds$ta_notice` and `dwtk_meldungen` tables, applying specific date and production flag filters.

The migration involved transforming the KornShell scripts into BigQuery Stored Procedures for orchestration and parameter handling, and the Oracle SQL*Plus script into BigQuery SQL within a stored procedure. Logging and job control mechanisms have been re-engineered to utilize BigQuery native tables.

## 2. Generated artifacts

    *   **Role**: Defines the schema for the `job_log` table, which centralizes all operational log messages generated by the migrated BigQuery procedures. This replaces file-based logging.
*   **`bqsql/my_project.my_dataset.job_control.sql`**:
    *   **Role**: Defines the schema for the `job_control` table, used to track the status, start/end times, and other metadata for each job run. This replaces shell-script based job status management.
*   **`bqsql/my_project.my_dataset.error_log.sql`**:
    *   **Role**: Defines the schema for the `error_log` table, dedicated to capturing detailed error information, including messages, codes, and stack traces. This replaces ad-hoc error logging in shell scripts.

    *   **Role**: Defines the schema for the BigQuery native table `dwtk_meldungen`, which is the migrated version of the Oracle `isbert_schema.dwtk_meldungen` table. It stores metadata used to determine the reference date (`v_datum`).
*   **`bqsql/my_project.my_dataset.cds_ta_notice.sql`**:
    *   **Role**: Defines the schema for the BigQuery native table `cds_ta_notice`, which is the migrated version of the Oracle `cds$ta_notice` table. This table serves as the primary source for the data processing logic. Data for this table must be populated via a separate ingestion pipeline.
*   **`bqsql/my_project.my_dataset.sof_ta_notice.sql`**:
    *   **Role**: Defines the schema for the BigQuery native table `sof_ta_notice`, which is the migrated target table, replacing the Oracle `sof$ta_notice`.
*   **`bqsql/my_project.my_dataset.sp_dwmsg_ermittle_nr.sql`**:
    *   **Role**: A BigQuery Stored Procedure that replicates the `DWMSG_ErmittleNr` logic. It generates a unique entry number for each job execution, typically by interacting with a control table or using a timestamp-based sequence.
*   **`bqsql/my_project.my_dataset.sp_dwmsg_logdateiname.sql`**:
    *   **Role**: A BigQuery Stored Procedure that replaces the shell script's `print` and `tee` commands. It inserts log messages into the `job_log` table, centralizing logging.
*   **`bqsql/my_project.my_dataset.sp_dwmsg_erzeuge_eintrag.sql`**:
    *   **Role**: A BigQuery Stored Procedure that replicates `DWMSG_ErzeugeEintrag`. It creates an initial entry in the `job_control` table when a job starts, marking its status as 'RUNNING'.
*   **`bqsql/my_project.my_dataset.sp_dwmsg_setze_stichtag_info.sql`**:
    *   **Role**: A BigQuery Stored Procedure that replicates `DWMSG_SetzeStichtagInfo`. It updates the `job_control` table with information about the reference date (`Stichtag`) used for the job run.
*   **`bqsql/my_project.my_dataset.sp_dwmsg_fehlerbehandlung.sql`**:
    *   **Role**: A BigQuery Stored Procedure that replicates `DWMSG_Fehlerbehandlung`. It updates the `job_control` table to 'FAILED' status, logs detailed error messages to `error_log`, and also records an error message in `job_log`.
*   **`bqsql/my_project.my_dataset.sp_dwmsg_setze_status_ok.sql`**:
    *   **Role**: A BigQuery Stored Procedure that replicates `DWMSG_SetzeStatusOK`. It updates the `job_control` table to 'SUCCESS' status upon successful completion, including the count of processed records.
*   **`bqsql/my_project.my_dataset.sp_dwmsg_send_notification.sql`**:
    *   **Role**: A placeholder BigQuery Stored Procedure for sending notifications, replacing the original `DWMSG_ERMITTLENR` (send_mail type) function. Currently, it logs the notification attempt.
*   **`bqsql/my_project.my_dataset.sp_d_ausd_v_ta_notice_sql.sql`**:
    *   **Role**: A BigQuery Stored Procedure that encapsulates the core data processing logic from `d_ausd_v_ta_notice.sql`. It determines the `v_datum`, truncates the target table, and inserts data from `cds_ta_notice` into `sof_ta_notice` based on the defined filters. It includes error handling.
*   **`bqsql/my_project.my_dataset.sp_k_ausd_v_ta_notice_core.sql`**:
    *   **Role**: A BigQuery Stored Procedure that replaces `k_ausd_v_ta_notice.ksh`. It handles job parameters, performs validation, orchestrates the execution of `sp_d_ausd_v_ta_notice_sql`, and updates job status.
*   **`bqsql/my_project.my_dataset.sp_r_ausd_v_ta_notice.sql`**:
    *   **Role**: The top-level BigQuery Stored Procedure, replacing `r_ausd_v_ta_notice.ksh`. It serves as the main entry point for the job, handling overall setup, parameter parsing, initial logging, and calling `sp_k_ausd_v_ta_notice_core`. It includes robust error handling for the entire workflow.

## 3. Key design decisions

*   **Orchestration via BigQuery Stored Procedures**: The KornShell wrapper scripts (`r_ausd_v_ta_notice.ksh`, `k_ausd_v_ta_notice.ksh`) have been directly translated into BigQuery Stored Procedures (`sp_r_ausd_v_ta_notice`, `sp_k_ausd_v_ta_notice_core`). This leverages BigQuery's native scripting capabilities for control flow, parameter handling, and error management, eliminating the need for external shell environments.
*   **Native BigQuery SQL for Data Processing**: The Oracle SQL*Plus script (`d_ausd_v_ta_notice.sql`) has been converted into a BigQuery SQL stored procedure (`sp_d_ausd_v_ta_notice_sql`). This ensures optimal performance by executing data manipulation directly within BigQuery's columnar, distributed architecture.
*   **Centralized Logging and Job Control**: File-based logging and job status management (e.g., `print`, `tee`, `tmpFile`) have been replaced by dedicated BigQuery tables (`job_log`, `job_control`, `error_log`) and helper stored procedures (`sp_dwmsg_*`). This provides a centralized, queryable, and scalable solution for monitoring job execution and auditing.
*   **Modularization with Helper Procedures**: Common utility functions and repetitive logic (e.g., `DWMSG_ErmittleNr`, `DWMSG_Logdateiname`) have been abstracted into separate BigQuery helper stored procedures. This improves code reusability, maintainability, and readability.
*   **DB Link Migration Strategy (Data Ingestion)**: The Oracle DB link (`cds$ta_notice@pcrs1`) has been addressed by assuming a data ingestion pipeline will populate a native BigQuery table (`my_project.my_dataset.cds_ta_notice`). This decision prioritizes performance and reliability within BigQuery over real-time federated queries, which can introduce latency and dependency on the source Oracle system. A similar approach is taken for `dwtk_meldungen`.
*   **Oracle-Specific Feature Translation**: Oracle-specific SQL functions (`NVL`, `TO_CHAR`, `TO_DATE`) and SQL*Plus commands (`WHENEVER SQLERROR`, `SPOOL`, `COLUMN ... NEW_VALUE`, `TRUNCATE TABLE` via `runstatement`) have been carefully translated to their BigQuery equivalents (`COALESCE`, `FORMAT_DATE`, `PARSE_DATE`, direct `TRUNCATE TABLE` DDL) or re-architected into BigQuery scripting constructs.
*   **Error Handling**: BigQuery's `BEGIN...EXCEPTION WHEN ERROR THEN...END` blocks are used for robust error handling within stored procedures, replacing shell `set -eu` and `trap` commands. Errors are logged to the `error_log` table and propagated up the call stack.

## 4. Manual steps before go-live

Before the migrated job can go live, the following manual steps must be completed:

1.  **BigQuery Dataset Creation**:
    *   Ensure the BigQuery dataset `my_project.my_dataset` exists in your Google Cloud project. If not, create it.

2.  **Table Creation**:
    *   Execute the `CREATE TABLE IF NOT EXISTS` statements for all generated table schemas:
        *   `bqsql/my_project.my_dataset.job_log.sql`
        *   `bqsql/my_project.my_dataset.job_control.sql`
        *   `bqsql/my_project.my_dataset.error_log.sql`
        *   `bqsql/my_project.my_dataset.dwtk_meldungen.sql`
        *   `bqsql/my_project.my_dataset.cds_ta_notice.sql`
        *   `bqsql/my_project.my_dataset.sof_ta_notice.sql`

3.  **Stored Procedure Deployment**:
    *   Deploy all generated BigQuery Stored Procedures by executing their `CREATE OR REPLACE PROCEDURE` statements in BigQuery. This includes all `sp_dwmsg_*` helper procedures, `sp_d_ausd_v_ta_notice_sql`, `sp_k_ausd_v_ta_notice_core`, and `sp_r_ausd_v_ta_notice`.

4.  **Data Ingestion for Source Tables**:
    *   **`my_project.my_dataset.cds_ta_notice`**: Set up a robust data pipeline (e.g., using Dataflow, Dataproc, Fivetran, or a custom Cloud Function) to continuously or periodically ingest data from the source Oracle `cds$ta_notice` table into the BigQuery `my_project.my_dataset.cds_ta_notice` table. This pipeline must be operational and verified before the ETL job runs.
    *   **`my_project.my_dataset.dwtk_meldungen`**: Similarly, ensure data from `isbert_schema.dwtk_meldungen` is ingested into `my_project.my_dataset.dwtk_meldungen`.

5.  **IAM/Permissions**:
    *   Grant the service account that will execute the BigQuery stored procedures (e.g., the Cloud Composer service account or a dedicated service account for Cloud Workflows) the necessary IAM roles:
        *   `BigQuery Data Editor` on `my_project.my_dataset` to allow `INSERT`, `UPDATE`, `TRUNCATE`, and `SELECT` operations on all tables.
        *   `BigQuery Job User` to run queries and stored procedures.
        *   If using external connections for `sp_dwmsg_send_notification` (e.g., Cloud Functions), ensure appropriate permissions for those services.

6.  **Scheduling**:
    *   Deactivate the original scheduler for `r_ausd_v_ta_notice.ksh`.
    *   Configure a new scheduler (e.g., Cloud Composer DAG or Cloud Workflows) to execute the top-level BigQuery Stored Procedure: `CALL \`my_project.my_dataset.sp_r_ausd_v_ta_notice\`('R_AUSD_V_TA_NOTICE');`.
    *   Ensure the scheduler is configured with the correct frequency and error handling.

7.  **Secrets Management**:
    *   If the data ingestion pipeline for `cds_ta_notice` or any notification mechanism requires credentials (e.g., Oracle database passwords, API keys), ensure these are securely stored in Secret Manager and accessed appropriately by the respective services.

## 5. Known gaps & unresolved references

*   **Missing Complexity/Automation Data**: The original design document noted the absence of `file_complexity` and `automation_rate` data, which required assumptions about the migration effort. A more precise assessment would have benefited from this information.
*   **Oracle-Specific Features**: While translated, the nuances of Oracle SQL*Plus specific commands (`WHENEVER SQLERROR`, `START ../trace.sql.cfg`, `SPOOL`, `COLUMN ... NEW_VALUE`) might have subtle behavioral differences in BigQuery scripting. Thorough testing is required.
*   **DB Link Performance**: The performance implications of migrating the `cds$ta_notice@pcrs1` DB link to a data ingestion pipeline need to be continuously monitored. If the ingestion pipeline cannot keep up with source changes or introduces unacceptable latency, alternative strategies (e.g., BigQuery federated queries with careful optimization) might need to be re-evaluated.
*   **Dynamic Script Paths**: The original use of `BERT_DIR_ROOT` for dynamic script paths has been resolved into static BigQuery procedure names. This removes runtime flexibility but simplifies deployment.
*   **`starteSQLSkript` Implementation Details**: The exact logic within `h_alis_sqlplus.ksh` and `starteSQLSkript` regarding error handling during SQL execution and output parsing was not fully detailed in the source. The BigQuery migration assumes standard BigQuery error propagation and logging.
*   **Job Control Semantics**: The "active jobs ignored" and "old active jobs deactivated" logic mentioned in `k_ausd_v_ta_notice.ksh` summary has been partially replicated by the `job_control` table and status updates. However, the full extent of this logic (e.g., preventing concurrent runs, explicit deactivation) might require additional logic within `sp_k_ausd_v_ta_notice_core` or the external orchestrator.
*   **Notification Mechanism (`sp_dwmsg_send_notification`)**: The `sp_dwmsg_send_notification` procedure is currently a placeholder. A concrete implementation (e.g., integrating with Cloud Functions, Pub/Sub, or a third-party notification service) is required to fully replicate the original `DWMSG_ERMITTLENR` (send_mail type) functionality.


3.  **"Passing" Criteria**:
    *   **Successful Procedure Execution**: The `CALL` statement for `sp_r_ausd_v_ta_notice` should complete without BigQuery reporting a job failure.
    *   **Job Control Status**: Query the `job_control` table:
        ```sql
        SELECT * FROM `my_project.my_dataset.job_control` WHERE job_kennung = 'R_AUSD_V_TA_NOTICE_TEST' ORDER BY start_timestamp DESC LIMIT 1;
        ```
        The `status` column for the latest entry should be 'SUCCESS'.
    *   **No Errors Logged**: Query the `error_log` table:
        ```sql
        SELECT * FROM `my_project.my_dataset.error_log` WHERE job_kennung = 'R_AUSD_V_TA_NOTICE_TEST';
        ```
        This query should return no rows, indicating no errors were encountered.
    *   **Log Messages**: Review the `job_log` table for informational messages:
        ```sql
        SELECT log_message FROM `my_project.my_dataset.job_log` WHERE job_kennung = 'R_AUSD_V_TA_NOTICE_TEST' ORDER BY log_timestamp;
        ```

        Verify that expected messages (e.g., "Starting...", "Determined v_datum...", "TRUNCATE TABLE...", "Inserted X records...", "Job completed successfully.") are present and in the correct sequence.
    *   **Target Data Verification**:
        *   Query the `my_project.my_dataset.sof_ta_notice` table to ensure data has been inserted correctly.

Pay close attention to date filters (`insert_at`, `modified_at`, `valid_to`) and the `is_production` flag.
    *   **Performance**: Monitor the execution time of the BigQuery job and compare it against the baseline performance of the original Oracle/KornShell job.

## 7. Rollback procedure

In case of critical issues or unexpected behavior after go-live, the following rollback procedure can be executed:

1.  **Stop BigQuery Job Execution**:
    *   Immediately pause or disable the Cloud Composer DAG or Cloud Workflows that schedules `sp_r_ausd_v_ta_notice`. This prevents further execution of the migrated job.

2.  **Reactivate Original Scheduler**:
    *   Re-enable the original scheduler (e.g., cron job, enterprise scheduler) that was responsible for executing `vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/r_ausd_v_ta_notice.ksh`.

3.  **Verify Original Job Functionality**:
    *   Monitor the execution of the original KornShell/Oracle job to ensure it runs successfully and produces the expected output in the Oracle `sof$ta_notice` table.

4.  **Data Restoration (if necessary)**:
    *   If the BigQuery job made any unintended or incorrect modifications to the `my_project.my_dataset.sof_ta_notice` table that could impact downstream processes, consider restoring `sof_ta_notice` to a known good state. This might involve:
        *   Truncating `my_project.my_dataset.sof_ta_notice`.
        *   Backfilling `my_project.my_dataset.sof_ta_notice` from a previous successful run's snapshot or by re-running the original Oracle job and then re-ingesting the data into BigQuery (if `sof_ta_notice` is also a source for other BigQuery processes).
    *   **Note**: The migrated BigQuery job `sp_d_ausd_v_ta_notice_sql` performs a `TRUNCATE` before `INSERT`. If the rollback is initiated *before* the BigQuery job completes its `INSERT` phase, the `sof_ta_notice` table in BigQuery might be empty. If the rollback is initiated *after* a successful BigQuery run, the `sof_ta_notice` table will contain data from the BigQuery run. The impact of this on downstream BigQuery processes needs to be assessed.

5.  **Investigation**:
    *   Analyze the `job_log`, `job_control`, and `error_log` tables in BigQuery for the failed runs of the migrated job to identify the root cause of the issue.
    *   Review BigQuery job history and logs for any performance bottlenecks or errors.

This rollback procedure ensures a quick return to the stable, original environment while allowing time for thorough investigation and remediation of the migrated job.
