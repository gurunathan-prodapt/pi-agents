# MIGRATION_NOTES.md

## 1. Summary

This document details the migration of the legacy KornShell script `k_ausd_bp_ta_msisdn.ksh` to Google Cloud Platform, specifically leveraging BigQuery Stored Procedures.

The original script served as an orchestration wrapper, responsible for:
*   Parsing command-line parameters (Jobkennung, Stichtag, EintragsNr, wiederanlaufWert).
*   Setting up the execution environment.
*   Performing date validation and derivation (e.g., `gestern.ksh` logic).
*   Executing a core SQL script (`d_ausd_bp_ta_msisdn.sql`) via a utility function (`starteSQLSkript`).
*   Capturing and reporting record counts.
*   Handling errors and potentially tracking job status (commented functionality).

The migration translates this orchestration logic into a BigQuery Stored Procedure (`proc_ausd_bp_ta_msisdn`), which in turn calls another BigQuery Stored Procedure (`proc_d_ausd_bp_ta_msisdn`) containing the translated core SQL logic. All environment setup, utility script functionalities, and error handling are re-implemented using BigQuery SQL scripting capabilities and dedicated logging/tracking tables.

## 2. Generated Artifacts

The migration process generates the following BigQuery and deployment artifacts:

*   **`ddl/job_error_log.sql`**:
    *   **Role**: BigQuery DDL (Data Definition Language) script to create or replace the `job_error_log` table. This table is designed to capture detailed error messages, stack traces, and input parameters for failed job executions, replacing the functionality of `f_alis_msgerr.ksh`.
*   **`ddl/job_tracking.sql`**:
    *   **Role**: BigQuery DDL script to create or replace the `job_tracking` table. This table is used to log the start, end, status, and statistics (e.g., records processed) of each job run, replacing the functionality of the commented-out FOS job management calls (`FOSJobErzeugeEintrag`, `FOSJobDeaktivate`).
*   **`ddl/target_bp_ta_msisdn.sql`**:
    *   **Role**: BigQuery DDL script to create or replace a placeholder target table named `target_bp_ta_msisdn`. This table is intended to receive the output data generated by the core SQL logic (`proc_d_ausd_bp_ta_msisdn`). **Note: Its schema is a placeholder and must be updated based on the actual output of `d_ausd_bp_ta_msisdn.sql`.**
*   **`stored_procedures/proc_d_ausd_bp_ta_msisdn.sql`**:
    *   **Role**: BigQuery Stored Procedure that encapsulates the core data processing logic originally found in `d_ausd_bp_ta_msisdn.sql`. This procedure is designed to be called by the main orchestration procedure. **Note: The current implementation is a placeholder and requires the actual translation of `d_ausd_bp_ta_msisdn.sql` content into BigQuery SQL.**
*   **`stored_procedures/proc_ausd_bp_ta_msisdn.sql`**:
    *   **Role**: The main BigQuery Stored Procedure that replaces the `k_ausd_bp_ta_msisdn.ksh` shell script. It handles parameter validation, date derivation, calls `proc_d_ausd_bp_ta_msisdn` for core logic execution, performs record counting, and manages error logging and job tracking.
*   **`deploy.sh`**:
    *   **Role**: A shell script to automate the deployment of all BigQuery DDLs and Stored Procedures to the specified GCP project and BigQuery dataset. It uses the `bq` command-line tool.

## 3. Key Design Decisions

The migration approach is based on the following key design decisions:

*   **BigQuery Stored Procedures for Orchestration**: The entire orchestration logic of the KornShell script (parameter parsing, validation, date derivation, error handling, SQL execution) is re-implemented as a BigQuery Stored Procedure (`proc_ausd_bp_ta_msisdn`). This decision leverages BigQuery's native scripting capabilities, eliminating external shell dependencies and centralizing the job logic within the data platform.
*   **Modular SQL Logic**: The core SQL logic from `d_ausd_bp_ta_msisdn.sql` is encapsulated in a separate BigQuery Stored Procedure (`proc_d_ausd_bp_ta_msisdn`). This promotes modularity, reusability, and easier maintenance, allowing the orchestration and core logic to evolve independently.
*   **Native BigQuery Utilities**: All shell utility scripts (`f_alis_msgerr.ksh`, `h_alis_date.ksh`, `h_alis_parameter.ksh`, `gestern.ksh`) are replaced by equivalent BigQuery SQL functions and scripting constructs (e.g., `RAISE ERROR`, `SAFE.PARSE_DATE`, `IF` statements, `CURRENT_DATE()`, `DATE_SUB()`). This removes external file system dependencies and integrates logic directly into the BigQuery environment.
*   **Structured Logging and Tracking**: Error reporting (`f_alis_msgerr.ksh`) is replaced by structured logging to a `job_error_log` BigQuery table. Similarly, the commented FOS job management is replaced by updates to a `job_tracking` BigQuery table. This provides a centralized, queryable, and structured audit trail for job executions.
*   **Direct BigQuery Execution**: The `starteSQLSkript` function and its reliance on SQL*Plus are entirely replaced by direct calls to BigQuery Stored Procedures, leveraging BigQuery's optimized execution engine.
*   **Record Counting via SQL**: The mechanism of writing record counts to a temporary file and then `cat`ing it is replaced by a direct `COUNT(*)` query against the target table within the BigQuery Stored Procedure, assigning the result to a `DECLARE` variable. This is a more idiomatic and efficient BigQuery approach.

**Notable Trade-offs:**

*   **Increased BigQuery SQL Complexity**: The orchestration logic, previously handled by shell scripting, now resides within BigQuery SQL, potentially making the BigQuery procedures more complex than simple DML statements.
*   **Loss of Direct OS Interaction**: The ability to execute arbitrary shell commands or interact with the file system is lost. Any such requirements would need to be re-evaluated for BigQuery-compatible solutions (e.g., Cloud Storage for file operations, Cloud Functions for external calls).
*   **Placeholder Dependencies**: The migration relies heavily on placeholders for the core SQL logic and target table schema, requiring significant manual effort to complete.

## 4. Manual Steps Before Go-Live

Before the migrated job can be considered ready for production, several manual steps are required:

1.  **GCP Project and Billing Setup**:
    *   Ensure a Google Cloud Project is active and has billing enabled.
    *   Identify or create a dedicated BigQuery dataset (e.g., `your_bq_dataset`) within your GCP project where these objects will reside.

2.  **IAM/Permissions**:
    *   A service account or user executing the `deploy.sh` script and running the BigQuery procedures must have sufficient IAM roles. Recommended roles include:
        *   `BigQuery Data Editor` (for creating/updating tables and procedures, inserting data).
        *   `BigQuery Job User` (for running queries and procedures).
        *   `BigQuery Metadata Viewer` (for viewing dataset/table information).

3.  **Update Placeholders**:
    *   **`your_gcp_project` and `your_bq_dataset`**: Replace all occurrences of these placeholders in `ddl/*.sql`, `stored_procedures/*.sql`, and `deploy.sh` with your actual GCP Project ID and BigQuery Dataset ID.

4.  **Source Table (`PoolBasisprodukt`) Migration/Availability**:
    *   The original `d_ausd_bp_ta_msisdn.sql` likely reads from a source table, inferred as `PoolBasisprodukt`. Ensure this source data is migrated to BigQuery and available in the specified dataset (e.g., `your_gcp_project.your_bq_dataset.PoolBasisprodukt`). The schema of this source table must be known.

5.  **Complete `proc_d_ausd_bp_ta_msisdn.sql` Implementation**:
    *   **Crucial Step**: The `stored_procedures/proc_d_ausd_bp_ta_msisdn.sql` file is currently a placeholder. The actual SQL logic from the original `d_ausd_bp_ta_msisdn.sql` script must be translated into BigQuery SQL and inserted into this procedure. This includes:
        *   Identifying all source tables and their BigQuery equivalents.
        *   Translating all `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `MERGE` statements.
        *   Converting any proprietary SQL functions or constructs to BigQuery standard SQL.
        *   Ensuring correct parameter usage (`p_job_kennung`, `p_stichtag_date`, etc.).

6.  **Define `target_bp_ta_msisdn` Schema**:
    *   **Crucial Step**: The `ddl/target_bp_ta_msisdn.sql` file provides a placeholder schema. Based on the completed `proc_d_ausd_bp_ta_msisdn.sql` (which defines what data is written), the schema for `target_bp_ta_msisdn` must be accurately defined. This includes column names, data types, partitioning, and clustering strategies.

7.  **Configuration Resolution**:
    *   If the original `$HOME/.dw_init` or `${BERT_DIR_ROOT}` contained critical configuration values (e.g., database connection strings, specific paths, thresholds), these need to be:
        *   Hardcoded as `DECLARE` constants within the BigQuery procedures.
        *   Passed as additional parameters to the procedures.
        *   Stored in a dedicated BigQuery configuration table.

8.  **Deployment**:
    *   After updating all placeholders and completing the core SQL logic, execute the `deploy.sh` script to deploy all BigQuery DDLs and Stored Procedures.
    *   `./deploy.sh`

9.  **Scheduling (if applicable)**:
    *   If external scheduling is required (beyond BigQuery's native scheduling capabilities for stored procedures), set up a Cloud Composer (Airflow) DAG or Cloud Workflow to invoke `your_gcp_project.your_bq_dataset.proc_ausd_bp_ta_msisdn` with the necessary parameters.

## 5. Known Gaps & Unresolved References

The following items are identified as known gaps or require further resolution:

*   **Core SQL Logic (`d_ausd_bp_ta_msisdn.sql`)**: The most significant gap is the actual content of `d_ausd_bp_ta_msisdn.sql`. Its translation into `proc_d_ausd_bp_ta_msisdn.sql` is a placeholder and requires detailed analysis and implementation. This is a **B4 (Redesign/Re-implementation)** item.
*   **Target Table Schema (`target_bp_ta_msisdn`)**: The schema for the target table is a placeholder. Its definitive structure depends entirely on the output of the translated `d_ausd_bp_ta_msisdn.sql` logic. This is also a **B4** item.
*   **Source Table (`PoolBasisprodukt`) Schema and Existence**: The design infers `PoolBasisprodukt` as a source. Its exact schema, location in BigQuery, and data availability need to be confirmed.
*   **Commented-out Code Reactivation**: The original script contains commented-out sections for FOS job management and data manipulation (`sed`, `sort`, `join`). A decision is needed on whether these functionalities should be reactivated and migrated. If so, they would require additional BigQuery SQL or potentially external processing (e.g., Dataflow for complex `sed`/`sort`/`join` if data volumes are large).
*   **`BERT_DIR_ROOT` and `DW_DIR_UTL` Resolution**: The specific values and usage patterns of these environment variables need to be fully understood to ensure any critical configurations or paths they pointed to are correctly handled in the BigQuery environment.
*   **`starteSQLSkript` Functionality Details**: While assumed to be a simple SQL*Plus wrapper, any complex logic within `starteSQLSkript` (e.g., custom error handling, specific connection parameters, pre/post-SQL execution commands) needs to be identified and replicated in BigQuery.
*   **Original Script Complexity Tier**: The complexity tier of `k_ausd_bp_ta_msisdn.ksh` was not available. A manual assessment is needed to confirm the effort and potential hidden complexities.

## 6. Validation

Validation of the migrated job involves several stages:

1.  **Deployment Validation**:
    *   **How to run**: Execute the `deploy.sh` script.
    *   **What "passing" means**: The script completes without errors. Verify in the BigQuery UI or using `bq ls` commands that `job_error_log`, `job_tracking`, `target_bp_ta_msisdn` tables, and `proc_d_ausd_bp_ta_msisdn`, `proc_ausd_bp_ta_msisdn` stored procedures exist in the target dataset.

2.  **Unit Testing of `proc_ausd_bp_ta_msisdn`**:
    *   **How to run**: Call `proc_ausd_bp_ta_msisdn` directly from the BigQuery console or `bq query` command with various input parameters.
        *   **Valid inputs**: Provide valid `Jobkennung`, `Stichtag` (DDMMYYYY), `EintragsNr`, and `wiederanlaufWert` (can be NULL).
        *   **Invalid `Stichtag`**: Provide a malformed date string (e.g., "32012023", "20230101").
        *   **Missing required parameters**: Call with `NULL` or empty strings for `p_job_kennung`, `p_stichtag_ddmmyyyy`, `p_eintragsnr`.
    *   **What "passing" means**:
        *   For valid inputs: The procedure executes successfully, `job_tracking` is updated with `SUCCEEDED` status, and `target_bp_ta_msisdn` contains expected data (once `proc_d_ausd_bp_ta_msisdn` is fully implemented).
        *   For invalid inputs: The procedure raises an error (e.g., `SIGNAL SQLSTATE '45000'`), and an entry is logged in `job_error_log` with `ERROR` severity and the appropriate error message. `job_tracking` should reflect a `FAILED` status.

3.  **Data Validation (Functional Testing)**:
    *   **How to run**:
        *   Execute the original `k_ausd_bp_ta_msisdn.ksh` script in the legacy environment for a specific `Stichtag` and capture its output.
        *   Execute the migrated `proc_ausd_bp_ta_msisdn` in BigQuery with the *exact same* parameters.
        *   Compare the data generated in `target_bp_ta_msisdn` with the output of the legacy job. This may involve comparing record counts, specific column values, or checksums.
    *   **What "passing" means**: The output data in BigQuery (e.g., `target_bp_ta_msisdn`) is identical to the output produced by the legacy job for the same inputs. Record counts in `job_tracking` match legacy counts.

4.  **Performance Testing**:
    *   **How to run**: Execute the migrated procedure with production-like data volumes and compare its execution time and resource consumption (slots, bytes processed) against the legacy job's performance.
    *   **What "passing" means**: The migrated job performs within acceptable timeframes and resource limits, ideally matching or improving upon legacy performance.

## 7. Rollback Procedure

In case of critical issues or failure to meet validation criteria, the following rollback procedure should be followed:

1.  **Halt New Executions**: Immediately stop any scheduled or manual executions of the `your_gcp_project.your_bq_dataset.proc_ausd_bp_ta_msisdn` BigQuery stored procedure. If using Cloud Composer or Workflows, disable or pause the relevant DAGs/workflows.

2.  **Reactivate Legacy Job**: Re-enable and restart the original `vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/k_ausd_bp_ta_msisdn.ksh` script in the legacy environment. Ensure it can process data from the point where the BigQuery migration attempt began, or from the last known good state.

3.  **Delete BigQuery Objects (Optional but Recommended)**:
    *   To ensure a clean state and avoid confusion, delete the migrated BigQuery objects.
    *   **Delete Stored Procedures**:
        ```bash
        bq rm -f --routine your_gcp_project:your_bq_dataset.proc_ausd_bp_ta_msisdn
        bq rm -f --routine your_gcp_project:your_bq_dataset.proc_d_ausd_bp_ta_msisdn
        ```
    *   **Delete Tables**:
        ```bash
        bq rm -f your_gcp_project:your_bq_dataset.target_bp_ta_msisdn
        bq rm -f your_gcp_project:your_bq_dataset.job_error_log
        bq rm -f your_gcp_project:your_bq_dataset.job_tracking
        ```
    *   **Note**: If the `target_bp_ta_msisdn` table contains data that needs to be preserved or analyzed for debugging, consider renaming it or moving it to a quarantine dataset instead of outright deletion.

4.  **Data Reconciliation (if necessary)**:
    *   If the BigQuery job partially processed data or wrote incorrect data to `target_bp_ta_msisdn` before rollback, assess the impact. Depending on the data, a cleanup or reconciliation process might be necessary to ensure data consistency in the legacy system or any downstream systems that might have consumed the BigQuery output.

5.  **Post-Rollback Verification**:
    *   Confirm that the legacy job is running as expected and producing correct output.
    *   Verify that no BigQuery objects related to this migration are inadvertently running or causing issues.
