# MIGRATION_NOTES.md

## 1. Summary

This document details the migration of the legacy KornShell script `vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/k_ausd_bp_ta_bpr_opt_text.ksh`. The original script served as an orchestration wrapper, handling parameter validation, date checks, environment setup, and executing a core SQL script (`d_ausd_bp_ta_bpr_opt_text.sql`) to process data and log record counts.

The migration re-implements this functionality to Google Cloud Platform, specifically targeting:
*   **Google BigQuery**: For core data processing logic, data storage, and audit logging, encapsulated within a BigQuery Stored Procedure.
*   **Google Cloud Composer (Apache Airflow)**: For job orchestration, scheduling, and parameter management.

## 2. Generated Artifacts

The migration process generated the following files:

*   **`sql/ddl/source_dataset.PoolBasisprodukt.sql`**
    *   **Role**: Data Definition Language (DDL) script to create the `PoolBasisprodukt` table in BigQuery. This table serves as a BigQuery representation of the original Oracle `PoolBasisprodukt` table, acting as a source for the migrated logic.
*   **`sql/ddl/job_error_audit.sql`**
    *   **Role**: DDL script to create the `job_error_audit` table in BigQuery. This table is used to log detailed information about any errors encountered during the execution of the BigQuery Stored Procedure, replacing parts of the legacy `f_alis_msgerr.ksh` functionality.
*   **`sql/ddl/job_run_audit.sql`**
    *   **Role**: DDL script to create the `job_run_audit` table in BigQuery. This table records the execution status, start/end times, and processed record counts for each run of the BigQuery Stored Procedure, replacing the commented-out `FOSJobErzeugeEintrag` functionality.
*   **`sql/ddl/sof_ta_bpr_optionen.sql`**
    *   **Role**: DDL script to create the `sof_ta_bpr_optionen` table in BigQuery. This is identified as a source table critical for the core business logic migrated from `d_ausd_bp_ta_bpr_opt_text.sql`.
*   **`sql/ddl/sof_ta_bpr_beschr.sql`**
    *   **Role**: DDL script to create the `sof_ta_bpr_beschr` table in BigQuery. This is another source table critical for the core business logic migrated from `d_ausd_bp_ta_bpr_opt_text.sql`.
*   **`sql/ddl/target_bp_ta_bpr_opt_text.sql`**
    *   **Role**: DDL script to create the `target_bp_ta_bpr_opt_text` table in BigQuery. This table serves as the final destination for the processed data generated by the core business logic.
*   **`sql/procedures/r_ausd_bp_ta_bpr_opt_text.sql`**
    *   **Role**: BigQuery Stored Procedure. This is the central piece of the migration, encapsulating all the orchestration logic (parameter validation, date derivation, error handling, audit logging) and the core business logic originally found in `d_ausd_bp_ta_bpr_opt_text.sql`. It replaces the entire KornShell script.
*   **`dags/k_ausd_bp_ta_bpr_opt_text_dag.py`**
    *   **Role**: Apache Airflow DAG (Directed Acyclic Graph) written in Python. This DAG is responsible for orchestrating the execution of the `r_ausd_bp_ta_bpr_opt_text` BigQuery Stored Procedure, passing necessary parameters, and managing its schedule within Cloud Composer.

## 3. Key Design Decisions

*   **Native BigQuery Implementation for Core Logic**: The core business logic from `d_ausd_bp_ta_bpr_opt_text.sql` and the orchestration logic from `k_ausd_bp_ta_bpr_opt_text.ksh` are consolidated into a single BigQuery Stored Procedure (`r_ausd_bp_ta_bpr_opt_text`).
    *   **Rationale**: This leverages BigQuery's native capabilities for data processing, eliminates the need for external SQL clients (like `sqlplus`), and keeps the entire data transformation pipeline within the BigQuery ecosystem, simplifying management and scaling.
    *   **Trade-offs**: Increases the complexity of the BigQuery Stored Procedure itself, requiring BigQuery-specific SQL knowledge for maintenance.
*   **Cloud Composer (Airflow) for Orchestration**: Apache Airflow on Cloud Composer is chosen for scheduling and invoking the BigQuery Stored Procedure.
    *   **Rationale**: Provides a robust, cloud-native, and scalable solution for job scheduling, dependency management, and monitoring, replacing the basic shell-based scheduling. It allows for flexible parameter passing and integration with other GCP services.
    *   **Trade-offs**: Introduces a new technology stack (Python/Airflow) for orchestration, requiring Airflow expertise.
*   **In-Procedure Error Handling and Audit Logging**: Error validation and logging (previously handled by `f_alis_msgerr.ksh` and `FOSJobErzeugeEintrag`) are re-implemented directly within the BigQuery Stored Procedure using `SIGNAL SQLSTATE` for immediate error reporting and `INSERT` statements into dedicated `job_error_audit` and `job_run_audit` tables.
    *   **Rationale**: Centralizes error management and auditing within the data platform, providing structured, queryable logs for operational insights.
    *   **Trade-offs**: Requires explicit `INSERT` statements for logging, which adds verbosity to the stored procedure code.
*   **Direct Date Function Translation**: Legacy date utility scripts (`h_alis_date.ksh`, `gestern.ksh`) are replaced by native BigQuery date functions (`CURRENT_DATE()`, `DATE_SUB()`, `SAFE.PARSE_DATE()`).
    *   **Rationale**: Simplifies the code, removes external script dependencies, and utilizes optimized BigQuery functions.
*   **Parameter Management via Stored Procedure Arguments**: Shell script parameter parsing (`getopts`) is replaced by direct input parameters to the BigQuery Stored Procedure.
    *   **Rationale**: Provides a clear, type-safe interface for the procedure, enforced by BigQuery.
*   **Placeholder for `PoolBasisprodukt`**: The `PoolBasisprodukt` table, identified as a critical source, is represented by a DDL in `source_dataset`.
    *   **Rationale**: Acknowledges the need for this data in BigQuery and provides a placeholder for its ingestion, which is an external dependency.

## 4. Manual Steps Before Go-Live

The following manual steps are required to prepare the environment and deploy the migrated solution:

1.  **GCP Project and BigQuery Dataset Setup**:
    *   Ensure the target GCP project (`project`) and BigQuery datasets (`dataset`, `source_dataset`) exist. If not, create them.
2.  **IAM Permissions**:
    *   Grant the service account used by Cloud Composer (Airflow) the necessary BigQuery permissions:
        *   `BigQuery Data Editor` on `project.dataset` (to create/update tables, execute procedures, insert into audit tables).
        *   `BigQuery Data Viewer` on `project.source_dataset` (to read source data).
        *   `BigQuery Job User` (to run BigQuery jobs).
3.  **Deploy BigQuery DDLs**:
    *   Execute all DDL scripts (`sql/ddl/*.sql`) in the correct order to create the necessary tables in BigQuery.
        *   `source_dataset.PoolBasisprodukt`
        *   `project.dataset.job_error_audit`
        *   `project.dataset.job_run_audit`
        *   `project.dataset.sof_ta_bpr_optionen`
        *   `project.dataset.sof_ta_bpr_beschr`
        *   `project.dataset.target_bp_ta_bpr_opt_text`
    *   **Note**: Replace `project` and `dataset` placeholders in the DDLs with actual GCP Project ID and BigQuery Dataset ID.
4.  **Deploy BigQuery Stored Procedure**:
    *   Execute the `sql/procedures/r_ausd_bp_ta_bpr_opt_text.sql` script to create the stored procedure in `project.dataset`.
    *   **Note**: Replace `project` and `dataset` placeholders in the stored procedure with actual GCP Project ID and BigQuery Dataset ID.
5.  **Ingest Source Data**:
    *   Establish and run data ingestion pipelines to populate `project.source_dataset.PoolBasisprodukt`, `project.dataset.sof_ta_bpr_optionen`, and `project.dataset.sof_ta_bpr_beschr` with current and historical data from their respective legacy sources (e.g., Oracle). This is a critical prerequisite for the stored procedure to function correctly.
6.  **Deploy Airflow DAG**:
    *   Upload the `dags/k_ausd_bp_ta_bpr_opt_text_dag.py` file to the DAGs folder of your Cloud Composer environment.
    *   **Note**: Replace `project` and `dataset` placeholders in the DAG with actual GCP Project ID and BigQuery Dataset ID.
7.  **Configure Airflow DAG Schedule**:
    *   Once deployed, enable the DAG in the Airflow UI and configure its schedule as per operational requirements (currently `schedule=None`, implying manual or external trigger).

## 5. Known Gaps & Unresolved References

*   **Detailed `d_ausd_bp_ta_bpr_opt_text.sql` Content**: The provided design document and generated code assume a simple `INNER JOIN` for the core logic. A thorough analysis and migration of the *actual* content of `d_ausd_bp_ta_bpr_opt_text.sql` is paramount. If it contains complex logic (e.g., multiple joins, subqueries, window functions, DML operations beyond simple `INSERT`), the `r_ausd_bp_ta_bpr_opt_text` stored procedure will need significant refinement.
*   **Oracle Schema Details**: The DDLs for `PoolBasisprodukt`, `sof_ta_bpr_optionen`, and `sof_ta_bpr_beschr` are generic. The precise schema (column names, data types, nullability, primary keys) of the original Oracle tables must be used to create accurate BigQuery tables and ensure data integrity during ingestion.
*   **`p_wiederanlaufWert` Usage**: The original script initializes `p_wiederanlaufWert`, but its specific usage within the KornShell script or the invoked `d_ausd_bp_ta_bpr_opt_text.sql` was not fully clear from the analysis. The migrated stored procedure accepts it as a parameter but does not currently use it. This needs to be clarified to ensure no business logic is missed.
*   **Error Handling Fidelity**: While a basic error logging mechanism is in place, the exact error codes and messages from the legacy `f_alis_msgerr.ksh` and `DWMSG_MeldeFehler` might not be perfectly replicated. Further refinement may be needed to match legacy error reporting if required.
*   **Legacy Flat-File Processing (Commented)**: The original script contained commented-out sections for processing flat files (`cibasis_data*.dat`) using `sed`, `sort`, and `join`. If these operations are ever reactivated or represent dormant business logic, they would require additional migration effort to translate into BigQuery SQL or Dataflow pipelines.
*   **`project` and `dataset` Placeholders**: All generated code uses `project` and `dataset` as placeholders. These *must* be replaced with the actual GCP Project ID and BigQuery Dataset IDs before deployment.

## 6. Validation

Validation ensures the migrated solution functions correctly and produces accurate results.

### How to Run Tests

1.  **Unit Test BigQuery Stored Procedure**:
    *   Manually execute the `r_ausd_bp_ta_bpr_opt_text` stored procedure directly in the BigQuery console or via the `bq query` command-line tool.
    *   Test with various parameter combinations:
        *   Valid `p_JobKennung`, `p_EintragsNr`, `p_Stichtag` (DDMMYYYY format).
        *   Missing `p_JobKennung`, `p_EintragsNr`, `p_Stichtag`.
        *   Invalid `p_Stichtag` format (e.g., "2023-01-01", "ABC").
    *   Verify that `job_error_audit` and `job_run_audit` tables are populated correctly for both success and failure scenarios.
2.  **Integration Test (Airflow DAG)**:
    *   Trigger the `k_ausd_bp_ta_bpr_opt_text_dag` from the Airflow UI.
    *   Monitor the DAG run in Airflow logs for successful completion or errors.
    *   Verify that the BigQuery Stored Procedure is invoked with the correct parameters.
3.  **Data Validation (End-to-End)**:
    *   Perform a test run of the legacy KornShell script and the migrated Airflow DAG/BigQuery Stored Procedure using the *same input data* and parameters.
    *   Compare the output data in `target_bp_ta_bpr_opt_text` with the output of the legacy system.
    *   Compare the record counts reported in `job_run_audit` with the record counts from the legacy script's logs.

### What "Passing" Means

A successful migration validation means:

*   The `k_ausd_bp_ta_bpr_opt_text_dag` completes successfully in Airflow without task failures.
*   The `r_ausd_bp_ta_bpr_opt_text` stored procedure executes without BigQuery errors for valid inputs.
*   For invalid inputs, the stored procedure correctly signals an error and logs it to `project.dataset.job_error_audit`.
*   The `project.dataset.job_run_audit` table contains an entry for each execution, accurately reflecting the `status` (SUCCESS/FAILED), `start_time`, `end_time`, and `processed_records`.
*   The data in `project.dataset.target_bp_ta_bpr_opt_text` is identical (or functionally equivalent, if minor data type changes occurred) to the data produced by the legacy `d_ausd_bp_ta_bpr_opt_text.sql` script for the same input.
*   The `processed_records` count in `job_run_audit` matches the count reported by the legacy script.

## 7. Rollback Procedure

In case of critical issues or unexpected behavior after go-live, the following rollback procedure can be initiated:

1.  **Disable Airflow DAG**: Immediately disable the `k_ausd_bp_ta_bpr_opt_text_dag` in the Airflow UI to prevent further executions of the migrated job.
2.  **Re-enable Legacy Script**: Re-enable the original `vobs/dw_source/isrpt/isbert/SQL/aktuell/aufbereitung/bin/k_ausd_bp_ta_bpr_opt_text.ksh` script in its legacy environment. Ensure its scheduler is reactivated.
3.  **Data Cleanup (Optional but Recommended)**:
    *   If the migrated job has written incorrect or partial data to `project.dataset.target_bp_ta_bpr_opt_text`, truncate or delete the affected partitions/rows in this table to prevent data corruption.
    *   The audit tables (`job_error_audit`, `job_run_audit`) can generally be left as is, as they contain historical execution logs.
4.  **Monitor Legacy System**: Verify that the legacy script is running as expected and producing correct output.
5.  **Investigation**: Analyze the root cause of the rollback, using the `job_error_audit` and `job_run_audit` tables, Airflow logs, and BigQuery logs for debugging.
6.  **Cleanup Migrated Assets (Post-Rollback)**: Once the legacy system is stable and the issue is understood, the BigQuery stored procedure and DDLs can be dropped if a complete re-migration or redesign is planned.
